# 本地知识库运维手册（实测样本 A）

> 这是一份**测试用虚构文档**，专门用来验证解析、分块、检索、引用与问答。
> 里面的数字都是故意写死的，答案必须能从原文逐字找到；系统答不出这些数字，就是流水线有问题。

## 1. 服务清单与端口

本机私有化部署一共四个进程，端口固定如下，任何一次变更都要走工单：

| 服务 | 端口 | 健康检查 | 停机影响 |
|---|---|---|---|
| PostgreSQL 17 | 5432 | `pg_isready -h 127.0.0.1 -p 5432` | 全站不可用 |
| rag-api | 8080 | `GET /api/health` | 前端只剩静态页 |
| rag-web | 5173 | 浏览器直接打开 | 只影响人看 |
| LM Studio Local Server | 1234 | `GET /v1/models` | 入库与问答全部停摆 |

LM Studio 的端口 1234 只在局域网内可达，**严禁**做端口映射或反向代理到公网；
跨机器访问时必须在 LM Studio 的 Local Server 面板里勾选 Serve on Local Network，
并在防火墙放行入站 TCP 1234。工单号 OPS-2026-118 记录过一次误配：把 1234 映射到了公网，
四小时内出现 117 次匿名 `/v1/completions` 调用，当天即回收。

## 2. 备份与恢复

数据库备份保留 **35 天**，每天 03:10 由 `pg_dump` 出一份自定义格式文件，落在 `/backup/rag/`。
对象存储目录 `data/objects` 里的原始文件不参与每日备份，改为**每周日 04:00 全量同步一次**，
理由是原件不可变、体积大，而数据库里的向量与正文才是会持续变化的部分。

恢复演练每季度做一次，验收标准只有一条：
从备份恢复出的库，`kb_segment` 里 `emb_status='READY'` 的行数必须与备份前一致，
且对同一个问题检索回来的 top6 chunk_no 完全相同。行数对得上但顺序对不上，
通常是 embedding 模型换了版本——这时要全量重算，不能留着两套向量空间混检。

单篇文档的恢复不需要动数据库：把原件重新上传一次即可，
系统按 sha256 判断内容是否已存在，同库同哈希不会重复消耗 embedding。

## 3. 入库参数

分块参数写在 `rag.ingest.chunk` 里，默认值是子块 **400 字**、相邻块重叠 **60 字**、
父块 **1200 字**、子块最短 **120 字**。子块上限来自 embedding 模型的 512 token 窗口：
中文大约一字一 token，超过 400 字的部分会被模型静默截断，
表现为「文档里明明写了却搜不到」，而不是任何报错。

embedding 一批 **16 条**，本机实测 16 条一批 0.41 秒、单条 0.04 秒。
并发固定为 1：单机单卡上调大并发不会更快，只会让 embedding 排队并撞 90 秒超时。
入库任务租约 **10 分钟**，最多重试 **3 次**；worker 崩溃后任务最多卡十分钟就会被重新排队。

扫描件、纯图片 PDF、乱码文件属于永久失败，错误码分别是
`GARBLED_TEXT`（文本可读比例过低）、`NO_SEGMENT`（清洗后没有任何可入库正文）、
`DIM_MISMATCH`（返回向量维度与 `rag.embedding.dim` 不符）。
这三类不消耗重试预算，直接置 FAILED 并在界面给出下一步动作。

## 4. 检索与问答

检索默认混合模式：向量路与关键词路各取 **40** 条候选，再用 RRF 融合，平滑常数 k=60。
最终返回 **top6**。RRF 分数量纲只有 0.01x，所以混合模式的阈值单独配成 0.012；
照抄纯向量模式的 0.45 会把所有结果滤光，看起来像「库里没有相关内容」，实际是配置错误。

问答上下文预算按当前 chat 模型的真实窗口算：窗口 4096，预留输出 700 token，
模板与问题本身预留 900 字，历史最多带 **4 轮 / 800 字**。
调大窗口要同时在 LM Studio 里调 context，否则超窗会被服务端裁掉最前面的引用，
答案里的 `[1]` 会指向一段模型根本没看到的文字。

检索命中不足时宁可不答：纯向量模式下相似度低于 0.45 直接拒答，
拒答文案固定为「知识库里没有找到可靠依据」，并保留引用区为空，
不让前端自己编一句「我不确定」。

## 5. 日常巡检

每天早上看三件事：

1. `GET /api/health?models=true` —— PG、chat、embedding、模型名回显四项全 UP。
   模型名对不上时是 DOWN 而不是 DEGRADED，因为此时写库就是往向量空间灌错模型产物。
2. 文档列表里停在中间态超过 10 分钟的行 —— 通常是 worker 挂了或租约还没过期。
3. `FAILED` 行的 `errorCode` —— `EMBED_BACKEND` 是网络或模型服务问题，可以重试；
   上面第 3 节列的三个码重试也没用，要回头修文件。

日志里每条请求带一个 traceId，前端错误提示末尾会原样带出，
报障时给这个串比给截图快：`grep 后端日志里的 traceId` 能直接定位到那次检索用了哪条 SQL、
召回了几块、有没有降级。

## 6. 常见故障与处置

**问答卡住不动。** 先看 LM Studio 是否还在服务，再看 rag-api 日志里有没有
`HTTP/2 upgrade` 相关字样。历史事故 OPS-2026-131：客户端默认协商 h2c，
LM Studio 不响应协议升级，请求既不报错也不返回，表现为线程池耗尽而不是异常栈。
处置办法是统一强制 HTTP/1.1 并设 5 秒连接超时，已在代码里固化。

**换了 embedding 模型后检索变差。** 新模型的向量空间与旧的不互通，
必须全量重算。界面路径是逐篇「重解析」，批量路径是导出归档包后用「强制重算向量」导入。

**答案引用跳过去的位置不对。** 先确认那一块有没有被人工编辑过：
`edited_at` 非空的行，`char_start/char_end` 描述的是**编辑前**的正文位置，
所以跳转偏移会看着偏，这是设计如此，不是 bug。

**导入归档包后文档数量比包里少。** 看返回体里的 `notes`：
同 sha256 已存在的文档按规矩跳过，正文空白的跳过，单篇异常只影响自己，
三种都会在 notes 里留一行说明。

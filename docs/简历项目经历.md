## 三、完整版（推荐，6 条）

### 智能知识库问答系统（RAG，私有化部署） — 全栈 / 主要开发者
`2026.03 - 2026.11` 技术栈：Vue 3.5 · TypeScript · Vite 8 · Element Plus · Java 17 · Spring Boot 4.1 · langchain4j · PostgreSQL 17 · pgvector · zhparser · Flyway · Testcontainers · Maven

**项目简介**：面向企业内部文档的智能问答系统，用户上传 PDF/Word/Markdown 等资料后可以直接用自然语言提问，
答案带原文引用位置可溯源。目标是**全本地私有化**——文档、向量、模型推理都留在内网，不依赖任何云端 API。
本人独立完成需求梳理、架构设计、前后端实现、部署脚本与端到端回归。

**职责与产出**：

- **混合检索**：自写 SQL 实现「pgvector 向量路 + 中文全文检索关键词路」双路召回，用 RRF（`k=60`）融合排名，
  解决纯向量检索在中文专有名词、编号、短词上召回不稳定的问题；两路分数不在同一量纲，因此阈值也按生效模式配对，
  避免把向量阈值照抄到 RRF 分数上导致召回被清空。

- **中文分词工程化**：官方 PG 镜像不含 zhparser，自建镜像（编译安装扩展 + `pg_retakeopclass` 支持），
  并把"分词扩展不可用"设计成三级降级而非启动失败——`tsvector(zhparser)` → `pg_trgm` 子串匹配 → 只走向量路，
  降级结果由启动探测缓存，健康检查与诊断接口能直接说明当前实际走哪一路。

- **父子分块与入库流水线**：语义分块（章节作父块 1200 字、句子级子块 400 字、重叠 60 字），
  子块用于精确命中、命中后取父块喂给模型，兼顾召回精度与上下文完整性；入库以任务队列驱动
  （租约 10 分钟 / 最多 3 次重试 / 永久失败与临时失败分别记账），批量向量化（16 条/批），
  索引切换用「影子代次 + available 开关」在**单事务**内完成，保证重算过程中检索不会读到半成品。

- **上下文预算与流式问答**：按 `n_ctx` 反推可装资料字符数（预留回答与提示词；窗口按模型加载实测，本机实测 16384 时装配上限 14784 字），
  装不下时不静默截半句——置 `truncated` 标记并在 SSE `meta` 帧里告知前端；
  检索无命中时**不调用模型**直接返回固定话术并记 `REFUSED`，从机制上压幻觉；
  问答走 SSE（`meta → delta* → done`），事件流外先落库，客户端断开也能保留已生成内容并标 `INTERRUPTED`；
  专用线程池（4 并发 + 8 队列）承载流式请求，避免长时间占用 Web 线程。

- **工程闭环**：后端 62 个类、约 7600 行主代码 / 39 个 REST 接口 / 9 张业务表，配套 **260 例不依赖数据库的单元测试**
  + 6 个 Testcontainers 集成测试（47 例，真 pgvector 上的迁移、检索谓词、归档落库与评测跑分），测试代码合计约 7000 行；
  端到端回归脚本 11 个步骤 / 62 项断言（含上传、轮询、三模式检索、契约负例、流式问答、块级禁用可逆、评测跑分、归档导出导入），
  一条命令判定里程碑是否退化。断言分两层：**契约层**（信封、字段、事件顺序）在没有数据库和模型的机器上也能全绿，
  **事实层**绑死故意写死的样本文档数值，防止"跑绿了但什么都没验"。

- **可运维性**：一键起停脚本 + 环境预检（JDK / Node 版本 / Docker 引擎可用性，15 秒超时判死而不是卡住），
  日志用 logback 按 20MB 滚动落 UTF-8 文件（Windows 控制台是 GBK，中文日志只有进文件才不会换机器就花），
  `traceId` 通过 `TaskDecorator` 跨线程传递，一次问答在 HTTP 线程与流式线程池之间的日志可以串起来查；
  另设 `/api/diagnostics` 暴露「依赖都通但结果可疑」的静默失败计数器（向量路降级、上下文截断、无证据拒答、补算向量失败）
  与配置风险告警，与 `/api/health`（只回答"通不通"）职责分开。

**30 秒版**：
"我做的是一个企业内网自用的知识库问答系统，就是把公司文档灌进去，员工用自然语言提问，回答带原文引用。
全部本地部署——数据库、向量、大模型都在内网，模型是 LM Studio 跑的开源模型，没有任何数据出外网。
前端 Vue 3 + TS，后端 Java + Spring Boot，检索用 pgvector 的向量检索加中文全文检索做双路召回、RRF 融合。
这个项目我是唯一一个开发者，从需求到部署都是自己做的。"

**2 分钟版**（30 秒版 + 下面三段，每段一个"我解决了一个不那么明显的问题"）：
1. "中文检索这块，纯向量对专有名词和编号召回不稳，所以要加全文检索；但官方 PG 镜像没有中文分词扩展，
   我就自己编译了带 zhparser 的镜像。同时我不想让"分词扩展没装"变成启动失败，所以做了三级降级：
   有 zhparser 走 tsvector，没有走 pg_trgm 按字匹配，再不行只剩向量——当前走哪一路会在健康检查里说出来。"
2. "上下文这块有两个坑，我一开始只看见一个。早期以为本地模型超窗口会静默丢掉中间段落，
   所以按窗口反推了一个字符预算：预留回答和提示词，装不下的块不硬塞，
   而是在流式协议的 meta 帧里明确告诉前端"被截断了、还有几条没装下"。
   后来用一条注定超限的请求去打模型才发现它其实是显式 HTTP 400，响应体里还带真实 `n_ctx`——
   于是超限单独成了一个 413 分支，不再和"模型服务不可用"混成一条错误，
   诊断端点也会因此报出"配置窗口比模型实测窗口小"，因为配小了不报错、只是每轮白白少装资料。"
3. "质量这块我不想依赖手工点，写了端到端回归。断言故意分两层：契约层只验接口信封、字段、SSE 事件顺序，
   在没有数据库和模型的机器上也能跑；事实层绑死我特意写死的样本文档里的数字，比如"备份保留 35 天"必须出现在答案里。
   这样"脚本崩了"和"断言红了"是两种不同的信号——前者修脚本，后者查系统。"
4. "回归只能保证'没坏'，保证不了'调参调对了'，所以后来加了一套只做检索的跑分：用例的判据是正文里必须出现的一段文字，
   而不是某个分块的 id——因为改分块尺寸之后 id 一定变，而评测要问的恰恰是'换了参数还找不找得到'。
   每轮跑分把当时的生效参数整套存进快照，两次分数才能归因到一个变量上。
   它抓到的第一个问题不是检索退化，而是我自己的判分：拒答标志被写成了常量，
   于是'混合模式压不住幻觉'这条唯一的真读数在报表上消失了一整轮。"

**关于两层断言**：契约层（信封、字段名、事件顺序、状态机迁移）在没有数据库和模型的机器上也能全绿，

必须连真库真模型跑，本机 2026-11-16 已经是 **62 项全绿（11 步 / PASS 62 / FAIL 0 / SKIP 0）**。
面试值得讲的是第一次真机跑揪出来的三处缺陷——`RETURNING` 被文本块剥掉空格拼成 `RETURNINGid`、
SSE 端点的起流前 400 被内容协商吃掉变成没有 body 的 500、缺 `kbIds` 兜底成"查默认库"——
**三条在当时的 216 例 mock 单测里全绿**，只有真机跑得出来；所以每条都补了能失败的测试，
其中 HTTP 那条用 `standaloneSetup` + 真实 `produces` 协商复现，去掉修复就变红。

### ❌ 不要写（写了对面试官就是送分题）

- **任何没有跑分记录背书的"准确率提升 XX%"**。评测集（M5e）现在有了，读数是**一次参数改动前后各一轮**，
  不是"接入模型前 vs 接入后"那种对比：同一批用例 hybrid `hit@1=hit@3=hit@K=MRR=1.0`，keyword 掉到 0.8
  （`空召回率=0.2`，掉的是那条"问句里没有正文字面 token"的工单题）。
  被追问"所以你的检索比别人的好多少"时，正确答案是范围："六条样本用例、单库、768 维 bge，
  这套评测的用途是**防止我改参数改退化**，不是给系统打市场分数。"
  真正值得讲的是它顺手量出的两个反直觉事实（详见 §12）：
  hybrid 的**拒答正确率是 0** 而不是 bug——RRF 闸门 0.012 谁都过，想让"库里真没有"落到拒答靠的是向量路的余弦闸门 0.45；
  以及 `hit@K=1.0` 与"资料没装进模型"可以同时成立，所以我把截断单独做成一项 `truncatedCaseRate`
  （实测 topK=50 时召回 22 块只装得下 12 块，检索分数毫无变化）。
- **"支持千万级文档""高并发"**。单机、单卡、HNSW 索引、连接池 10——被追问 TPS 就露底。说"我按部门级知识库的规模设计"。
- **"生产环境上线"**。没做鉴权与多租户，信任边界是局域网，这个你要么别说，要么主动说明边界（第九节话术）。
- **"用 Milvus/ES"**。本项目的检索完全在 PostgreSQL 里做，别把简历写成技术栈大杂烩。
- **langchain4j 的"封装能力"**。核心检索 SQL 是手写的（ADR-001：不用 `PgVectorEmbeddingStore`），
  langchain4j 在这里只承担模型客户端与文档解析，别说"用框架做了混合检索"。

## 九、可能被当场问到的"项目性质"问题，怎么答

**Q：这是公司项目还是个人项目？**
> 如实答。如果是个人项目就说："个人项目，独立完成。之所以自己做，是因为公司当时想用知识库问答但数据不能出内网，
> 市面上的方案要么要求 SaaS，要么检索这块没法满足中文资料的溯源要求，我就把整条链路自己实现了一遍。"

**Q：一个人做，怎么保证没有自嗨？没人评审你的设计。**
> "我用两个外置约束替代评审：一是所有非平凡的取舍都写成编号决策记录（项目里有 21 条 ADR，每条都是「决定 + 理由 + 代价」三段），
> 半年后自己也能看懂当时为什么这么选；二是回归脚本的期望值绑死在一批故意写死的样本文档上，
> 脚本对我讲"你实现了什么"不客气——它只认事实。比如我把向量阈值照抄到 RRF 分数上时，脚本立刻红了，
> 因为 RRF 分数量级是 0.01x，这种错误靠自审很容易放过。"

**Q：如果重做一遍，你会改什么？**
> "三点。第一，评测集应该在 M3 之后马上做，我把它排到 M5e，导致中间所有检索调参都靠样本断言和经验判断；
> 现在补上了，它第一个抓到的不是检索退化，而是我自己的判分写错——负例的 `refused` 被写成常量，
> 让"混合模式压不住幻觉"这条唯一的真读数在报表上消失了整整一轮；
> 第二，鉴权和多租户我明确推迟了，因为信任边界是局域网，但真要给公司用这块必须是第一批；
> 第三，前端一开始我想加更多组件库依赖，后来请求层删到只剩 fetch（ADR-014），SSE 分帧自己写反而更短更可控。"

（这一问答得好很加分：3–6 年岗考察的就是"能不能识别自己方案的边界"。）

# 实测指导（Docker 引擎能应答之后照着跑）

这份文档只写**能当场判定对错**的步骤。样本文件都在 `samples/`，事实是故意写死的，
答不出来就是流水线有问题，不是「模型不够聪明」。

- 预计耗时：首轮 60–90 分钟（大头是全量 embedding 与 Testcontainers 拉镜像）。
- 前置条件：LM Studio 已加载 chat 与 embedding 两个模型，且 Local Server 已开；
  `samples/` 七个文件在位；psql 用 `docker exec` 就够，不用本机装客户端。
- 所有命令默认在仓库根目录执行，PowerShell 与 Git Bash 都能跑；
  带 `curl` 的行在 PowerShell 里是 `Invoke-WebRequest` 的别名，建议用 Git Bash。
- 想先把「能自动判」的那一半跑掉：`deploy/smoke.sh`（加 `--archive` 连归档段一起跑）。
  它覆盖 §4 的检索量纲断言、§5 的样本入库与失败判定、§6 的三种模式与 rrf 量纲、
  §7 的流式问答与引用、§9 的块级禁用可逆、§10 的导出→删除→导入 CARRIED 与人工状态保留、
  §11 的诊断计数与 meta 对账、§12 的评测集建例→两轮跑分→删用例后历史仍可读。
  剩下必须手点的只有 §1~§3 的 psql/镜像检查、§4 的 `models=true` 逐项读数、§8 的反馈语义、
  §9 的分块覆盖预览，以及所有要看界面样子的部分——脚本只认接口，不认像素。

## 0. 一分钟自检：环境到底通不通

```bash
docker info --format '{{.ServerVersion}}'   # 期望：打印 2x.x.x，这一条通就算引擎通
wsl --status                                # 期望：默认版本 2
```

判不通要看**报的是哪一种**，本机 2026-11-16 实测纠正了此前写错的一条结论：

| 现象 | 真实原因 | 处置 |
|---|---|---|
| `docker version` 只回 Client；报 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine ... cannot find the file` | **Docker Desktop 进程没在运行**（服务 `com.docker.service` = Stopped）。这不等于虚拟化没开 | 启动 `C:\Program Files\Docker\Docker\Docker Desktop.exe`，引擎约 20 秒内应答 |
| `Get-CimInstance Win32_ComputerSystem` 里 `HypervisorPresent=True`，`wsl --version` 有内核版本号 | hypervisor 与 WSL2 都正常，BIOS 不用动 | 别再去翻 BIOS |
| `HyperVRequirements` 为空、`Win32_Processor.VirtualizationFirmwareEnabled=False` | 消费级主板没提供 ACPI 扩展；且 hypervisor 已接管 VMX 时该字段本来就报 False | **是假信号**，别拿它判定 |

此前本文档写的「`docker info` 报 500 的原因是 Windows 虚拟化没开」是误判：真实故障只是 Docker Desktop 没启动。
判据统一用 `docker info --format '{{.ServerVersion}}'`（`deploy/start.sh` 也是这么判的，并套了 15 秒超时）。

## 1. 起数据库（含自建 zhparser 镜像）

```bash
# 上游源码包只取一次（脚本自带 sha256 校验），之后镜像构建全程离线
sh deploy/pg/fetch-vendor.sh

# 手工跑 compose 必须带 --env-file .env：compose 默认只读 deploy/.env，根目录 .env 里的覆盖不生效
# （deploy/start.sh 自己 source 过 ./.env，所以走脚本时不用带）
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps        # 期望 rag-postgres 状态 healthy
```

第一次会编译 zhparser，耗时 5–15 分钟属正常。构建失败最常见的是**境外源不可达**，本机 2026-11-16 实测四条都撞过：

| 源 | 本机实测 | 处置 |
|---|---|---|
| `registry-1.docker.io:443` | 连接超时 | `.env` 里 `RAG_PG_BASE=docker.m.daocloud.io/pgvector/pgvector:pg17` |
| `deb.debian.org`、`apt.postgresql.org` | 连接超时 | `.env` 里 `RAG_DEBIAN_MIRROR`、`RAG_PGDG_MIRROR`（见下） |
| **容器内** `github.com:443` | `git clone` 直接连不上（exit 128） | 构建时不 clone：改成 `COPY vendor/*.tar.gz` 离线解压编译 |
| 宿主侧 `codeload.github.com` | **通**（`git ls-remote` 走的 smart-http 仍不通） | 这就是 `fetch-vendor.sh` 取包的那条路 |

三个变量就是 `deploy/pg/Dockerfile` 顶部的三个 ARG，默认值仍是官方源——**换源只是取同一份官方字节的另一条路径**，
构建完可以核对基础镜像 digest（本机拉到的 `pgvector/pgvector:pg17` 是
`sha256:b513c48566e4777cd3370451400000c78eda6a08131d68f4c31d4a76f27bd8fd`）。
不要改成「直接用别人预编译的 zhparser 镜像」绕过，那样中文全文检索这一路就永远验不到，可审计性也没了。

两个坑记在这儿，别再踩：

- **apt 源必须写 `http://`**。`pgvector/pgvector:pg17` 里没装 ca-certificates（`dpkg -l ca-certificates` 显示 `un`），
  用 https 源会在「装证书」这一步之前先失败，形成先有鸡还是先有蛋。apt 的完整性靠仓库 Release 文件的 GPG 签名，不靠 TLS。
- **`postgresql-server-dev-17` 只在 PGDG 有**。只换 Debian 源会报 `Unable to locate package`，
  必须同时给 `RAG_PGDG_MIRROR`（本机 `mirrors.aliyun.com/postgresql/repos/apt` 通，ustc 同路径 404）。

```bash
# 扩展与分词配置
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select extname, extversion from pg_extension order by 1;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select cfgname from pg_ts_config order by 1;"
```

期望：`pg_extension` 里有 **vector、pg_trgm、zhparser** 三行；`pg_ts_config` 里有 **chinese**。
没有 chinese 说明 zhparser 没装成，检索会退化成 pg_trgm——系统仍能跑，但 §6 的关键词期望要按降级重读。

```bash
# 当场判定「分词真的在工作」，而不是只装了扩展
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select to_tsvector('chinese','数据库备份保留多少天，原件每周日 04:00 全量同步');"
```

本机 2026-11-16 实测输出（照这个对，词位必须是**词**而不是逐字）：

```
'00':8 '04':7 '保留':3 '全':9 '原件':5 '同步':11 '备份':2 '天':4 '数据库':1 '每周日':6 '量':10
```

逐字切说明 `tsearch_data/dict.utf8.xdb` 没进最终镜像（`Dockerfile` 里那两条 tsearch_data 的 COPY 是必需的，
**扩展装上了≠词库带上了**）。顺带两条实测事实，后面 §6 判定要用：

- 编号类词会被连字符切开：`LEDGER-7731` → `'ledger' '7731'`，`TAIL-9F3C` → `'tail' '9f' '3c'`。
  正文与查询走同一套切法，所以 `mode=keyword` 仍命中——看到三个词位不是分词坏了。
- 数字与年份照样进索引：`35 天` → `'35' & '天'`，`2032年` → `'2032'`。
  词性映射只留了 `n,v,a,i,e,l,j,x`（上游推荐集），未收录的词落进 `x` 而不是被丢掉，
  所以库里根本没有的问题仍然是 0 命中，而不是「全部命中」。

## 2. 迁移与 schema

```bash
cd rag-api && mvn -o spring-boot:run
```

首次启动日志里要看清三件事：

1. `Migrating schema "public" to version "1 - core schema"` 与 `"2 - task and chat"`；
2. `RAISE NOTICE` 那句 **关键词检索使用 chinese(zhparser) 分词 + GIN tsvector**（若出现「退化为 pg_trgm」，回到 §1）；
3. 没有 Flyway 校验和报错。改动过 `V1__core_schema.sql` 的旧库要先 `flyway clean` 或换新库，
   本次是全新数据库，正常不会遇到。

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select column_name, data_type, udt_name from information_schema.columns
  where table_name in ('kb_segment','kb_document')
    and column_name in ('embedding','content_ts','edited_at','chunk_override') order by 1;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select indexname, indexdef from pg_indexes where tablename='kb_segment' order by 1;"
```

期望：`embedding` 是 `USER-DEFINED/vector`，`content_ts` 是 `tsvector`（生成列），`edited_at` 是 `timestamptz`，
`chunk_override` 是 `jsonb`；索引里有 `idx_segment_embedding_hnsw`（**HNSW，不是 IVFFlat**）、
`idx_segment_content_ts`（GIN）、`idx_segment_content_trgm`（GIN）。
`embedding` 的维度必须是 768，与 `rag.embedding.dim` 一致——不一致说明启动时用的
`RAG_EMBEDDING_DIM` 与建表时不同源，此时先别继续，改回同一个值再重建库。

## 3. 自检接口与 LM Studio 真实窗口

```bash
curl "http://localhost:8080/api/health"
curl "http://localhost:8080/api/health?models=true"
curl http://192.168.1.61:1234/v1/models      # 地址以本机配置为准
```

期望：`ready: true`，探测项 database / objectDir / chat / embedding 全 **UP**，
`modelIds` 显示配置里的两个模型名都在 `/v1/models` 列表内。

| 现象 | 含义与处置 |
|---|---|
| `modelIds` DOWN | 配置的模型名与 `/v1/models` 的 id 不是逐字符相同。LM Studio 对认不出的名字**不报错**，会用当前已加载模型应答，静默换模型比报错更难查——改 `LM_STUDIO_CHAT_MODEL` / `LM_STUDIO_EMBEDDING_MODEL`，不是改代码 |
| 模型服务单纯不可达只 DEGRADED | 正常：本机常见先起 rag-api 再起 Local Server |
| 健康检查卡住不动 | 历史上是 HTTP/2 协商问题（ADR-004），已固化 HTTP/1.1 + 5s 连接超时；若复现，先确认没绕过 `LmStudioHttpClient` |

**n_ctx 必须与 LM Studio 实际窗口对齐，而 LM Studio 不提供查询端点——撑爆它一次，它自己会说。**

`/v1/models` 里没有 context 字段，界面上的数字又容易看漏。可靠的读法是发一条注定超限的请求，
400 的响应体里带着 `n_ctx` 与 `n_prompt_tokens`（2026-11-16 本机实测，两个 chat 模型都是 16384）：

```bash
node -e 'const s="混合检索与倒数排名融合的说明。".repeat(4000);
require("fs").writeFileSync("/tmp/over.json",JSON.stringify({model:"glm-4-9b-chat-1m",
  messages:[{role:"user",content:s}],max_tokens:8}))'
curl -s http://192.168.1.61:1234/v1/chat/completions -H "Content-Type: application/json" --data @/tmp/over.json
# → "request (36005 tokens) exceeds the available context size (16384 tokens)...","n_ctx":16384
```

同一条数据顺便给出换算系数：60000 汉字 = 36005 token（glm）/ 40019 token（qwen），
即 **1 token ≈ 1.5 个汉字**，所以 `chars-per-token=1.0` 站在「少装」那一侧，是刻意保守，不是估算失误。
窗口值写进配置（两边只改一边就是 bug）：

```bash
RAG_LLM_N_CTX=16384 mvn -o spring-boot:run     # 或写进 .env；默认值已是本机实测的 16384
```

窗口写大了，请求会被模型服务拒绝——现在这条分支是独立的 413，报错里回显模型侧真实窗口，
并在 `/api/diagnostics` 留下 `contextOverflow` 计数与告警，不会伪装成「模型服务不可用」；
写小了不会报错，只会每轮白白少装几块资料，所以撞过一次 400 之后 diagnostics 会主动提示「把 RAG_LLM_N_CTX 提到 X」。

| 现象 | 含义与处置 |
|---|---|
| 答案少了一段但没有报错 | 先查 `effective.contextBudgetChars` 与 `unplacedHits`；n_ctx 配小了不会报错，只会少装 |
| 问答直接 413「上下文超出模型窗口」 | 配置窗口 ≥ 模型真实窗口：在 LM Studio 里调大 context，或降 `RAG_LLM_N_CTX`/`RAG_RETRIEVAL_TOP_K` |
| 第一次调用特别慢（实测冷加载 chat 31.3s、embedding +1.5s） | 正常，模型正在装进显存。chat 侧超时是 90s、自检小请求是 45s，都在实测之上；连续两次以上才慢说明是被换出去了 |

```bash
cd rag-api && mvn -o verify
LM_STUDIO_IT=true mvn -o verify -Dfailsafe.forkedProcessTimeoutInSeconds=240
```

期望：`failsafe-reports` 里六个 IT（47 例）都跑过而不是 skipped——
`SchemaMigrationIT`（真 pgvector 上的迁移与谓词能力，故意用**不含 zhparser** 的官方镜像覆盖退化分支）、
`RetrievalIT`（混合检索 SQL）、`IngestPipelineIT`（解析→分块→向量→发布全链路，embedding 用 mock）、
`ArchiveIT`（§10 归档：导出包结构、CARRIED 免重算、人工意图带回、四条拒绝路径）、
`EvaluationIT`（§12 跑分：名次由真实余弦决定、参数与逐条判定真的落进 jsonb、用例删掉后历史仍可读、

`LmStudioConnectivityIT`（真机三个请求：models / embed / chat 流式，只有这条需要模型）。

出现 `Tests are skipped.` 就是 Docker 还没通；`mvn -o verify` 只跑单测不会碰库，别把两件事混了。

**Docker Hub 不通的机器上，这两个 IT 依赖的镜像要先本地 retag 一次**（本机 2026-11-16 实测：
不 retag 时 Testcontainers 会卡在拉 `testcontainers/ryuk:0.14.0`，报
`dialing registry-1.docker.io:443 ... connectex`，然后一路「Retrying pull」到超时——
现象是 IT 莫名慢，不是失败信息）：

```bash
docker pull docker.m.daocloud.io/pgvector/pgvector:pg17      # 与 §1 同一个 digest
docker tag  docker.m.daocloud.io/pgvector/pgvector:pg17 pgvector/pgvector:pg17
docker pull docker.m.daocloud.io/testcontainers/ryuk:0.14.0
docker tag  docker.m.daocloud.io/testcontainers/ryuk:0.14.0 testcontainers/ryuk:0.14.0
```

镜像名保持官方的原因是测试代码里写的就是 `pgvector/pgvector:pg17`（`SchemaMigrationIT` 特意用
**没装 zhparser 的官方镜像**验退化分支，所以不能用上面自建的那个 `local/rag-postgres`）。
本地已有同名镜像时 Testcontainers 不再联网，retag 只是给同一份字节再起个名。
不想 retag 就改环境变量：`TESTCONTAINERS_RYUK_DISABLED=true`（少了孤儿容器兜底，IT 自己会关掉容器，可以接受）。

## 5. 入库实测（七个样本，逐个判定）

界面路径：文档页 → 右上角「上传文档」，一次一个文件。命令行等价：

```bash
for f in samples/*; do
  echo "--- $f"; curl -sS -F "file=@$f" http://localhost:8080/api/documents; echo
done
```

> **上面那条只在 Linux/macOS 的 shell 里可靠。** 本机 Git Bash + Windows 版 curl 会把 multipart 里的
> 文件名按控制台代码页（GBK）送出去，后端原样落库，于是列表里是 `04-????.md` 这种乱码名字——
> 实测只影响名字显示，正文、分块、终态都不受影响（04/05 照样 FAILED、06 照样 `duplicated: true`）。
> 要名字也干净就用界面拖拽，或 `node deploy/smoke.mjs`（它自己上传，UTF-8 没问题）；
> 已经传乱了就删掉重传：`curl -X DELETE http://localhost:8080/api/documents/{id}`。

| 样本 | 期望终态 | 这一条在验什么 |
|---|---|---|
| `01-运维手册.md` | READY | 有标题层级 → `heading_path` 非空；表格与列表能正常切；块数最多，是后面所有检索的基准 |
| `02-术语表.txt` | READY | 纯文本无标题 → `heading_path` 全 NULL，引用位置只显示页/字偏移；含一段「薪酬」用于 §9 的块级禁用 |
| `03-无标点长段落.md` | READY | 几乎没有句号 → 切分退回定长窗口，相邻块仍重叠 60 字；末尾校验码 `TAIL-9F3C` 必须搜得到（段落尾没被丢掉） |
| `04-空正文.md` | **FAILED** | 只有全角空格 → `errorCode=GARBLED_TEXT`，文案「解析结果为空文本」；不消耗重试预算 |
| `05-乱码扫描件.md` | **FAILED** | 全角 ASCII 占比约 49% > 15% 底线 → `GARBLED_TEXT`，文案「疑似 CID 字体乱码（异常字符占比 49%）」 |
| `06-重复副本-运维手册.md` | 不新增行 | 与 01 的 sha256 完全相同 → 返回 `duplicated: true`，一次 embedding 都不花 |
| `07-变更台账.csv` | READY | CSV 走同一解析路；独有事实 `LEDGER-7731`、「共 7 次变更，其中 2 次回滚」 |

上传完看进度（界面会自动轮询；命令行自己刷）：

```bash
curl -sS http://localhost:8080/api/documents | head -c 2000
curl -sS http://localhost:8080/api/documents/summary
```

库内对账（**这是 M2/M5d 最重要的一条 SQL**，后面导入验收要和它比）：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select d.name, d.status, d.version, d.error_code,
         count(s.id) as 块数,
         count(s.embedding) filter (where s.available) as 有向量且可用,
         count(*) filter (where s.emb_status='SKIPPED') as 父块,
         count(*) filter (where not s.available) as 已禁用,
         count(s.edited_at) as 已编辑
  from kb_document d left join kb_segment s on s.doc_id=d.id and s.doc_version=d.version
  where d.deleted_at is null group by 1,2,3,4 order by 1;"
```

期望：READY 的行「父块 + 子块 = 块数」「有向量且可用 = 子块数」；FAILED 两行没有块或块全不可用。
若「有向量且可用」小于子块数，索引发布应当已经拒绝切换并报「有 N 个可检索块没有向量」——
能出现这个状态说明发布守卫被绕过，是 bug，直接记下来。

## 6. 检索实测（三种模式 + 降级可见）

```bash
# 混合（默认）：期望第一条来自 01 第 2 节
curl -sS "http://localhost:8080/api/search?q=%E5%A4%87%E4%BB%BD%E4%BF%9D%E7%95%99%E5%A4%9A%E5%B0%91%E5%A4%A9&kbId=1&topK=5"

# 关键词路独占：编号类词向量路召不稳，这里必须命中 07
curl -sS "http://localhost:8080/api/search?q=LEDGER-7731&kbId=1&mode=keyword"

# 段落尾部校验码：命中 03 的最后一块
curl -sS "http://localhost:8080/api/search?q=TAIL-9F3C&kbId=1&mode=hybrid"

# 库里根本没有的问题：期望 hitCount=0 或全部低于阈值
curl -sS "http://localhost:8080/api/search?q=2032%E5%B9%B4%E7%81%AB%E6%98%9F%E6%A4%AD%E6%B0%91%E9%A2%84%E7%AE%97&kbId=1"
```

每条返回都要看这六个字段，它们决定了「召回差」是模型问题还是配置问题：

| 字段 | 期望 |
|---|---|
| `requestedMode` / `effectiveMode` | 一致；不一致说明发生了降级，`degraded=true` 且 `keywordEngineNote` 会解释原因 |
| `keywordEngine` | `CHINESE_TSVECTOR`（装了 zhparser）或 `TRIGRAM`（退化）；`NONE` 表示关键词路整条不可用 |
| `rrf` | 混合模式下量级 **0.01x**（如 0.0164）。若看到 0.4x 量级，说明阈值或融合算错了 |
| `min-rrf-score` 效果 | 混合模式阈值 0.012，**不能**照抄纯向量的 0.45，否则 hitCount 恒为 0 |
| `similarity` | 纯向量模式才有值；低于 0.45 的会被滤掉，宁可不答 |
| `tookMs` | 本机量级：几十到几百毫秒。突然上到秒级先看 LM Studio 是不是在加载模型 |

## 7. 问答实测（流式 / 引用 / 拒答 / 中断）

```bash
curl -N -H "Content-Type: application/json" \
  -d '{"question":"数据库备份保留多少天？原件多久同步一次？","kbIds":[1]}' \
  http://localhost:8080/api/chat/ask
```

期望事件序列 `meta → delta* → done`；答案里出现 **35 天** 与 **每周日全量同步**；
`meta.sources` 至少一条指向 `01-运维手册.md` 且 `location` 说得出「第 2 节 / 页 / 字偏移」。
界面侧：点答案里的 `[1]` 应跳到文档详情并定位到那一块。

**Git Bash 里 `-d '{…中文…}'` 会踩编码坑**：Windows 控制台是 GBK，命令行里的中文按 GBK 送进请求体，
后端报「Invalid UTF-8 middle byte」——看着像后端坏了，其实是请求体不是 UTF-8。
凡是 body 带中文，先把 JSON 写成 UTF-8 文件再用 `--data-binary @文件`（上面 413 那条就这么写），
或者干脆在界面里问。

- **拒答**：问「2032 年火星殖民预算」→ `status=REFUSED`，文案是固定的「知识库里没有找到可靠依据」，
  引用区为空。模型自己编一句「我不确定」也算不合格。
- **中断**：生成过程中点停止 → 该条消息 `status=INTERRUPTED`，重新进入页面仍是 INTERRUPTED（落库的，不是前端状态）。
- **预算**：把 `RAG_RETRIEVAL_TOP_K` 调到 20、`n-ctx` 调小到 2048 再问一次，
  `meta.retrievalMeta` 里 `contextTruncated=true`、`unplacedHits>0` 必须可见——
  装不下多少块是运行事实，界面得说出来，不能静默丢。
- **多轮**：先问「备份保留多少天」，再问「那原件呢」，第二轮的 `queryFinal` 应被改写成带主题的问题
  （不是原样把「那原件呢」丢给检索）。
- **缺范围**：不带 `kbIds` 也不带已有会话地问一次 → **HTTP 400 + JSON 信封**，不是事件流里的 `error`，
  会话列表里也不该多出一条答不下去的问句（范围在任何写入之前决定）。
  这一条曾经兜底成「查默认知识库」，答案照样通顺，只能从 `meta.sources` 看出资料来自没选过的库。
- **超限（413）**：见下面「主动撞一次 413」，这是 n_ctx 唯一可靠的读法。

**主动撞一次 413，把超限分支的证据拿到手**（本机 2026-11-16 实测走的就是这条）：

```bash
# 把配置窗口临时抬到模型真实窗口之上，装配就不会自我约束，请求一定越过 n_ctx
# 行内变量优先于 .env（start.sh 会把顶掉的项说出来），所以不用改文件、也不怕忘了改回来
deploy/stop.sh && RAG_LLM_N_CTX=60000 deploy/start.sh
node -e 'require("fs").writeFileSync("over.json",JSON.stringify({question:"混合检索与倒数排名融合的说明。".repeat(2750),kbIds:[1]}))'
curl -N -H "Content-Type: application/json" --data-binary @over.json http://localhost:8080/api/chat/ask
```

期望：事件序列 `meta → error`（**没有 delta**，一个字都没生成），`code: 413`，
`message` 里同时有「配置窗口 60000 token」「模型侧 回传 16384 token」「本次提示词 35002 token」；
`/api/diagnostics` 里 `counters.contextOverflow` +1，`lastContextOverflow` 记录 configured/reported，
并留一条告警「配置 n-ctx=60000 比模型真实窗口 16384 还大……在 LM Studio 里调大 context」。
这一轮答案 `status=FAILED` 而不是 `INTERRUPTED`：装配失败和模型半路死掉是两类原因，评测要分得开。
测完顺手 `rm over.json` 再回看一眼 `/api/health?models=true` 的 `effective.nCtx` 是不是 16384——
大窗口不会弄坏数据，但每轮长答案都会白撞一次 413，忘了恢复的话下一段实测全在解释一个不存在的问题。

## 9. 分块覆盖与单块编辑（M5c / M5b）

1. 文档详情 → 分块预览：把子块从 400 改成 **260**、父块 **900**，先「预览」不写库，块数应变多；
   再「存为本文档覆盖」→「重算」。期望进度文案里出现 `语义分块 子块 260 / 父块 900 字`，
   且 `kb_document.version` +1，`chunk_override` 里**只有差异的两个键**（等于全局的键不落库）。
2. 恢复全局默认后必须再重算一次才生效——覆盖只影响下次入库，这是设计。
3. 单块编辑：在 01 的表格里挑一块，把内容改乱再订正回来，勾「同时重算向量」。

4. 块级禁用：把 02 里「内部薪酬」那一块的 `available` 关掉，

5. 入库进行中拒绝编辑（409）：上传 01 之后立刻去编辑某块，应被拒绝并说明当前状态。

## 10. 归档包导出 / 导入（M5d 验收，最关键的一段）

这一段现在有 `ArchiveIT` 六例连库测试兜着（`mvn -o verify`，不需要模型），下面这串 curl 是它的等价人工版：
自动化测的是「包结构与落库事实」，你手跑要补的是**界面侧**（导入结果框里 mode 标签、八个计数与逐篇 notes）
和真模型下 `rebuild=true` 的实际耗时。两边结论对不上时，先信数据库里的那条 SQL。

```bash
# 导出：带向量 + 带原件
curl -sS -OJ "http://localhost:8080/api/knowledge-bases/1/export?vectors=true&files=true"
unzip -l kb-1-*.zip
```

期望包内条目：`manifest.json`、`content/0.txt … N.txt`、`segments/0.jsonl … N.jsonl`、
`files/{slot}/{原始文件名}`。`manifest.json` 里 `format: 1`、`vectors: true`、`files: true`、
`source.embeddingDim` 等于 768、`source.embeddingModel` 与配置同名，`documents[]` 每项带
`slot / name / sha256 / version / segmentCount / chunkOverride`。
slot 从 0 连续编号，**不是**数据库 id。

```bash
# 记下 §5 那条对账 SQL 的结果，然后清空当前库的文档（软删，与界面删除等价）
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "update kb_document set deleted_at=now(), available=false where kb_id=1;"
```

```bash
# 导入同一个包：期望免重算
curl -sS -F "file=@kb-1-20261115-XXXXXX.zip" \
  "http://localhost:8080/api/knowledge-bases/1/import?rebuild=false"
```

期望返回（样本里 READY 的是 01/02/03/07 四篇：06 与 01 同哈希不会成第二行，04/05 是 FAILED 不入包）：

```json
{"code":200,"message":"向量直接可用：导入 4 篇 / … 块，未花一次 embedding",
 "data":{"kbId":1,"mode":"CARRIED","imported":4,"queued":0,"segmentsCarried":…,
         "originalsRestored":4,"skippedSame":0,"skippedEmpty":0,"failed":0,"notes":[…]}}
```

- `mode=CARRIED`、`queued=0`，rag-api 日志里**不出现**任何 EMBEDDING 阶段——这是「没重算」的唯一硬证据。
- `skippedEmpty` 这里是 0：正文为空的文件根本到不了 READY，也就不会进包，这个计数只在手工改过的包里出现。
- 软删只标 `deleted_at`，**不删块**（检索靠 `d.deleted_at IS NULL` 过滤）。导入后
  `select count(*) from kb_segment` 的总数会接近翻倍，那是正常残留，别当成导入重复——
  对账永远用按文档分组的那条 SQL。
- 再跑一遍 §5 的对账 SQL：`块数 / 有向量且可用 / 父块` 三个数必须与清空前逐行一致；
  `已禁用` 仍等于你在 §9 关掉的那几块（`available=false` 是人工意图，导入必须原样带回来）；
  `已编辑` 仍等于 §9 编辑过的块数（`edited_at` 没丢）。
- 检索复验：`LEDGER-7731`、`TAIL-9F3C`、`薪酬`（仍应因禁用而不命中）三条结果与清空前一致。
- 原件复验：对任意一篇点「重解析」，能读到原文件说明 `files/` 真落盘了（`file_path` 非空）。

四条拒绝路径也要跑，它们比成功路径更容易在真实数据上出问题：

```bash
# 1) 不是 zip → 400，且发生在写第一行数据之前
curl -sS -F "file=@README.md" "http://localhost:8080/api/knowledge-bases/1/import"

# 2) 同库重复导入 → 全部 skippedSame，一行都不写
curl -sS -F "file=@kb-1-XXXX.zip" "http://localhost:8080/api/knowledge-bases/1/import?rebuild=false"

# 3) 强制重算 → mode=REBUILT，文档排队到 PENDING，最终逐篇 READY（这次会真花 embedding）
#    导进本节末尾建好的 2 号库；不想建库就导回 1 号库，但要先再执行一次上面的软删，
#    否则同哈希全部命中 skippedSame，一行都不会写，看不出重算效果
curl -sS -F "file=@kb-1-XXXX.zip" "http://localhost:8080/api/knowledge-bases/2/import?rebuild=true"

# 4) 维度不符 → 409，文案给出「本库 N 维 / 当前配置 M 维」两个数（校验在 kb 行与配置之间，不在包里）
RAG_EMBEDDING_DIM=512 mvn -o spring-boot:run   # 另开一个库或改配置后重启，再导入同一个包
```

界面侧同步验一遍：文档页 → 「归档」→ 目标库 / 带向量 / 带原件 → 导出（浏览器存下的文件名应是
`kb-1-yyyyMMdd-HHmmss.zip` 且能解压）；「选择 .zip」导入后弹「导入结果」框，
`mode` 标签、八个计数与逐篇 `notes` 都要显示出来——notes 是唯一能说清「为什么少了一篇」的地方。

**可选：跨库导入。** 目前只有 `ensureDefault` 会建「默认知识库」，没有建库接口，
手工插一行即可（模型名与维度必须与配置一致，否则命中的是拒绝路径 4）：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "insert into knowledge_base (name, embedding_model, embedding_dim)
  values ('迁移验证库', 'text-embedding-bge-base-zh-v1.5', 768) returning id;"
```

对端口的提醒：**LM Studio 的 1234 只做局域网、不做鉴权，这是既定决策**（信任边界=不出局域网）。
在跑 LM Studio 的那台机器上 `0.0.0.0:1234 LISTENING` 是**预期状态**（勾了 Serve on Local Network 就该这样），
要确认的是另外两件事：路由器上没有把 1234 映射出去，防火墙入站只放专用网络。
```bash

```

还有一个不在本项目控制内的边界变化：**服务端 `logSensitiveData` 实测是开启的**，
意味着每次问答的原文与提示词都以明文留在 192.168.1.61 的 LM Studio 历史里，而不只在咱们的库里。

同理，那台机器是 DHCP 拿的 `192.168.1.61`，路由器上没做静态租约时地址会漂——
换过 Wi-Fi 或重连网络后 `LM_STUDIO_BASE_URL` 打不通，先看地址漂没漂，再看代码。

## 11. 运行诊断与日志（M5f 验收）

```bash
curl -sS http://localhost:8080/api/diagnostics
```

这个端点回答的是 health 答不了的那一类问题：依赖全通，但结果已经不值得信。四段怎么读：

| 看什么 | 期望 | 不对说明什么 |
|---|---|---|
| `run.counters.vectorDegraded` | 0 | 大于 0 就说明本轮至少有一次检索的向量路没走成，**§6 那批 rrf 分数整批作废**（分数是关键词路给的，量纲也换了）。`lastVectorFailure.reason` 是最后一次的原因 |
| `run.counters.embeddingFailures` | 0 | 模型服务被碰过：查询向量化、单块补算、入库批量任一处失败都算一次。先去看 LM Studio 里 embedding 模型还在不在 |
| `run.counters.contextTruncated` | 与 §7 那条「预算截断可见」的用例次数一致 | 对不上就是计数器与 SSE 事件有一条线接错了（`deploy/smoke.sh` 第 11 步专门对这条账） |
| `run.counters.refused` | 与 §7 的拒答用例次数一致 | 比预期多：多半是 `min-score` / `min-rrf-score` 调严了，或者分块把答案切散了 |
| `run.counters.contextOverflow` | 0 | 大于 0 说明有一次问答在生成开始前就被模型拒了（413）。`lastContextOverflow` 同时带着配置的窗口和模型回传的窗口，两个数不等就该对齐配置——照 §3 那条 curl 复核 |
| `effective.contextBudgetChars` | `n_ctx − 700 − 900 −（历史 + 问题）` | 与手算差一截说明 `rag.retrieval.budget.n-ctx` 和 LM Studio 里实际加载的 context 不是同一个值 |
| `warnings` | `[]` | 后端自己发现配置矛盾：`min-rrf-score` 高过 RRF 第一名的分数（检索会长期 0 命中），或 `child-chars` 超过 embedding 的 512 token 窗口（正文尾部被静默截断） |

## 12. 评测集与跑分（M5e 验收）

三条命令就能看完整个闭环（建用例 → 跑一轮 → 回看参数与分数）：

```bash
curl -sS -X POST http://localhost:8080/api/evaluation/cases -H 'content-type: application/json' \
  -d '{"kbId":1,"question":"数据库备份保留多少天","expectMarker":"35","expectDoc":"运维手册"}'
curl -sS -X POST http://localhost:8080/api/evaluation/cases -H 'content-type: application/json' \
  -d '{"kbId":1,"question":"食堂今天几点关门","shouldAnswer":false}'
curl -sS -X POST 'http://localhost:8080/api/evaluation/run?kbId=1&mode=hybrid&note=第一版'
```

判据只有 `expectMarker` 一个：命中块正文里出现这段文字（忽略大小写、折叠空白）就算找到。
锚在文字而不是 `segment_id` 上——改分块尺寸或重算向量之后块 id 一定变，而评测要问的恰恰是「换了参数还找不找得到」。

跑分只走检索、不生成答案，一轮几秒钟。但**别以为 embedding 服务没起就能安全跑分**：查询向量算不出来时
检索不报错，而是当场退成关键词路，跑分照样出全套指标——只是那一轮的分数是一路的分数，跟正常轮次不可比。
三处会说实话：
逐条 `reason` 末尾多一句「降级跑的：请求 HYBRID，实际只走 KEYWORD（原因）」；
日志一行 WARN（`grep 降级跑出来的 deploy/logs/rag-api.log`）；
`GET /diagnostics` 的 `vectorDegraded` 计数。参数快照帮不上这个忙——快照是在跑第一条用例**之前**写的，
记的只能是「请求了什么」。`deploy/smoke.mjs` 第 11 步专门对 `vectorDegraded` 这本账，它排在第 9 步之后，
所以真降级会先把整条回归拦住（本机全绿时读数是 `降级 0`）。

### 每个指标在问什么

| 看什么 | 它在问 | 读数注意 |
|---|---|---|
| `hitAt1` / `hitAt3` / `hitAtK` | 期望块排进前 1 / 前 3 / 前 K（K=本次 topK）的正例比例 | `hitAtK < 1` 而 `emptyRecallRate = 0` → 是排序问题不是闸门问题；两个一起掉才先怀疑阈值 |
| `mrr` | 相关块名次的倒数平均 | 只用来整体看排序质量，别拿它做单参数决策（第 1 名和第 6 名的差被压成 0.83） |
| `emptyRecallRate` | 正例一条都没召回的比例 | 这个数动的是闸门：`min-score`（余弦量纲 0.45）/ `min-rrf-score`（融合分量纲 0.012）调严了先红这里 |
| `rankedBeyondK` | 召回了、但期望块不在窗口内 | 与 `hitAtK` 互补；加大 `topK` 能救，代价是上下文预算 |
| `refusalAccuracy` | 负例（库里真没有）里正确拒答的比例 | 分母是负例条数。**没有负例时报「不适用」（null），不是 0** |
| `truncatedCaseRate` | 正例里「召回了但有块没装进上下文」的比例 | 量的是**装配**不是检索：它不为 0 时 hit@K 照样可以是 1.0（块排到了但模型读不到）。修法在 `n_ctx` / `parent-max-chars`，别去动阈值 |
| `invalid` | 未标注的正例条数 | 整条不进任何分母，只在这里报数；`cases` 里含它 |
| `avgTookMs` | 单条检索平均耗时 | 只有判过分的条目参与，别和 `cases` 对不上 |

### 一次真机读数（本机 2026-11-16，用例照抄 §6 那张事实表）

| 轮次 | hit@1 | hit@3 | hit@K | MRR | 空召回率 | 排在K外 | 拒答正确率 | 截断率 |
|---|---|---|---|---|---|---|---|---|
| `mode=hybrid`（topK=6） | 0.8 | 1.0 | 1.0 | 0.9 | 0 | 0 | **0** | **1.0** |
| `mode=keyword`（topK=6） | 0.8 | 0.8 | 0.8 | 0.8 | 0.2 | 0 | 1.0 | 0 |
| `mode=hybrid&topK=50` | 0.8 | 1.0 | 1.0 | 0.9 | 0 | 0 | 0 | 1.0 |

`GET /runs` 里相邻两轮的 `delta`：`{"hitAt1":0,"hitAt3":-0.2,"hitAtK":-0.2,"mrr":-0.1,"refusalAccuracy":1,"emptyRecallRate":0.2,"truncatedCaseRate":-1.0}`
（hybrid → keyword 那一跳：前三与整窗都掉一档，但拒答反而全对、截断归零——keyword 召回得少，预算反而够用了。）

这三行读数背后是四课，比分数本身值钱，别当噪音：

- **hybrid 的 `hit@1=0.8` 掉在并列名次上，而且是刻意留的。** `LEDGER-7731` 那条用例里，期望块
  （`07-变更台账.csv` 第 0 块，segment_id 389）是关键词路第 1 名，另一块（`01-运维手册.md` 第 15 块，id 378）
  是向量路第 1 名，RRF 只按名次给分，两者拿到**一模一样**的 `1/(60+1)=0.016393`——
  `GET /api/search?q=LEDGER-7731` 前两行的 `vectorRank/keywordRank` 与 `rrf` 就是这四句话的直接证据。
  并列总要有先后，现在的破法是「文档名 + 块序」，`01-` 排在 `07-` 前面，期望块于是落第 2 名（`hit@3` 与 `hit@K` 不受影响）。
  这不是缺陷而是取舍：**宁可要一个每次都能复现的次序，也不要一个每次不一样、还会被当成信号读的顺序。**
  改之前用插入号 `f.id` 破并列，而重新入库、`--archive` 重导入、重算向量都会换块 id：库里 19:32–20:24 的
  21 轮 hybrid 全报 `hit@1=1.0`（那一刻台账的块号更小），20:24:58 那批样本重传之后 `kb_document` 40~43
  是全新行、块 id 从 363 起重新排过，20:51 起的每一轮就全报 `0.8`——判据、参数、正文一个字没改，分数自己动了，
  ADR-021 立的「改一个参数、分数变化归因到那个参数」当场作废。
  改完之后（25~30 六轮）七项指标逐轮完全相同，`ORDER BY` 也不给插入号留决定名次的口子（有单测钉住，见 `docs/重构方案.md` §20 ADR-022）。
  真要把它读成 1.0，办法是改判据或改样本命名，而不是改破法——后者只是把不可复现换成一个好看的不可复现。
- **hybrid 的拒答正确率 0 不是 bug。** 该轮生效闸门是 `min-rrf-score=0.012`（RRF 融合分量纲：两路都拿第 1 名约
  0.032，只有一路命中的第 1 名约 0.0164，`1/(60+rank) >= 0.012` 解出来单路前 23 名都能过），
  任何一条向量近邻都能过。库里没有「食堂」这个话题，检索器照样端回 6 块运维手册，
  装配不为空 → 不拒答 → 模型被拿无关资料提问。**想让「库里真没有」真的落到拒答，靠的是向量路的余弦闸门
  `min-score=0.45`（`mode=vector`），不是 RRF 阈值。** 这一条就是留着负例的目的：它测的是幻觉抑制的边界，不是检索准不准。
- **keyword 那一轮 `空召回率=0.2` 掉的是「工单 OPS-2026-118 记了什么误配」**：纯关键词路对这种
  「问句里没有正文里的字面 token」的问题无能为力（同一条在 hybrid 里 rank=1）。
  两路各自的能力边界 §6 讲过一次，这次是以分数的形式读出来的。
- **`截断率=1.0` 而 `hit@K=1.0`，这两件事同时成立才是对的。** hybrid 每轮召回 6 块，装配按名次从前往后装，
  父块正文长，把快照里的 `contextBudgetChars=14784` 吃到只剩不到 120 字符后就停下不装了——于是
  「召回 6 块里有 1 块没装进上下文」。这一条**不该**去动 hit@K：hit@K 量的是检索排第几，
  把它和预算混在一起，调 `n_ctx` 就会看起来在改检索质量。想验证得更狠就 `topK=50` 跑一轮：
  每例召回 19~21 块、只装得下 10~11 块，hit@K 仍是 1.0，截断率仍是 1.0，而逐条原因会写出「召回 20 块里有 10 块没装进上下文」。
  反过来，如果相关块恰好排在装不下的那一截里，原因会写成「排在第 N 名，本次上下文只装下 M 块，模型没读到它」——
  检索层记命中、线上却答不出来，这种不一致只有这一项读数能提前暴露。
  日志里同步有一行 WARN（`grep 却没装进上下文 deploy/logs/rag-api.log`），因为它意味着这轮分数与预算充足那轮不可比。

### 参数快照与归因

`eval_run.settings` 记 15 项当轮真正生效的参数（模式、生效阈值 `threshold` 及其两个来源 `minScore`/`minRrfScore`、
`topK`、`candidateK`、`rrfK`、`parentContext`、`keywordEngine`、`embeddingModel`、`embeddingDim`、`nCtx`、
折算出的 `contextBudgetChars`，以及 `modeOverride`/`topKOverride`）。要比较的两次跑分必须只有一个变量不同，
所以覆盖项只开 `mode` 与 `topK` 两个——阈值这类改了要重启服务，这样快照必然等于真实生效值。

`truncatedCaseRate` 是后加的指标，之前的历史轮次没有存这个数：列表里它们读成 `null`（信封写「不适用」），
`delta` 也会跳过这一项而不是拿 0 去比。**「没存过」和「一条都没截」是两件事**，这里按前者处理。

`GET /runs/{id}` 的逐条结果里，`reason` 是判的那一刻写下的中文一句话。三种失败长得像但修法完全不同：

| 原因文案 | 该动哪里 |
|---|---|
| `空召回：阈值过滤后一条命中都没有` | 库里真没有，或 `min-score` / `min-rrf-score` 太严 |
| `召回 N 条但装配一条都没装下（正文为空或预算不足）` | 分块尺寸或 `n_ctx` 预算，跟检索无关；线上这条会真的拒答 |
| `相关块没进前 N 名（召回 M 条，其余 K 条没装进上下文，本来就够不到模型）` | 名次够不到；如果 K>0，先加大 `topK` 再看预算装不装得下 |
| `找到了，但召回 N 块里有 K 块没装进上下文` | 期望块进了模型，别的没进——分数没错，但线上少资料，动 `n_ctx` / `parent-max-chars` |
| `排在第 N 名，本次上下文只装下 M 块，模型没读到它` | hit@K 记了命中、线上却答不出：这是预算问题，不是排序问题 |
| `库里没有的东西被召回了：《x》 第 1 名` | 负例没被闸门挡住 → 拒答正确率掉的就是这一项 |

删掉一条用例（`DELETE /cases/{id}`）不会抹掉历史：`eval_result` 存了那一刻的问句、判据、名次与原因，
所以「当初为什么是 1.0」在用例没了之后还读得回来（这是 `case_id` 故意不建外键的原因）。
`GET /runs` 的 `delta` 只在列表里算（相邻两轮），单条 `runs/{id}` 恒为空——这是有意的。

### 从反馈里长用例

```bash
curl -sS -X POST 'http://localhost:8080/api/evaluation/cases/from-feedback?kbId=1'
```

只捞 `rating=-1` 且已填 `annotatedAnswer` 的回答（§8 那一步的产物），取的是 `query_final`
（改写后那句才是检索真正面对的输入），按会话的 `kb_ids` 过滤，一次最多 50 条，生成 `enabled=false` 的待标注用例。
一律不启用是刻意的：判据得人给，机器从订正答案里截一段当 `expect_marker` 等于让评测自己考自己。
未启用的正例强行 `PATCH enabled=true` 会吃 400，`POST /run` 在没有启用用例时同样 400 且不落任何 `eval_run` 行。

### 界面

评测**没有前端页面**，这是有意的取舍：跑分要成批比较参数、逐条读错例原因，命令行与回归脚本比界面顺手。
所以这一节要么用 curl，要么直接跑 `deploy/smoke.sh`（第 9 步）。等标注工作量真的大到需要批量操作时再补页面。

同一个位置还揪出第二个盲区：装配「召回 6 块只装下 5 块」这件事当时在跑分里完全没有读数，
只有逐条原因里一句顺带写出的话，`hit@K=1.0` 看起来一切正常。现在它有自己的指标 `truncatedCaseRate`，
第 9 步多跑一轮 `topK=50`（实测每例召回 19~21 块、装下 10~11 块）专门逼出这个数，并断言「汇总说截断、逐条就得有原因」。
第三个是这一轮补的，性质不一样：前两个是「少了一个读数」，这个是「已有的读数不可复现」——
文档写的 `hit@1=1.0` 在真库上稳定读出 0.8，而它之前又确确实实读出过 1.0。

代价是本机读数从此固定为 0.8：**这一节里所有分数都应当按「你重跑一遍能不能读出同一组数」来读，
而不是按好不好看来读。** 同一套参数连跑两轮七项指标逐项相同，才算这套跑分有比较资格。

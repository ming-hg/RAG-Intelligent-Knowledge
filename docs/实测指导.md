# 实测操作手册（照着做，每一步都告诉你「应该看到什么」）

这份文档只干一件事：让你**从零跑到「这套系统真的能用」这个结论**，而且每个判断都能在当场做出来。
样本文件在 `samples/`，里面的事实是故意写死的——答不出来就是流水线有问题，不是「模型不够聪明」。

## 怎么读这份文档

每一节都是同一张卡片，四个小节固定顺序：

| 小节 | 内容 |
|---|---|
| **先要有什么 / 做什么** | 前置条件，以及这一步用一句话说清目的 |
| **敲什么 / 点哪里** | 可以整块复制的命令，或界面路径 |
| **应该看到什么** | 本机 2026-11-17 实测的真实输出，逐字段告诉你看哪几个 |
| **看不到怎么办** | 现象 → 原因 → 去哪儿改。对不上就照这张表处理，**先别改代码** |

带 ▸ 的段落是「为什么」，第一次跑可以整段跳过；要与人争口径时再回来看。

## 三条路线，先选一条

| 路线 | 适合谁 | 用时 | 覆盖什么 | 走哪些节 |
|---|---|---|---|---|
| **A 一条命令**（推荐先跑） | 刚装好，只想确认通不通 | 10–20 分钟；首轮要编译镜像，多留 20 分钟 | 54 项自动断言（带 `--archive` 是 63 项） | §0→§3 起环境，然后 `deploy/smoke.sh` |
| **B 界面手点** | A 绿了，要验「人眼看得见的东西」 | 40–60 分钟 | 上传、检索、问答、分块、归档结果框、诊断 | §5~§11 里标着「界面」的小节 |
| **C 全量留证据** | 交付前要有据可查 | 60–90 分钟 | A + B + 连库测试 + SQL 对账 + 跑分手算 | 全文，最后按 §13 回填记录表 |

> **脚本只认接口，不认像素。** A 跑绿不等于界面是对的；B 里那几处必须用眼睛看，替代不了。

## 开始之前：需要准备的东西

| 要什么 | 怎么确认（Git Bash 里敲） | 缺了会怎样 |
|---|---|---|
| Git Bash（装了 Git 就有） | `bash --version` | 文档里所有命令按 Git Bash 写，PowerShell 会假报错 |
| Docker Desktop（WSL2 后端） | `docker info --format '{{.ServerVersion}}'` 能打印版本号 | 数据库起不来，停在 §1 |
| JDK 17 | `java -version` 里有 `17` | `rag-api` 起不来，停在 §2 |
| Maven | `mvn -v` | 打包和测试都跑不了 |
| Node 20.19+ 或 22.12+ | `node -v` | 前端起不来（Vite 8 硬要求，`start.sh` 会当场拦住你） |
| 模型机：LM Studio 已开 Local Server，加载了 chat 与 embedding 两个模型 | `curl http://<模型机IP>:1234/v1/models` | 检索会退化成纯关键词、问答会超时。**不装模型也能跑完 §0~§2**，但 §5 之后没意义 |
| 仓库根目录有 `.env` | `cp .env.example .env` | 全部用 `application.yml` 默认值，模型地址大概率不是你机器的 |

`psql` 不用装，`docker exec` 就够（文档里所有 SQL 都是这么跑的）。

## 只有 3 个值需要你改成自己机器的

打开 `.env`，改这三行，其余默认值就是本机实测环境：

| 键 | 去哪儿看真实值 | 本机实测值 |
|---|---|---|
| `LM_STUDIO_BASE_URL` | LM Studio → Local Server 的地址。跨机器要勾 **Serve on Local Network** 并放行入站 TCP 1234 | `http://192.168.1.61:1234/v1` |
| `LM_STUDIO_CHAT_MODEL` | `curl <BASE_URL>/models` 返回里的 `id`，**逐字符复制** | `glm-4-9b-chat-1m` |
| `LM_STUDIO_EMBEDDING_MODEL` | 同上 | `text-embedding-bge-base-zh-v1.5` |

两个别随手动的值：`RAG_EMBEDDING_DIM=768` 是数据库 schema 的一部分，改了必须重建库；
`RAG_LLM_N_CTX=16384` 必须等于模型里真实加载的窗口，**怎么量出来见 §3**。

## 新手最容易踩的四个坑

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 用 PowerShell 跑本文命令 | `curl : 无法处理参数` 之类怪错 | 用 Git Bash（`curl` 在 PowerShell 里是 `Invoke-WebRequest` 的别名） |
| 用 `127.0.0.1:5173` 打前端 | 连接被拒 | 前端固定用 `http://localhost:5173/`（Vite 只绑 IPv6 回环）；后端 `localhost` 和 `127.0.0.1` 都行 |
| 命令行 `-d` 里直接写中文 | 后端报 `Invalid UTF-8 middle byte`，看着像服务坏了 | Windows 控制台是 GBK。把 JSON 存成 UTF-8 文件再 `--data-binary @文件`，或直接在界面里问 |
| 上传完立刻判定 | 文档还在 `PENDING`，就断言「入库失败」 | 等 `status=READY`（界面自动轮询）。首轮全量 embedding 要几分钟，模型机不在就永远不 READY |

## 0. 一分钟自检：环境到底通不通

**先要有什么**：Git Bash、Docker Desktop、JDK 17、Maven、Node。**做什么**：确认 Docker 引擎真的在应答，别把「Docker Desktop 没启动」当成「虚拟化没开」。

### 敲什么

```bash
docker info --format '{{.ServerVersion}}'   # 期望打印 2x.x.x，这一条通就算引擎通
wsl --status                                # 期望：默认版本 2
```

### 应该看到什么

一个版本号，例如 `27.1.1`。**只有版本号这一条算通**，别的都别信。

### 看不到怎么办

判不通要看**报的是哪一种**，本机 2026-11-16 实测纠正了此前写错的一条结论：

| 现象 | 真实原因 | 去哪儿改 |
|---|---|---|
| `docker version` 只回 Client；报 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine ... cannot find the file` | **Docker Desktop 进程没在运行**（服务 `com.docker.service` = Stopped）。这**不等于**虚拟化没开 | 启动 `C:\Program Files\Docker\Docker\Docker Desktop.exe`，约 20 秒后重试 |
| `Get-CimInstance Win32_ComputerSystem` 里 `HypervisorPresent=True`，`wsl --version` 有内核版本号 | hypervisor 与 WSL2 都正常 | BIOS 不用动，别去翻 |
| `HyperVRequirements` 为空、`Win32_Processor.VirtualizationFirmwareEnabled=False` | 消费级主板没提供 ACPI 扩展；且 hypervisor 已接管 VMX 时该字段本来就报 False | **假信号**，不要拿它判定 |

▸ 此前本文档写过「`docker info` 报 500 的原因是 Windows 虚拟化没开」，那是误判，真实故障只是 Docker Desktop 没启动。
判据统一用 `docker info --format '{{.ServerVersion}}'`——`deploy/start.sh` 也是这么判的，并且套了 15 秒超时，
所以引擎没起来时它会明确停下，不会挂在那里让人以为卡死。

## 1. 起数据库（第一次要编译中文分词镜像，5–15 分钟）

**先要有什么**：§0 通过。**做什么**：拉起带 pgvector + zhparser 的 PostgreSQL 容器，并确认**中文分词真的在工作**，而不只是「扩展装上了」。

### 敲什么

```bash
# 1) 分词源码包（scws 1.2.3 + zhparser 2.3）只取一次，之后镜像构建全程离线
sh deploy/pg/fetch-vendor.sh

# 2) 起容器。手工跑 compose 必须带 --env-file .env：
#    compose 默认只读 deploy/.env，根目录 .env 里的换源覆盖不会生效
#    （走 deploy/start.sh 时不用带，它自己 source 过 ./.env）
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build

# 3) 看状态
docker compose -f deploy/docker-compose.yml ps     # 期望 rag-postgres 状态 healthy
```

### 应该看到什么

`fetch-vendor.sh` 打印两个包名与校验通过的行；`ps` 那一行状态是 `Up (healthy)`。
构建日志里最后有 `DONE` 而不是 `ERROR`。然后跑这三条，全对才算这一步过：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select extname, extversion from pg_extension order by 1;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select cfgname from pg_ts_config order by 1;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "select to_tsvector('chinese','数据库备份保留多少天，原件每周日 04:00 全量同步');"
```

- `pg_extension` 里有 **vector、pg_trgm、zhparser** 三行；
- `pg_ts_config` 里有 **chinese**；
- 最后一条必须切出**词**，本机 2026-11-16 实测输出（照这个对）：

```
'00':8 '04':7 '保留':3 '全':9 '原件':5 '同步':11 '备份':2 '天':4 '数据库':1 '每周日':6 '量':10
```

### 看不到怎么办

| 现象 | 原因 | 去哪儿改 |
|---|---|---|
| `chinese` 不在 `pg_ts_config` 里 | zhparser 没装成 | 检索会退化成 `pg_trgm`：系统仍能跑，但 §6 的关键词期望要按降级重读。回看构建日志哪一步失败 |
| `to_tsvector` 切出来是**单个字**（`'数':1 '据':2 …`） | 词库文件 `tsearch_data/dict.utf8.xdb` 没进最终镜像 | 检查 `deploy/pg/Dockerfile` 里那两条 `tsearch_data` 的 COPY——**扩展装上了 ≠ 词库带上了** |
| 构建时报 `registry-1.docker.io` 连接超时 | 境外镜像站不可达 | `.env` 里放开 `RAG_PG_BASE=docker.m.daocloud.io/pgvector/pgvector:pg17` |
| 构建时报 `deb.debian.org` / `apt.postgresql.org` 超时 | 同上 | `.env` 里放开 `RAG_DEBIAN_MIRROR`、`RAG_PGDG_MIRROR`（值见下） |
| 构建时报 `Unable to locate package: postgresql-server-dev-17` | 这个包**只在 PGDG 有**，只换 Debian 源不够 | 必须同时给 `RAG_PGDG_MIRROR`（本机 `mirrors.aliyun.com/postgresql/repos/apt` 通，ustc 同路径 404） |
| apt 阶段报 `No system certificates available` | 基础镜像里没装 ca-certificates（`dpkg -l ca-certificates` 显示 `un`），用 https 源会在「装证书」之前先失败 | 镜像源**必须写 `http://`**。apt 的完整性靠仓库 Release 文件的 GPG 签名，不靠 TLS |

▸ **换源只是取同一份官方字节的另一条路径**，不是换内容。那三个变量就是 `deploy/pg/Dockerfile` 顶部的三个 ARG，
默认值仍是官方源；构建完可以核对基础镜像 digest（本机拉到的 `pgvector/pgvector:pg17` 是
`sha256:b513c48566e4777cd3370451400000c78eda6a08131d68f4c31d4a76f27bd8fd`）。
▸ **不要改成直接用别人预编译的 zhparser 镜像**——那样中文全文检索这一路永远验不到，可审计性也没了。
▸ 容器内 `git clone` github.com 在本机不通（exit 128），而宿主侧 `codeload.github.com` 通——这就是 `fetch-vendor.sh`
取包、镜像里 `COPY vendor/*.tar.gz` 离线解压的原因，别在 Dockerfile 里改回 clone。
▸ 两条后面 §6 判定要用到的实测事实：编号类词会被连字符切开（`LEDGER-7731` → `'ledger' '7731'`，
`TAIL-9F3C` → `'tail' '9f' '3c'`），但正文与查询走同一套切法，所以 `mode=keyword` 仍命中——看到三个词位不是分词坏了；
数字与年份照样进索引（`35 天` → `'35' & '天'`），词性映射只留了 `n,v,a,i,e,l,j,x`（上游推荐集），
未收录的词落进 `x` 而不是被丢掉，所以库里根本没有的问题仍然是 0 命中，而不是「全部命中」。

## 2. 建表与 schema（后端首次启动会自己迁移）

**先要有什么**：§1 的 `rag-postgres` 是 healthy。**做什么**：起一次后端让 Flyway 建表，然后核对索引和向量维度。

### 敲什么

```bash
cd rag-api && mvn -o spring-boot:run      # 看到 ready 就 Ctrl+C；正式起用 deploy/start.sh（§3）
```

### 应该看到什么

首次启动日志里要看清三件事：

1. `Migrating schema "public" to version "1 - core schema"` 与 `"2 - task and chat"`；
2. 一句 `RAISE NOTICE`：**关键词检索使用 chinese(zhparser) 分词 + GIN tsvector**；
3. **没有** Flyway 校验和报错。

再用两条 SQL 核对落库结构：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select column_name, data_type, udt_name from information_schema.columns
  where table_name in ('kb_segment','kb_document')
    and column_name in ('embedding','content_ts','edited_at','chunk_override') order by 1;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select indexname, indexdef from pg_indexes where tablename='kb_segment' order by 1;"
```

期望：`embedding` 是 `USER-DEFINED/vector`、`content_ts` 是 `tsvector`（生成列）、
`edited_at` 是 `timestamptz`、`chunk_override` 是 `jsonb`；索引里有
`idx_segment_embedding_hnsw`（**HNSW，不是 IVFFlat**）、`idx_segment_content_ts`（GIN）、`idx_segment_content_trgm`（GIN）。

### 看不到怎么办

| 现象 | 原因 | 去哪儿改 |
|---|---|---|
| 日志出现「退化为 pg_trgm」 | 中文分词没就绪 | 回 §1，别继续 |
| Flyway 报 checksum mismatch | 改动过 `V1__core_schema.sql` 的旧库 | 先 `flyway clean` 或换新库。全新数据库正常不会遇到 |
| `embedding` 维度不是 768 | 启动用的 `RAG_EMBEDDING_DIM` 与建表时不同源 | 改回同一个值再重建库，**先别继续** |

## 3. 一键起整套，并读出模型的真实窗口

**先要有什么**：§1、§2 过。**做什么**：用 `deploy/start.sh` 起 PG + 后端 + 前端，读自检接口，然后把 `n_ctx` 对齐到模型真实窗口。

### 敲什么

```bash
deploy/start.sh          # 仓库根目录执行；它按 0/4→4/4 五段走，每段失败都停下并说去哪儿改
```

### 应该看到什么

五个阶段依次打印，最后是这样一段（本机原样）：

```
== 0/4 环境
   node v22.x.x
== 1/4 PostgreSQL（首次会编译 zhparser 镜像，5-15 分钟属正常）
   关键词检索：chinese(zhparser) 可用
== 2/4 rag-api
   pid 88 · 日志 deploy/logs/rag-api.log
== 3/4 rag-web
== 4/4 自检
{"code":200,"message":"关键依赖就绪",...}

起来了：
  前端  http://localhost:5173/
  后端  http://127.0.0.1:8080/api
  日志  deploy/logs/rag-api.log · deploy/logs/rag-web.log
  停止  deploy/stop.sh
```

然后自检接口——**这一步是分水岭**，五个探针 UP 说明库通，八个 UP 说明模型也通：

```bash
curl "http://localhost:8080/api/health"                 # 不带 models：只查本地依赖（5 个探针）
curl "http://localhost:8080/api/health?models=true"     # 带 models：真连模型（8 个探针）
```

本机 2026-11-17 实测 `models=true` 返回（照这个对，`ready` 必须是 `true`）：

```json
{"code":200,"message":"关键依赖就绪","data":{"ready":true,"probes":[
 {"name":"postgres",            "status":"UP","detail":"pgvector 0.8.7，HNSW 索引就绪"},
 {"name":"chineseFullText",     "status":"UP","detail":"使用 chinese(zhparser) 分词做关键词检索"},
 {"name":"storage",             "status":"UP","detail":"...\\.storage 可写"},
 {"name":"embeddingConsistency","status":"UP","detail":"库内 text-embedding-bge-base-zh-v1.5 与配置一致"},
 {"name":"modelIds",            "status":"UP","detail":"6 个模型可选，chat/embedding 均在列表内"},
 {"name":"embedding",           "status":"UP","detail":"768 维"},
 {"name":"chat",                "status":"UP","detail":"模型 glm-4-9b-chat-1m 响应：正常"},
 {"name":"modelEcho",           "status":"UP","detail":"回显一致：embedding=text-embedding-bge-base-zh-v1.5，chat=glm-4-9b-chat-1m"}],
 "traceId":"ec41f549"}}
```

浏览器打开 **`http://localhost:5173/`**（注意不是 `127.0.0.1`），应看到「问答 / 文档 / 检索调试 / 自检」四个页签。

### 看不到怎么办

| 现象 | 含义 | 去哪儿改 |
|---|---|---|
| `modelIds` DOWN | 配置的模型名与 `/v1/models` 的 id 不是逐字符相同。LM Studio 对认不出的名字**不报错**，会用当前已加载模型应答——静默换模型比报错更难查 | 改 `.env` 的 `LM_STUDIO_CHAT_MODEL` / `LM_STUDIO_EMBEDDING_MODEL`，**不是改代码** |
| 模型不可达只报 DEGRADED，`ready` 仍 false | 正常时序问题：本机常先起 rag-api 再起 Local Server | 把模型机起来，再 `curl .../health?models=true` 复看 |
| 健康检查卡住不动 | 历史上是 HTTP/2 协商问题（ADR-004），已固化 HTTP/1.1 + 5s 连接超时 | 若复现，先确认没有绕过 `LmStudioHttpClient` |
| 第 2 步打印「已在运行（pid N），跳过启动」 | 后端本来就在跑，**这一支不打包也不替换**：改了代码的话自检绿的是旧 jar | 先 `deploy/stop.sh` 再 `deploy/start.sh` |
| 第 2 步打印「`127.0.0.1:8080` 上已经有一个会答 `/api/health` 的进程，且不是本脚本起的」 | 端口被别的实例占着（IDE 里跑的、或前端联调用的 mock） | 那是 mock 的话先停掉，否则第 4 步的绿是假的 |
| `rag-web` 45 秒没起来 | 端口被占 | `RAG_WEB_PORT=5174 deploy/start.sh` |

### 现在把 `n_ctx` 对齐真实窗口（一次就够）

**LM Studio 不提供查询上下文的端点**，`/v1/models` 里没有 context 字段，界面上的数字又容易看漏。
唯一可靠的读法：**发一条注定超限的请求，让 400 错误体自己说。**

```bash
node -e 'const s="混合检索与倒数排名融合的说明。".repeat(4000);
require("fs").writeFileSync("/tmp/over.json",JSON.stringify({model:"glm-4-9b-chat-1m",
  messages:[{role:"user",content:s}],max_tokens:8}))'
curl -sS http://192.168.1.61:1234/v1/chat/completions -H "Content-Type: application/json" --data-binary @/tmp/over.json
```

应该看到（本机 2026-11-16 实测，两个 chat 模型都是 16384）：

```
"request (36005 tokens) exceeds the available context size (16384 tokens)...","n_ctx":16384
```

把这个数写进 `.env` 的 `RAG_LLM_N_CTX`（**默认值已是本机实测的 16384**）。同一条响应顺便给出折算系数：
60000 汉字 = 36005 token（glm）/ 40019 token（qwen），即 **1 token ≈ 1.5 个汉字**，
所以配置里的 `chars-per-token=1.0` 站在「少装」那一侧，是刻意保守，不是估算失误。

| 写错的后果 | 症状 | 说明 |
|---|---|---|
| 写大了（配置 > 模型真实窗口） | 问答直接 413 | 现在这条是独立的 413 分支，报错里回显模型侧真实窗口，`/api/diagnostics` 留下 `contextOverflow` 计数，**不会伪装成「模型服务不可用」** |
| 写小了 | 不报错，但每轮白白少装几块资料 | 撞过一次 400 之后 diagnostics 会主动提示「把 `RAG_LLM_N_CTX` 提到 X」 |
| 答案少了一段但没报错 | 装配吃不下 | 查 `effective.contextBudgetChars` 与 `unplacedHits`（§11） |

## 6. 检索实测：三种模式 + 降级必须看得见

**先要有什么**：§5 有 READY 的文档，`kbId` 由 `GET /api/knowledge-bases` 给出（默认库是 1，必须显式指定）。
**做什么**：四种查询各打一次，核对召回与量纲。

### 敲什么 / 点哪里

界面：左侧「检索调试」。命令行等价（中文已做 URL 编码，直接复制不会踩 GBK 的坑）：

```bash
# 混合（默认）：期望第一条来自 01 第 2 节
curl -sS "http://localhost:8080/api/search?q=%E5%A4%87%E4%BB%BD%E4%BF%9D%E7%95%99%E5%A4%9A%E5%B0%91%E5%A4%A9&kbId=1&topK=5"

# 关键词路独占：编号类词向量路召不稳，这里必须命中 07
curl -sS "http://localhost:8080/api/search?q=LEDGER-7731&kbId=1&mode=keyword"

# 段落尾部校验码：命中 03 的最后一块
curl -sS "http://localhost:8080/api/search?q=TAIL-9F3C&kbId=1&mode=hybrid"

# 库里根本没有的问题：期望 hitCount=0 或全部低于阈值
curl -sS "http://localhost:8080/api/search?q=2032%E5%B9%B4%E7%81%AB%E6%98%9F%E6%A4%AD%E6%B0%91%E9%A2%84%E7%AE%97&kbId=1"
```

### 应该看到什么

每条返回都要看这六个字段——**它们决定「召回差」是模型问题还是配置问题**：

| 字段 | 期望 |
|---|---|
| `requestedMode` / `effectiveMode` | 一致；不一致说明发生了降级，`degraded=true` 且 `keywordEngineNote` 会解释原因 |
| `keywordEngine` | `CHINESE_TSVECTOR`（装了 zhparser）或 `TRIGRAM`（退化）；`NONE` 表示关键词路整条不可用 |
| `rrf` | 混合模式下量级 **0.01x**（如 `0.01639344262295082`）。若看到 0.4x 量级，说明阈值或融合算错了 |
| `min-rrf-score` 效果 | 混合模式阈值 0.012，**不能**照抄纯向量的 0.45，否则 hitCount 恒为 0 |
| `similarity` | 纯向量模式才有值；低于 0.45 的会被滤掉，宁可不答 |
| `tookMs` | 本机量级：2ms（纯关键词）到几十毫秒。突然上到秒级先看 LM Studio 是不是在加载模型 |

本机实测的三条正解，可以当标准答案：

```
「备份保留多少天」  hybrid  rank=1  rrf=0.03252247488101533  命中《01-运维手册.md》且正文含 35
LEDGER-7731        keyword   rank=1  rrf=0.01639344262295082  命中《07-变更台账.csv》
TAIL-9F3C          hybrid    rank=1  rrf=0.03252247488101533  命中《03-无标点长段落.md》
```

▸ rrf 的量纲是 `Σ 1/(rrfK + rank)`，`rrfK=60`：只有一路命中第 1 名是 `1/61=0.016393`，两路都第 1 名是 `2/61=0.032787`。
看到 `0.032` 与 `0.016` 两种数是**正常**的，前者说明这条两路都召回到过。

### 看不到怎么办

| 现象 | 原因 | 去哪儿改 |
|---|---|---|
| `hitCount=0` 且问的是正解词 | 阈值调严了，或库里没有 | 看 §11 的 `effective.minRrfScore`；确认没把 `min-score=0.45` 抄到混合模式 |
| `effectiveMode` 变成 `KEYWORD` | 向量路没走成（模型不可达 / embedding 维度不符） | **此时这批 rrf 分数全部作废**，量纲换了。先修 §3 的 `embedding` 探针再重跑 |
| `keywordEngine=TRIGRAM` | zhparser 没就绪 | 回 §1。系统仍能跑，但关键词召回会差一截，§12 的 keyword 读数要按降级重读 |
| 库里没有的问题也召回一堆 | 这是**预期**：混合模式的闸门是 `min-rrf-score=0.012`，任何一条向量近邻都能过 | 真正能压住「库里没有」的是向量路的余弦闸门 `min-score=0.45`（`mode=vector`）。见 §12 的拒答正确率为什么是 0 |

## 7. 问答实测：流式、引用、拒答、中断、装不下

**先要有什么**：§6 检索能命中。**做什么**：问一个答案写死在样本里的问题，然后逐条验四种「不正常」。

### 点哪里 / 敲什么

### 应该看到什么

事件序列必须是 `meta → delta* → done`。答案里出现 **35 天** 与 **每周日全量同步**。
`meta.sources` 至少一条指向 `01-运维手册.md` 且 `location` 说得出「第 2 节 / 页 / 字偏移」。

### 再验四种「不正常」

| 要验的 | 怎么做 | 期望 |
|---|---|---|
| **拒答** | 问「2032 年火星殖民预算」 | `status=REFUSED`，文案是固定的「知识库里没有找到可靠依据」，引用区为空。**模型自己编一句「我不确定」也算不合格** |
| **中断** | 生成过程中点停止 | 该条消息 `status=INTERRUPTED`，重新进入页面仍是 INTERRUPTED（落库的，不是前端状态） |

| **多轮改写** | 先问「备份保留多少天」，再问「那原件呢」 | 第二轮的 `queryFinal` 应被改写成带主题的问题，不是原样把「那原件呢」丢给检索 |
| **缺范围要在起流之前挡** | 不带 `kbIds` 也不带已有会话地问一次 | **HTTP 400 + JSON 信封**，不是事件流里的 `error`；会话列表里也不该多出一条答不下去的问句 |

▸ 最后这条曾经兜底成「查默认知识库」，答案照样通顺，只能从 `meta.sources` 看出资料来自没选过的库——
范围必须在任何写入之前决定。

`/api/diagnostics` 里 `counters.contextOverflow` +1，`lastContextOverflow` 记录 configured/reported，
并留一条告警「配置 n-ctx=60000 比模型真实窗口 16384 还大……在 LM Studio 里调大 context」。
这一轮答案 `status=FAILED` 而不是 `INTERRUPTED`：装配失败和模型半路死掉是两类原因，评测要分得开。

**测完必须收尾**：`rm over.json ask.json`，再回看一眼 `curl ".../api/health?models=true"`——
大窗口不会弄坏数据，但每轮长答案都会白撞一次 413，忘了恢复的话下一段实测全在解释一个不存在的问题。

## 9. 分块覆盖与单块编辑（M5c / M5b）

**先要有什么**：§5 有 READY 的文档。**做什么**：验四件事——覆盖只影响下次重算、单块编辑能把向量作废、
块级禁用可逆、入库进行中拒绝编辑。这一段**必须在界面上点**，`smoke.sh` 只自动验了「块级禁用可逆」那一条。

### 点哪里

界面：「文档」→ 任选一篇点进详情 → 「分块」区。

| 序号 | 操作 | 应该看到什么 |
|---|---|---|
| 1 | 把子块从 400 改成 **260**、父块 **900**，先点「预览」 | 预览**不写库**，块数应变多 |
| 2 | 点「存为本文档覆盖」→「重算」 | 进度文案里出现 `语义分块 子块 260 / 父块 900 字`；`kb_document.version` +1 |
| 3 | 查库 | `chunk_override` 里**只有差异的那两个键**——等于全局默认的键不落库 |
| 4 | 把值改回全局默认，再「重算」 | 恢复默认**必须再重算一次才生效**：覆盖只影响下次入库，这是设计，不是 bug |
| 5 | 挑 01 表格里的一块，把内容改乱再订正回来，勾「同时重算向量」 | 该块出现「已编辑」标签、`emb_status` 回 `READY` |
| 6 | 同一条不勾「同时重算向量」再改一次 | 只改文字：`emb_status=PENDING`，并长出「重算向量」按钮 |
| 7 | **把模型服务关掉**，重复第 6 步（不勾重算） | 仍然 **200 + `embedded:false` + 一句 note**，**不是 502**——文字保存才是用户点这一步的目的 |
| 8 | 把 02 里「内部薪酬」那一块的 `available` 关掉，再检索 | `curl "…/api/search?q=%E8%96%AA%E9%85%AC&kbId=1&mode=keyword"` → 不再命中；重新打开即恢复 |
| 9 | 上传 01 之后**立刻**去编辑某块 | 被拒：**409**，并说明当前状态（入库进行中不允许改） |

第 3、5 步的库内确认：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select id, version, chunk_override from kb_document where name like '%运维手册%' and deleted_at is null;"
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "select id, left(content,24) as 正文, emb_status, available, edited_at is not null as 已编辑
  from kb_segment where doc_id={docId} order by chunk_no limit 12;"
```

### 看不到怎么办

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 改了覆盖值但块数没变 | 只「存为覆盖」没「重算」 | 覆盖不影响已有块，必须重算 |
| 重算之后 `chunk_override` 里全是五个键 | 把等于默认值的键也写进去了 | 是 bug：只有差异该落库，记下来 |
| 第 8 步关掉之后仍命中「薪酬」 | 禁用没进检索谓词 | 记 `traceId`。smoke 第 7 步对这条有断言，可直接 `deploy/smoke.sh` 复现 |

## 10. 归档包导出 / 导入（M5d 验收，最关键的一段）

**先要有什么**：§5 的对账 SQL 结果存了一份。**做什么**：整库搬家一次，验「向量免重算」和「人工意图原样带回」。
这段现在有 `ArchiveIT` 六例连库测试兜着（`mvn -o verify`，不需要模型），下面的 curl 是它的等价人工版：
自动化测的是**包结构与落库事实**，你手跑要补的是**界面侧**（导入结果框）和真模型下 `rebuild=true` 的实际耗时。
两边结论对不上时，**先信数据库里的那条 SQL**。

### 第 1 步：导出

```bash
curl -sS -OJ "http://localhost:8080/api/knowledge-bases/1/export?vectors=true&files=true"
unzip -l kb-1-*.zip
```

期望包内条目：`manifest.json`、`content/0.txt … N.txt`、`segments/0.jsonl … N.jsonl`、`files/{slot}/{原始文件名}`。
`manifest.json` 里 `format: 1`、`vectors: true`、`files: true`、`source.embeddingDim` 等于 768、
`source.embeddingModel` 与配置同名，`documents[]` 每项带 `slot / name / sha256 / version / segmentCount / chunkOverride`。
**slot 从 0 连续编号，不是数据库 id。**

### 第 2 步：清空当前库（软删，与界面删除等价）

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
  "update kb_document set deleted_at=now(), available=false where kb_id=1;"
```

### 第 3 步：导入同一个包，验「免重算」

```bash
curl -sS -F "file=@kb-1-20261117-XXXXXX.zip" \
  "http://localhost:8080/api/knowledge-bases/1/import?rebuild=false"
```

期望返回（样本里 READY 的是 01/02/03/07 四篇：06 与 01 同哈希不会成第二行，04/05 是 FAILED 不入包）：

```json
{"code":200,"message":"向量直接可用：导入 4 篇 / … 块，未花一次 embedding",
 "data":{"kbId":1,"mode":"CARRIED","imported":4,"queued":0,"segmentsCarried":…,
         "originalsRestored":4,"skippedSame":0,"skippedEmpty":0,"failed":0,"notes":[…]}}
```

`mode` 只有两种，这是判断「有没有白花钱」的关键：

| `mode` | 含义 |
|---|---|
| `CARRIED` | 模型名与维度都对得上 → 向量直接照搬，一次 embedding 都没花 |
| `REBUILT` | 空间不兼容（或你勾了 `rebuild=true`）→ 按重新入库排队，等文档变 READY 后检索才完整 |

### 第 4 步：四条硬判据（缺一不可）

1. `mode=CARRIED`、`queued=0`，且 **rag-api 日志里不出现任何 EMBEDDING 阶段**——这是「没重算」的唯一硬证据：
   ```bash
   grep -c EMBEDDING deploy/logs/rag-api.log     # 导入这一段应当没有新增
   ```
2. `skippedEmpty` 这里是 0：正文为空的文件根本到不了 READY，也就不会进包，这个计数只在手工改过的包里出现。
3. **再跑一遍 §5 那条对账 SQL**：`块数 / 有向量且可用 / 父块` 三个数必须与清空前**逐行一致**；
   `已禁用` 仍等于你在 §9 关掉的那几块（`available=false` 是人工意图，导入必须原样带回来）；
   `已编辑` 仍等于 §9 编辑过的块数（`edited_at` 没丢）。
4. 检索与原件复验：`LEDGER-7731`、`TAIL-9F3C`、`薪酬`（仍应因禁用而不命中）三条结果与清空前一致；
   对任意一篇点「重解析」能读到原文件，说明 `files/` 真落盘了（`file_path` 非空）。

▸ 软删只标 `deleted_at`，**不删块**（检索靠 `d.deleted_at IS NULL` 过滤）。导入后
`select count(*) from kb_segment` 的总数会接近翻倍，那是正常残留，别当成导入重复——对账永远用按文档分组的那条 SQL。

### 第 5 步：四条拒绝路径（比成功路径更容易在真实数据上出问题）

```bash
# 1) 不是 zip → 400，且发生在写第一行数据之前
curl -sS -F "file=@README.md" "http://localhost:8080/api/knowledge-bases/1/import"
# 期望：code=400 这个包不是有效的 zip：zip END header not found

# 2) 同库重复导入 → 全部 skippedSame，一行都不写
curl -sS -F "file=@kb-1-XXXX.zip" "http://localhost:8080/api/knowledge-bases/1/import?rebuild=false"

# 3) 强制重算 → mode=REBUILT，文档排队到 PENDING，最终逐篇 READY（这次会真花 embedding）
#    导进下面建好的 2 号库；不想建库就导回 1 号库，但要先再执行一次第 2 步的软删，
#    否则同哈希全部命中 skippedSame，一行都不会写，看不出重算效果
curl -sS -F "file=@kb-1-XXXX.zip" "http://localhost:8080/api/knowledge-bases/2/import?rebuild=true"

# 4) 维度不符 → 409，文案给出「本库 N 维 / 当前配置 M 维」两个数
RAG_EMBEDDING_DIM=512 deploy/start.sh      # 换配置重启，再导入同一个包
```

**可选：跨库导入用的 2 号库**——目前只有 `ensureDefault` 会建「默认知识库」，没有建库接口，手工插一行即可
（模型名与维度必须与配置一致，否则命中的是拒绝路径 4）：

```bash
docker exec -it rag-postgres psql -U rag -d rag_knowledge -c \
 "insert into knowledge_base (name, embedding_model, embedding_dim)
  values ('迁移验证库', 'text-embedding-bge-base-zh-v1.5', 768) returning id;"
```

### 界面侧同步验一遍（这一段替代不了）

「文档」页 → 「归档」→ 目标库 / 带向量 / 带原件 → 导出（浏览器存下的文件名应是 `kb-1-yyyyMMdd-HHmmss.zip` 且能解压）；
「选择 .zip」导入后弹「导入结果」框，`mode` 标签、八个计数与逐篇 `notes` 都要显示出来——
**notes 是唯一能说清「为什么少了一篇」的地方**。

### 跑这一段时顺带确认的三件边界事

- **1234 只做局域网、不做鉴权，这是既定决策**（信任边界 = 不出局域网）。在跑 LM Studio 的那台机器上
  `0.0.0.0:1234 LISTENING` 是**预期状态**（勾了 Serve on Local Network 就该这样）。要确认的是另外两件：
  路由器上没有把 1234 映射出去，防火墙入站只放专用网络。
  ```bash
  netstat -ano | findstr :1234     # 期望 0.0.0.0:1234 LISTENING（内网机），且没有公网映射
  ```
- **模型服务端的 `logSensitiveData` 实测是开启的**——每次问答的原文与提示词都以明文留在那台机器的
  LM Studio 历史里，而不只在咱们的库里。「数据不出本地设备」因此实际是「不出这两台机器」。
  合同、台账这类内容放进来之前要想清楚；要收回去就在 LM Studio 设置里关掉对话历史
  （本项目不改它的任何设置，也不建议改模型服务的运行参数）。
- **那台机器是 DHCP 拿的 `192.168.1.61`**，路由器上没做静态租约时地址会漂。换过 Wi-Fi 或重连网络后
  `LM_STUDIO_BASE_URL` 打不通，**先看地址漂没漂，再看代码**。开启 AP 隔离的 Wi-Fi 会让设备之间根本不通，
  排查时先换网线确认。

## 12. 评测集与跑分（M5e 验收）

**先要有什么**：§5 有 READY 文档、§6 那批事实能命中。**做什么**：建 6 条用例、跑两轮、读参数快照与 delta。
**这一节没有前端页面**（有意的取舍，见本节末），只能用 curl 或 `deploy/smoke.sh` 第 9 步。

### 敲什么

```bash
curl -sS -X POST http://localhost:8080/api/evaluation/cases -H 'content-type: application/json' \
  -d '{"kbId":1,"question":"数据库备份保留多少天","expectMarker":"35","expectDoc":"运维手册"}'
curl -sS -X POST http://localhost:8080/api/evaluation/cases -H 'content-type: application/json' \
  -d '{"kbId":1,"question":"食堂今天几点关门","shouldAnswer":false}'
curl -sS -X POST 'http://localhost:8080/api/evaluation/run?kbId=1&mode=hybrid&note=第一版'
curl -sS "http://localhost:8080/api/evaluation/runs?limit=5"      # 每轮带参数快照与相对上一轮的 delta
```

判据只有 `expectMarker` 一个：命中块正文里出现这段文字（忽略大小写、折叠空白）就算找到。
**锚在文字而不是 `segment_id` 上**——改分块尺寸或重算向量之后块 id 一定变，而评测要问的恰恰是「换了参数还找不找得到」。
跑分只走检索、不生成答案，一轮几秒钟。

### 应该看到什么

本机 2026-11-17 真机读数（库内 4 篇 READY 全块可用，用例照抄 §5/§6 那张事实表）：

| 轮次 | hit@1 | hit@3 | hit@K | MRR | 空召回率 | 排在K外 | 拒答正确率 | 截断率 |
|---|---|---|---|---|---|---|---|---|
| `mode=hybrid`（topK=6） | 1.0 | 1.0 | 1.0 | 1.0 | 0 | 0 | **0** | **0.8** |
| `mode=keyword`（topK=6） | 0.8 | 0.8 | 0.8 | 0.8 | 0.2 | 0 | 1.0 | 0 |
| `mode=hybrid&topK=50` | 1.0 | 1.0 | 1.0 | 1.0 | 0 | 0 | 0 | 1.0 |

`smoke.sh` 第 9 步打印的就是这三行（对照你自己的读数）：


相邻两轮的 `delta`（hybrid → keyword 那一跳）：

```json

 "emptyRecallRate":0.2,"truncatedCaseRate":-0.8}
```

每个指标在问什么：

| 看什么 | 它在问 | 读数注意 |
|---|---|---|
| `hitAt1` / `hitAt3` / `hitAtK` | 期望块排进前 1 / 前 3 / 前 K（K=本次 topK）的正例比例 | `hitAtK < 1` 而 `emptyRecallRate = 0` → 是排序问题不是闸门问题；两个一起掉才先怀疑阈值 |
| `mrr` | 相关块名次的倒数平均 | 只用来整体看排序质量，别拿它做单参数决策（第 1 名和第 6 名的差被压成 0.83） |
| `emptyRecallRate` | 正例一条都没召回的比例 | 这个数动的是闸门：`min-score`（余弦量纲 0.45）/ `min-rrf-score`（融合分量纲 0.012）调严了先红这里 |
| `rankedBeyondK` | 召回了、但期望块不在窗口内 | 与 `hitAtK` 互补；加大 `topK` 能救，代价是上下文预算 |
| `refusalAccuracy` | 负例（库里真没有）里正确拒答的比例 | 分母是负例条数。**没有负例时报「不适用」（null），不是 0** |
| `truncatedCaseRate` | 正例里「召回了但有块没装进上下文」的比例 | 量的是**装配**不是检索：它不为 0 时 hit@K 照样可以是 1.0。修法在 `n_ctx` / `parent-max-chars`，别去动阈值 |
| `invalid` | 未标注的正例条数 | 整条不进任何分母，只在这里报数；`cases` 里含它 |
| `avgTookMs` | 单条检索平均耗时 | 只有判过分的条目参与，别和 `cases` 对不上 |

### 看不到怎么办：逐条 `reason` 就是排查表

`GET /runs/{id}` 的逐条结果里，`reason` 是判的那一刻写下的中文一句话。三种失败长得像，但修法完全不同：

| 原因文案 | 该动哪里 |
|---|---|
| `空召回：阈值过滤后一条命中都没有` | 库里真没有，或 `min-score` / `min-rrf-score` 太严 |
| `召回 N 条但装配一条都没装下（正文为空或预算不足）` | 分块尺寸或 `n_ctx` 预算，跟检索无关；线上这条会真的拒答 |
| `相关块没进前 N 名（召回 M 条，其余 K 条没装进上下文，本来就够不到模型）` | 名次够不到；如果 K>0，先加大 `topK` 再看预算装不装得下 |
| `找到了，但召回 N 块里有 K 块没装进上下文` | 期望块进了模型，别的没进——分数没错，但线上少资料，动 `n_ctx` / `parent-max-chars` |
| `排在第 N 名，本次上下文只装下 M 块，模型没读到它` | hit@K 记了命中、线上却答不出：预算问题，不是排序问题 |
| `库里没有的东西被召回了：《x》 第 1 名` | 负例没被闸门挡住 → 拒答正确率掉的就是这一项 |

### 四件必须记住的事（比分数本身值钱）

- **`hit@1` 是 0.8 还是 1.0，取决于库里哪些块可用，不取决于参数。** 本轮 `LEDGER-7731` 的期望块是
  `07-变更台账.csv` 第 2 块，两路都把它排第 2（`vectorRank=2 / keywordRank=2`，`rrf=1/62+1/62=0.032258`），
  于是它自己就是第 1 名，**没有并列**，`hit@1=1.0`。而 11-16 那三行报的是 `0.8`：当时台账 6 块里有 5 块被
  `--archive` 那段关掉了（每跑一轮关一块、从不恢复），只剩表头那块可用，关键词路第 1 名成了 `07-…#0`、
  向量路第 1 名是 `01-运维手册.md#15`，两路第 1 名各拿一模一样的 `1/(60+1)=0.016393` 才并列；
  并列要有先后，破法是「文档名 + 块序」，`01-` 排在 `07-` 前面，期望块于是落第 2 名（`hit@3` 与 `hit@K` 不受影响）。
  **错的是把某一轮的 `0.8` 当成这套参数的固定答案。** 破法本身别退回插入号 `f.id`：重新入库、`--archive` 重导入、
  单块重算向量都会换块 id，名次就跟着数据库的写入顺序走（详见 `docs/重构方案.md` §20 ADR-022）。
  改完之后本机 37~42 六轮（三种参数各两轮）七项指标逐轮完全相同——**同一套参数连跑两轮读数相同，这套跑分才有比较资格。**
- **hybrid 的拒答正确率 0 不是 bug。** 该轮生效闸门是 `min-rrf-score=0.012`（RRF 融合分量纲：两路都拿第 1 名约
  0.032，只有一路命中的第 1 名约 0.0164，`1/(60+rank) >= 0.012` 解出来单路前 23 名都能过），任何一条向量近邻都能过。
  库里没有「食堂」这个话题，检索器照样端回 6 块运维手册，装配不为空 → 不拒答 → 模型被拿无关资料提问。
  **想让「库里真没有」真的落到拒答，靠的是向量路的余弦闸门 `min-score=0.45`（`mode=vector`），不是 RRF 阈值。**
  这就是留着负例的目的：它测的是幻觉抑制的边界，不是检索准不准。
- **keyword 那一轮 `空召回率=0.2` 掉的是「工单 OPS-2026-118 记了什么误配」**：纯关键词路对这种
  「问句里没有正文里的字面 token」的问题无能为力（同一条在 hybrid 里 rank=1）。
- **`截断率=0.8` 而 `hit@K=1.0`，这两件事同时成立才是对的。** hybrid 每轮召回 6 块，装配按名次从前往后装，
  父块正文长，把 `contextBudgetChars=14784` 吃到只剩不到 120 字符后就停下不装了——于是 5 条正例里 4 条的原因写着
  「召回 6 块里有 1~2 块没装进上下文」。这一条**不该**去动 hit@K：hit@K 量的是检索排第几，
  把它和预算混在一起，调 `n_ctx` 就会看起来在改检索质量。想验得更狠就 `topK=50` 跑一轮：
  每例召回 23~25 块、只装得下 13 块上下，hit@K 仍是 1.0，截断率仍是 1.0。
  日志里同步有一行 WARN（`grep 却没装进上下文 deploy/logs/rag-api.log`），因为它意味着这轮分数与预算充足那轮不可比。

### 还有两个容易踩空的地方

- **别以为 embedding 服务没起就能安全跑分。** 查询向量算不出来时检索不报错，而是当场退成关键词路，
  跑分照样出全套指标——只是那一轮的分数是一路的分数，跟正常轮次不可比。三处会说实话：
  逐条 `reason` 末尾多一句「降级跑的：请求 HYBRID，实际只走 KEYWORD（原因）」；日志一行 WARN
  （`grep 降级跑出来的 deploy/logs/rag-api.log`）；`GET /diagnostics` 的 `vectorDegraded` 计数。
  参数快照帮不上这个忙——快照是在跑第一条用例**之前**写的，记的只能是「请求了什么」。
- **`truncatedCaseRate` 是后加的指标**，之前的历史轮次没存这个数：列表里读成 `null`（信封写「不适用」），
  `delta` 也会跳过这一项而不是拿 0 去比。**「没存过」和「一条都没截」是两件事**，这里按前者处理。

`eval_run.settings` 记 15 项当轮真正生效的参数（模式、生效阈值 `threshold` 及两个来源 `minScore`/`minRrfScore`、
`topK`、`candidateK`、`rrfK`、`parentContext`、`keywordEngine`、`embeddingModel`、`embeddingDim`、`nCtx`、
折算出的 `contextBudgetChars`，以及 `modeOverride`/`topKOverride`）。要比较的两次跑分必须只有一个变量不同，
所以覆盖项只开 `mode` 与 `topK` 两个——阈值这类改了要重启服务，这样快照必然等于真实生效值。

### 从反馈里长用例

```bash
curl -sS -X POST 'http://localhost:8080/api/evaluation/cases/from-feedback?kbId=1'
```

只捞 `rating=-1` 且已填 `annotatedAnswer` 的回答（§8 的产物），取的是 `query_final`
（改写后那句才是检索真正面对的输入），按会话的 `kb_ids` 过滤，一次最多 50 条，生成 `enabled=false` 的待标注用例。
**一律不启用是刻意的**：判据得人给，机器从订正答案里截一段当 `expect_marker` 等于让评测自己考自己。
未启用的正例强行 `PATCH enabled=true` 会吃 400，`POST /run` 在没有启用用例时同样 400 且不落任何 `eval_run` 行。

删掉一条用例（`DELETE /cases/{id}`）不会抹掉历史：`eval_result` 存了那一刻的问句、判据、名次与原因，
所以「当初为什么是 1.0」在用例没了之后还读得回来（这是 `case_id` 故意不建外键的原因）。
`GET /runs` 的 `delta` 只在列表里算（相邻两轮），单条 `runs/{id}` 恒为空——这是有意的。

评测**没有前端页面**，这是有意的取舍：跑分要成批比较参数、逐条读错例原因，命令行与回归脚本比界面顺手。
等标注工作量真的大到需要批量操作时再补页面。

### 我已经先跑过一遍（本机 2026-11-17）

`mvn -o verify` 261 例单测（30 类）+ 47 例 IT（6 类）全绿，其中 4 条连 LM Studio 的按 `LM_STUDIO_IT` 开关跳过；
`node deploy/smoke.mjs --models --archive` → **PASS 63 / FAIL 0 / SKIP 0**
（不带 `--archive` 是 54 项，多的那 1 项是归档段自己的「恢复本轮关掉的块」）。
所以**这一轮你跑出来的失败项，第一嫌疑是环境差异（模型名、服务地址、`.env` 里的窗口值），不是代码本身。**

首轮真机跑一共揪出三处产品缺陷（新建会话 SQL 拼坏、SSE 前参数错没有 JSON 信封、缺范围兜底默认库）
和三处脚本自身的误报，都已修掉并各补了能失败的测试——「连库跑」和「mock 跑」能发现的问题不是一类，
这也是这套自动化测试仍然要留着人工清单的原因。跑 M5e 那次同理：负例的 `refused` 被写死成常量 `true`，
纯单测与连库测试都看不出（那边的负例本来就真拒答），是 smoke 第 9 步在真库上跑出
「混合模式拒答正确率 0」才对上号——见 §12 那张读数表。
同一个位置还揪出第二个盲区：装配「召回 6 块只装下 5 块」这件事当时在跑分里完全没有读数，
`hit@K=1.0` 看起来一切正常，现在它有自己的指标 `truncatedCaseRate`。
第三个是 11-17 补的，性质不一样：前两个是「少了一个读数」，这个是「已有的读数不可复现」——
文档写的 `hit@1=1.0` 在真库上稳定读出 0.8，而它之前又确确实实读出过 1.0；查下去是 RRF 并列名次由块 id 决定，
重新入库就会换人（§12 第一条）。
**这一节里所有分数都应当按「你重跑一遍能不能读出同一组数」来读，而不是按好不好看来读。**

### 还没做 / 不要按「应该过」来记的部分

- rerank 不是「没做」而是**已按实测否决**：本机 Lynx-8B 在 CPU 上 5 候选要 11.7s，top-3 顺序与原序完全一致——
  纯负收益，别再排期。
- 评测集**没有前端页面**，只有 8 个接口与回归脚本第 9 步（理由见 §12 末）。

  **仍然要人工跑的只剩两件事**：界面侧的导出/导入结果框（notes 是否逐篇显示出来），以及真模型下
  `rebuild=true` 到底花多少时间——后者是搬库时的实际决策依据，假向量测不出来。

# LM Studio 在另一台机器上的接入方式

本项目后端（`rag-api`）与前端都跑在这台开发机（当前局域网地址 `192.168.1.60`），模型推理跑在另一台机器的 LM Studio 上。

## 1. 在跑 LM Studio 的那台机器上

1. 左侧 **Local Server**（或 `Ctrl/Cmd + L`）。
2. 打开 **Serve on Local Network** 开关（默认只监听 `127.0.0.1`，别的路径都连不上）。
   等价 CLI：`lms server start --bind 0.0.0.0`
3. 端口保持 `1234`。
4. **Windows 防火墙**：给 TCP 1234 加入站规则（专用网络）。不做这步的表现是「IP 是对的但一直连不上」。
5. 需要时再加载 Embedding 模型（`/v1/embeddings`）与对话模型（`/v1/chat/completions`）—— 两个都要在 `/v1/models` 里能看到。
6. CORS 不用开：浏览器只访问 `rag-api`，模型调用全在后端进程里发生。

## 2. 在这台开发机上

`application.yml` 里的默认值已经按实测环境写好（`http://192.168.1.61:1234/v1` + 两个真实模型 id），换机器才需要覆盖：

```bash
export LM_STUDIO_BASE_URL=http://<那台机器的IP>:1234/v1
export LM_STUDIO_EMBEDDING_MODEL=<该机器 /v1/models 里 embedding 的 id>
```

或在 `rag-api` 启动时传入：

```bash
mvn spring-boot:run -Dspring-boot.run.arguments="--rag.lm-studio.base-url=http://192.168.1.x:1234/v1"
```

真机校验已经做成可选集成测试，默认跳过，跑一次把地址、模型名、维度、批量与流式全验掉：

```bash
LM_STUDIO_IT=true mvn verify -Dfailsafe.forkedProcessTimeoutInSeconds=240
```

## 3. 验证顺序（先 curl 再框架，能省掉大半排查时间）

```bash
# 1) 端口通不通 + 模型 ID 到底是什么（模型名必须与此处返回的 id 完全一致）
curl http://192.168.1.x:1234/v1/models

# 2) 对话链路
curl http://192.168.1.x:1234/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"<id>","messages":[{"role":"user","content":"只回复两个字：正常"}],"temperature":0.3}'

# 3) 向量链路（重点看返回数组长度，它决定 rag.embedding.dim）
curl http://192.168.1.x:1234/v1/embeddings -H "Content-Type: application/json" \
  -d '{"model":"<embedding-id>","input":"本地知识库健康检查"}'

# 4) 后端自检（会实调模型并报告维度）
curl "http://localhost:8080/api/health?models=true"

# 5) 后端列出模型（用于核对 chat-model / embedding-model 是否写错）
curl http://localhost:8080/api/models

# 6) 走后端链路分别试调，embedding-test 会直接告诉你维度是否与 rag.embedding.dim 一致
curl http://localhost:8080/api/models/chat-test -H "Content-Type: application/json" \
  -d '{"question":"只回复两个字：正常"}'
curl http://localhost:8080/api/models/embedding-test -H "Content-Type: application/json" \
  -d '{"text":"本地知识库健康检查"}'
```

`/api/models` 返回的 `models` 就是那台机器 `/v1/models` 里的 id 列表；
把 `LM_STUDIO_CHAT_MODEL` / `LM_STUDIO_EMBEDDING_MODEL` 改成里面的 id（大小写、连字符都要一致）。

## 4. 安全与「数据不出本地」边界的变化

LM Studio 默认**没有任何鉴权**。开局域网后，同一网段内任何设备都能占用那台机器的 GPU。
- 当前决定：**不开鉴权**，接受边界从「不出本地设备」变成「**不出本地局域网**」。
- 因此硬性要求是：只在受信任的局域网监听，绝不把 1234 端口暴露到公网/路由器；换到公共 Wi-Fi 或公司网络时要关掉 Local Server。
- LM Studio 0.4+ 支持 API Token；将来要启用时把 token 配到 `LM_STUDIO_API_KEY` 即可，代码已经带上 `Authorization` 头，不用改代码。
- **还有一条不在这个项目控制内**：那台机器的 LM Studio `logSensitiveData` 实测是开启的，每次问答的原文与
  提示词都以明文存在它的对话历史里。所以「数据不出本地」的真实口径是「不出这两台机器」。
  合同、台账这类内容放不放进去要单独判断；要收回去就在 LM Studio 设置里关掉历史（本项目不改它的任何设置）。
- 地址是 DHCP 拿的，`192.168.1.61` 不是常量。连不通时先确认地址漂没漂，再看代码；
  开 AP 隔离的 Wi-Fi 会让两台设备根本不通，排查时先换网线。

## 5. 本机实测结论（2026-11-15，`http://192.168.1.61:1234`）

| 项 | 实测 | 对实现的影响 |
|---|---|---|
| 可达性 | 本机 curl `/v1/models` 47ms 返回 200 | 防火墙与 Serve on Local Network 均已就绪 |
| 已加载模型 | `qwen2.5-vl-7b-instruct`、`glm-4-9b-chat-1m`、`google/gemma-3-4b`、`llama-3-patronus-lynx-8b-instruct`、`text-embedding-bge-base-zh-v1.5`、`text-embedding-nomic-embed-text-v1.5` | 当时默认 chat=`qwen2.5-vl-7b-instruct`（**2026-11-16 起改 `glm-4-9b-chat-1m`，理由见 §5.1**），embedding=`text-embedding-bge-base-zh-v1.5`（**注意前缀 `text-embedding-`，早期配置里写的 `bge-base-zh-v1.5` 是错的**） |
| embedding 维度 | 两个 embedding 模型都是 **768** | `RAG_EMBEDDING_DIM=768` 无需改；但维度相同意味着换模型不会被 schema 挡住，靠 ADR-005 的回显校验兜 |
| 批量 | 16 条一批 0.41s；单条 0.04s | `batch-size=16` 有 20 倍余量，入库慢时优先调这个而不是并发 |
| chat 参数 | `temperature` / `top_p` / `max_tokens` 均接受 | `AiConfig` 现有装配安全 |
| 流式 | `stream=true` 正常，106 chunk，首 token 0.46s，`data: [DONE]` 收尾 | M3 的 SSE 链路可行；增量拼接等于完整回答已由 IT 断言 |
| 错误模型名 | **HTTP 200**，回显变成实际加载的模型 | 见 ADR-005；不能只看 HTTP 状态码 |
| chat 模型当 embedding | HTTP 400 `Model is not embedding.` | 报错可直读，无需额外翻译 |
| 空 input | HTTP 200 且返回一个向量 | M2 必须在入库前丢弃空白分块，否则会占位且检索命中噪声 |
| 上下文长度 | `n_ctx=4096`，超限 400：`n_keep: 9625 >= n_ctx: 4096` | 见硬性约束 9；那是**那一次加载**的窗口，第二天复核变成 16384，逐条见 §5.1 |
| `/v1/rerank` | HTTP 200 + `{"error":"Unexpected endpoint or method."}` | LM Studio 没有 rerank 端点，且**用 200 表示失败**；默认关闭重排的判断成立 |
| JDK HttpClient 默认协商 | `GET /v1/models` 永久挂住（同 URL curl 47ms） | 见 ADR-004，客户端已强制 HTTP/1.1 |

## 5.1 2026-11-16 复核：另一份接入规格逐条对账

那份规格是拿同一台机器写的，但结论有几条与咱们的代码或实测不一致。逐条复核，动作写在这一列：

| 规格条目 | 复核结果 | 落地动作 |
|---|---|---|
| chat 用 `glm-4-9b-chat-1m`，`n_ctx=16384` 是硬上限 | 用一条注定超限的请求反读窗口：glm 与 qwen2.5-vl **都回 16384**。glm 0.17s 返回（已驻留显存），qwen 31.3s（现加载）。而咱们配的还是 4096 —— 等于每轮白白少装约 3/4 资料，且不报错 | `RAG_LLM_N_CTX` 默认与 `.env` 改 16384；默认 chat 模型改 `glm-4-9b-chat-1m`（换回只改 `LM_STUDIO_CHAT_MODEL` 一行） |
| 超限是显式 HTTP 400，带 `n_prompt_tokens`，「必须做成可捕获分支」 | 之前只被归进「模型服务不可用」，用户会去重启一个本来就好的服务 | 新增 `ContextOverflow`：413 独立分支、`contextOverflow` 计数、`/api/diagnostics` 回显模型侧真实窗口，`LmStudioConnectivityIT` 加了一条真机窗口探针 |
| 1600 字 ≈ 2400 token（≈1.5 token/字） | 实测 60000 字 = 36005（glm）/ 40019（qwen）token，即 **1 token ≈ 1.5 字**，规格把方向写反了 | `chars-per-token=1.0` 保留并注明它站在「少装」那一侧；改配成 1.5 反而会把预算放大 1.5 倍去撞 400 |
| embedding 训练长度 512 token 是硬约束 | 与 `child-chars=400` 一致，且 `DiagnosticsController` 在 >480 时已告警 | 无需改 |
| 查询侧不要加中文指令前缀 | 代码从来没加（`embed(text)` 原样送），与规格实测「加不加名次一致、相似度掉 0.6→0.51」一致 | 无需改，已有注释防回归 |
| 不建议接重排器 | 全仓 grep 无 rerank 实现与配置项；规格给的实测是 CPU 跑 Lynx-8B、5 候选 11.7s、top-3 与原序完全一致 | M5g 直接否决，`.env.example` 留一行「为什么不做」，别再排期 |
| 「本项目不需要视觉：入库时图片与 PDF 已 OCR 成文本」 | 结论对、**理由错**：`TikaDocumentParser` 明确不做 OCR（扫描件只会得到 `NO_SEGMENT`/`GARBLED_TEXT`）。真实理由是「全链路只往模型发文本，图片从不进模型」 | 按真实理由换模型；同时意味着图片型 PDF 目前不可用，这是产品边界不是配置问题 |
| 不要用 tool_calls / `response_format` | 全仓 grep 两者都不发（答案走纯文本 + 自建引用标记） | 无需改 |
| embedding 的 `usage.prompt_tokens` 恒为 0 | 咱们只读 embedding 的维度与向量，不读 usage | 无需改 |
| 冷启动 chat +16s、embedding +1.5s | 实测冷加载 chat 31.3s。自检类小请求的 read timeout 原来是 15s < 冷加载时间，表现是「服务好好的却报调用失败」 | `SMALL_REQUEST_READ_TIMEOUT` 15s → 45s；生成侧 90s 不变（前端不轮询深检，`withModels` 默认 false） |
| CORS 关着 | 浏览器只访问 rag-api，模型调用全在后端进程；Vite dev 的 `/api` 代理也是服务端转发 | 无需改 |
| `logSensitiveData` 开启 | 属实且不受本项目控制，已写进 §4 的边界说明 | 记入口径：数据不出「这两台机器」 |
| 跨设备真实连通性（规格里标未验证） | 本机 `curl http://192.168.1.61:1234/v1/models` 直接返回 6 个 id，链路通 | 这条从「未验证」划掉 |

## 6. 换 embedding 模型之后怎么收尾


模型换完，`/api/health?models=true` 先确认回显与 `rag.embedding.dim`，再逐库处理：

1. **维度没变（本机两个 embedding 模型都是 768）**：向量空间不互通，老数据必须重算。`GET /api/documents` 拿到 id，逐个 `POST /api/documents/{id}/reindex`。默认复用库里已存的清洗正文，只花 embedding 的钱；只有改了清洗/解析规则或怀疑正文本身有问题才加 `?reparse=true` 回原文件重跑 Tika（见 ADR-008）。
2. **维度变了**：`knowledge_base.embedding_dim` 与 schema 里的 `vector(N)` 绑定，改 `RAG_EMBEDDING_DIM` 后要重建 schema 并全量重算，否则上传直接报「知识库向量维度与配置不一致」——这条报错是设计好的挡板，不是 bug。
3. **慢的话先看批量**：入库卡在 `EMBEDDING` 阶段时调 `RAG_EMBEDDING_BATCH_SIZE`（实测 16 条 0.41s，有 20 倍余量），不要靠 `RAG_INGEST_CONCURRENCY` 堆并发——单台 LM Studio 只会自己排队。

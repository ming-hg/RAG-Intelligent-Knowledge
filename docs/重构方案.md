# RAG 智能知识库问答系统 · 重构基线方案

> 状态：已确认，作为 M0–M6 执行基线。确认日期：2026-11-15
> 旧 Node 实现（`rag-server`）与新栈并行保留，**M6 验收通过后一次性删除**；`rag-web` 重写。

## 1. 项目目标

前后端分离、全本地私有化部署的 RAG 知识库问答系统。对接 LM Studio 本地大模型，支持私有文档上传→解析→语义分块→向量化→混合检索→带引用溯源的精准问答，全程数据不出本机。

## 3. 技术选型

后端：Spring Boot `4.1.2`（最低 JDK 17，注意默认已是 Jackson 3 `tools.jackson`）· LangChain4j BOM `1.23.0` · `langchain4j-open-ai`（手工 `@Bean` 装配，**不用 spring starter**，避免与 Boot 4 的额外耦合）· `langchain4j-pgvector` · `langchain4j-document-parser-apache-tika`（锁 Tika 3.3.3）· Flyway · Testcontainers。

前端：Vue 3.5 + Vite + TypeScript + Pinia（持久化插件真正装上）+ vue-router + Element Plus + axios + markdown-it + highlight.js + **DOMPurify**。

模型服务：LM Studio（OpenAI 兼容，`baseUrl` 必须含 `/v1`，默认免鉴权、key 填占位串）。
- `/v1/chat/completions`、`/v1/embeddings`、`/v1/models` 可用；**无 `/v1/rerank`** → 重排走本地 ONNX。
- `OpenAiEmbeddingModel.maxSegmentsPerBatch` 默认 2048，对本地模型必然超时/OOM，**默认改 16 且可调**。

## 4. 架构

```
浏览器 ──Vite 5173 / Nginx 80──▶ rag-api :8080 ──┬─▶ PostgreSQL :5432（pgvector + zhparser）
                                                  ├─▶ LM Studio :1234（chat / embeddings）
                                                  └─▶ ./storage（原始文件与导出物）
```

分层：`web`（Controller/SSE/统一响应与异常）→ `app`（用例编排）→ `domain`（模型与状态机，纯 Java）→ `rag`/`ingest`（分块、检索、融合、重排、Prompt、解析）→ `infra`（LangChain4j 装配、JDBC 仓储）。

刻意不引入：Redis、MQ、Elasticsearch。任务队列用 PG 表 + `FOR UPDATE SKIP LOCKED` + 租约字段（`lease_owner/lease_until`）+ 线程池 Worker。理由：单人本地场景引入 MQ 只增加运维面不增加能力。

## 5. 功能范围

P0（18 项，全部实现）：多知识库；PDF/DOCX/MD/TXT/XLSX/CSV/PPTX/HTML + 手工录入 + URL 抓取；sha256 去重；中文 PDF 乱码检测报错；文档重解析与版本蓝绿切换；三种分块模式（通用/父子/按标题）；分块预览与人工编辑、块级禁用；异步流水线状态机 + 进度 SSE + 指数退避重试 + 手动重训；embedding 批处理；模型与维度绑定不可混改；混合检索 + RRF；三级检索配置（全局→库→请求）；元数据过滤；查询改写；召回测试面板；段落级 `[n]` 引用溯源 + 空召回兜底不调 LLM；SSE 流式 + 停止 + 重新生成 + 多轮上下文 + 点赞点踩。

P1：评测集跑分（hit@k / MRR / 空召回率）、检索与问答日志 + CSV 导出、知识库导入导出、设置热生效。

不做：工作流/Agent 编排、GraphRAG/RAPTOR、自研 OCR 版面、飞书/语雀/Notion 同步与爬虫、多租户权限、多模态、WebSocket、对外发布渠道。

## 6. 文档处理状态机

`PENDING → PARSING → SPLITTING → EMBEDDING → INDEXING → READY`，任何阶段可分支 `FAILED`。
重试与重新入库都回到 `PARSING` 重走一遍（`FAILED → PARSING`），非法迁移在写库前抛错，进度字段 `progress/progress_msg` 与状态同一条 UPDATE 落库。
早期方案里的 `STALE` 不再单列状态：旧索引继续可检索这件事由 `doc_version` 代次 + `available` 开关保证（见 ADR-007），状态字段只管「这一代走到哪了」。

## 7. 已知硬性约束（实现时不得违反）

1. **RRF 分数量纲**：融合得分约 `0.016–0.033`，绝不能沿用纯向量的 `minScore≈0.6`。阈值字段按检索模式分离。
2. **pgvector 索引维度上限 2000**（`vector` 类型），超 2000 维模型需 `halfvec`。
3. `PgVectorEmbeddingStore` 自动建的是 **IVFFlat**，HNSW 必须用 Flyway migration 手工建；GIN 全文索引仅在 `createTable=true` 时自动建，改表后需手工补。
4. HYBRID 模式要求 `EmbeddingSearchRequest.query()` 非空，且 `text` 列必须写入原文。
5. PG 原生 parser 对中文不分词，中文全文检索必须走 zhparser/pg_jieba 自定义 text search configuration。
6. 检索谓词固定包含 `segment.available AND doc.status=READY AND index_version=当前版本`。
7. **对 LM Studio 的 HTTP 客户端必须锁 HTTP/1.1 且设死超时**，RestClient 与 LangChain4j 两条路都要（实测默认 JDK HttpClient 的 h2c 升级请求会让 `GET /v1/models` 永久挂住，同 URL 用 curl 47ms 返回）。
8. **LM Studio 对认不出的模型名不报错**：传错 id 仍返回 200，并用当前已加载的模型应答；且 `text-embedding-bge-base-zh-v1.5` 与 `text-embedding-nomic-embed-text-v1.5` 同为 768 维，维度校验挡不住静默换模型。任何向量写入前必须已完成 `/v1/models` + 响应回显双重比对。
9. **`n_ctx` 是「这一次加载」的属性，不是模型的属性**：同一台 192.168.1.61 上，2026-11-15 实测加载出 4096（超限报 `n_keep: 9625 >= n_ctx: 4096`），2026-11-16 两个 chat 模型都加载出 16384。装配预算必须按 `n_ctx - 回答预留 - 提示词模板` 收口；超限不会被静默截断，而是 HTTP 400 明确拒绝（响应体带 `n_prompt_tokens` 与 `n_ctx`），`ContextOverflow` 把它单独收成 413 并回显模型侧真实窗口。模型服务不提供查询窗口的端点，只能这样反推。
10. **子块 400 字是模型窗口上限，不是排版偏好**：bge-base-zh-v1.5 在 512 token 处静默截断，中文约 1 字 1 token。调大 `rag.ingest.chunk.child-chars` 不会让模型多看一点，只会让超出部分不进向量。
11. **`'\f'`（U+000C）必须活过清洗并独占一行**：PDF 页码完全靠它定位。`TextCleaner` 早期把 U+000C 当控制符删掉，结果所有块都记成第 1 页且不报错。
12. **Tika 3.3.3 的纯文本输出里没有任何分页标记**（实测）：页结构只在 XHTML 事件的 `<div class="page">` 上，页数在 `xmpTPg:NPages`。`BodyContentHandler(-1)` 之后按字符串切是拿不到页码的，所以解析直接消费 SAX 事件。
13. **分块偏移量只有一个基准**：`ChineseSemanticSplitter.offsetBase(清洗后正文)`。`kb_segment.char_start/char_end` 与 `GET /api/documents/{id}/content` 必须同源，否则引用高亮整体错位且不报错。

## 8. 风险与退路

| 风险 | 退路 |
|---|---|
| zhparser 对 PG17 官方支持不确定（口径到 16） | 退 PG16 镜像；再不行 `pg_trgm` 子串相似度；最后纯向量 + rerank |
| ONNX rerank 在 Windows 缺 VC++ Redistributable | 默认关闭；开启时给明确自检与提示 |
| Boot 4.1 + Jackson 3 与三方依赖冲突 | 退 Boot 4.0.x 同 GA 线 |
| LM Studio 批量 embedding 上限官方未公布 | 实测 16 条一批 0.41s、单条 0.04s；batch 16 起步，报错信息直接指向该参数 |
| 已加载模型的 `n_ctx` 说不准（实测过 4096 也实测过 16384），超限直接 400 | 按 `n_ctx` 预算装配；超限单独成 413 分支并回显模型侧真实窗口，`/api/diagnostics` 报「配置比实测小」；要更长时在 LM Studio 调大 context，而不是偷偷截断 |
| 中文 PDF CID 字体乱码不可逆 | 检测 + 报错 + 提示用户换解析器，不静默入库 |
| 本机 PATH 里 `node` 解析到 18.20.2 | 用 nvm 已装的 22.20.0；必要时显式路径调用 |

## 10. 执行中的架构修正（ADR）

**ADR-001：不使用 `PgVectorEmbeddingStore`，改为自建 JDBC 仓储 + 自写混合检索 SQL。**
发现于 M0 落地阶段。LangChain4j 的 store 会独占它那张表的 schema 约定（`id/embedding/text/metadata`），无法表达 P0 需要的 `doc_id`/`chunk_no`/`doc_version`/`page_start`/`available`/`parent_id`/`hit_count` 等列，也就无法实现「块级禁用」「版本蓝绿」「页码级引用」「命中次数统计」。
做法：保留 LangChain4j 的模型层（`ChatModel`/`StreamingChatModel`/`EmbeddingModel`/Tika 解析/未来的 rerank `ScoringModel`），检索 SQL  ourselves 写——单条 CTE：向量路 `ORDER BY embedding <=> ?` + 关键词路（`chinese` tsvector 或 `pg_trgm`）+ RRF `1/(k+rank)` 融合，与 store 内部实现同构，但谓词完全可控。
代价：检索层多约 1 人日；收益：P0 第 6/7/11/12/14 项全部可实现。
已核实并沿用的约束：HNSW 必须手工建（store 只建 IVFFlat）、RRF 分数量纲、`ORDER BY 操作符` 才走索引。

**ADR-002：embedding 维度是 schema 级全局约束，通过 Flyway 占位符注入。**
`kb_segment.embedding vector(${embedding_dim})` 与 `rag.embedding.dim` 同源（同一环境变量），启动时 `/api/health` 校验库内已存 `embedding_model` 与配置是否一致，混用即报 DEGRADED 并提示全量重算。多库不同维度的隔离留给「导出/导入 + 重建」路径，不做动态建表。

**ADR-003：中文全文检索三级降级。**
`chinese(zhparser)` → `pg_trgm` 子串相似度 → 纯向量 + rerank。三级都在同一份 SQL 里按能力探测分支，健康检查明确报告当前处于哪一级，避免用户以为召回差是模型问题。

**ADR-004：LM Studio 客户端统一强制 HTTP/1.1 + 显式超时。**
发现于 M1 真机联调（`192.168.1.61:1234`）。`java.net.http.HttpClient` 默认协商 HTTP/2，明文端口上先发 h2c `Upgrade` 请求；LM Studio 不响应升级，请求既不报错也不返回，`CompletableFuture.get()` 无限等待——表现为「健康检查卡住 / 入库线程池耗尽」，而不是任何可诊断的异常。
做法：`LmStudioHttpClient` 集中产出 `HTTP_1_1` + `connectTimeout=5s` 的 builder，RestClient 侧注册为 `ClientHttpRequestFactory` bean，LangChain4j 三个模型 bean 统一 `httpClientBuilder(...)`，读超时取 `rag.lm-studio.timeout`。
验证：`LmStudioConnectivityIT`（`LM_STUDIO_IT=true mvn verify` 打开）修复前挂死 10 分钟被 fork 超时杀掉，修复后 3 个用例 2.5s 全绿。

**ADR-005：模型名不能只信配置，要信回显。**
实测 LM Studio 传未知模型 id 返回 200 并用已加载模型应答，`model` 字段才反映真实服务者。`/api/health` 新增两个探测：快探测 `modelIds`（配置名是否在 `/v1/models` 列表内，不在则 DOWN 并挡住 ready，因为此时写库就是往向量空间里灌错模型产物）；深探测 `modelEcho`（`models=true` 时比对 embedding/chat 响应回显）。模型服务单纯不可达只报 DEGRADED，不挡 ready——本机常见的是先起 API 再起 Local Server。

**ADR-006：Boot 4 的 autoconfigure 拆包必须用 starter 表达。**
Boot 4.1 把各技术栈自动配置拆成独立模块，`spring-boot-starter-web` 不再提供 `RestClient.Builder`，只引 `flyway-core` 则迁移根本不执行（`spring.flyway.placeholders.embedding_dim` 被静默忽略，schema 建不出来）。已改用 `spring-boot-starter-flyway` + `spring-boot-starter-restclient`，并加 `RagApiContextTest` 作为不依赖数据库与模型服务的装配门：少引一个 starter 会当场表现为 bean 缺失，而不是等到连库时才发现。

**ADR-007：索引切换是「代次 + available 开关」，且整条切换只有一个事务。**
发现于 M2 设计阶段。重新入库时旧索引必须继续可检索，直到新一代全部写完；分批放开会让一次崩溃留下半新半旧的召回结果。
做法：`doc_version + 1` 作为新一代写入，行默认 `available=false`；写完父子链接后在同一个事务里放开新一代、删除其余代次、把 `kb_document` 置 READY。放开前有一条守卫——只要有可检索块缺向量就拒绝切换并报 `有 N 个可检索块没有向量`。
崩溃面：worker 启动时 `reapExpiredLeases()` 回收过期租约，`IngestStartupRecovery` 把仍在入库中的文档置 FAILED 并给出「可直接重试」的文案；正常退出 `@PreDestroy` 归还自己持有的租约，不让下一次启动等 10 分钟。

**ADR-008：清洗后的正文进 `kb_document.content`，重新分块默认不再碰原文件。**
真正花钱的是 embedding，不是 Tika。`V1` 里新增 `content` 列（保留 `'\f'`），入库时落一次；`reindex` 复用库内正文，`POST /api/documents/{id}/reindex?reparse=true` 才回原始文件重跑解析。
约束：偏移量基准是 `offsetBase(content)`（`'\f'`→`'\n'`，等宽替换），所以复用正文与首次入库的 `char_start/char_end` 完全一致；页码仍从带 `'\f'` 的正文算，因此存的一定是清洗后、未做等宽替换的那一份。

**ADR-009：永久失败与临时失败分开记账。**
`GARBLED_TEXT`、`NO_SEGMENT`、`DIM_MISMATCH`、`DOC_GONE` 重试一万次也是同样结果，直接抛 `PermanentIngestException` → 任务 `abandon`（不再排队）+ 文档 FAILED 带错误码；只有网络抖动、模型服务未起这类才走指数退避（5s 起，`attempt` 每加一次翻倍）并消耗 `max-attempts`。
理由：一个扫描件 PDF 烧掉整份重试预算，会让后面排队的正常文档跟着排队等待，而本地机器最缺的就是这种无意义等待。

## 11. M2 交付面（接口与配置）

接口：`POST /api/documents`（multipart，同库同 sha 直接复用不重复消耗 embedding）、`GET /api/documents`、`GET /api/documents/summary`、`GET /api/documents/{id}`、`GET /api/documents/{id}/segments`、`GET /api/documents/{id}/content`、`GET /api/documents/{id}/chunks/preview`（按参数重切预览，不写库不调模型）、`PATCH /api/documents/{id}/segments/{segmentId}?available=`（块级禁用/恢复，WHERE 里带 doc_id 防越权）、`POST /api/documents/{id}/reindex?reparse=`、`DELETE /api/documents/{id}`、`GET /api/knowledge-bases`。

`preview` 的参数边界与 `ChunkConfig` 一致，越界一律 400 并回显四个值——让 `ChunkConfig` 直接抛 `IllegalArgumentException` 会变成 500，把用户填错参数说成服务故障。

配置（全部有可直接跑的默认值，环境变量前缀 `RAG_INGEST_`）：

```yaml
rag:
  ingest:
    worker-enabled: true      # false 只入队不起线程，便于单独调试 worker
    poll-interval: 2s
    lease-duration: 10m
    max-attempts: 3
    concurrency: 1            # 本地单模型服务，>1 只会让 LM Studio 排队
    max-file-size-mb: 100
    allowed-extensions: [pdf, docx, doc, md, markdown, txt, csv, json, html, htm]
    chunk:
      child-chars: 400        # 见硬性约束 10，别超过 512 token
      child-min-chars: 120
      overlap-chars: 60       # 重叠按整句给，可能略大于该值
      parent-max-chars: 1200
      parent-child: true
```

状态机、分块、清洗、解析、编排、落盘六层都有不依赖数据库的单测（`mvn -o test`，78 例）；连库的 M2 验收用例已经写完（`IngestPipelineIT`：蓝绿切换、偏移量回放、页码、租约回收、SKIP LOCKED 不重发、退避到上限、永久失败不占额度），Docker 一起来用 `mvn -o verify` 一次跑完。

尚未实现的 M2/P0 相邻项，留给后续里程碑：进度 SSE（当前前端轮询 `progress`）。人工编辑块内容与单块重算向量已在 M5b 落地，见 §16；按文档覆盖分块参数已在 M5c 落地，见 §15。

**ADR-010：检索阈值是「生效模式」的属性，不是请求模式的属性。**
RRF 分数量级只有 `1/(60+1)≈0.016`，余弦相似度是 0–1，两者绝不能共用一个阈值：`min-score: 0.45` 套在混合检索上会把命中一刀切光，反过来 rrf 阈值套在纯向量上等于不设限。做法：阈值选择落在 `RetrievalMode.effectiveThreshold(minScore, minRrfScore)`，并且取降级之后真正执行的那一路——LM Studio 挂掉自动退化为纯关键词时，用的是关键词阈值而不是用户请求的向量阈值。
连带决定：pg_trgm 分支额外设绝对下限 `word_similarity >= 0.25`。RRF 只给名次不给绝对分，纯关键词检索时不砍尾巴，第 40 名的噪音会和第 1 名一起进上下文；`chinese` tsvector 分支不需要它，因为词匹配本身是二值的。

**ADR-011：范围谓词写进每一路召回自己的 WHERE，不物化 scope CTE。**
`WITH scope AS (SELECT id FROM kb_segment WHERE ...)` 再让向量路子查询去 join，HNSW 索引对上层查询不再可见，`ORDER BY embedding <=> ? LIMIT k` 退化成全表精算——库里上万块以后是几十倍延迟，而且不报错。做法：每条召回路子查询各自持有 `kb_id / doc_id / s.available / d.available / d.deleted_at`，融合层只做 FULL OUTER JOIN 与排序截断。
也因此 SQL 用命名参数（`NamedParameterJdbcTemplate`）拼装：同一段范围过滤要在两条路里各写一遍，位置参数一旦调换顺序就会把向量塞进关键词槽位，同样不报错、只出脏结果。补充两条 pgvector 约束：比较式写成 `索引列 <=> CAST(:v AS vector)` 且索引列在左侧；SQL 里出现 `::vector` 会被 Spring 误认成参数名。

**ADR-012：上下文预算按字符算，不按 token 算。**
本地拿不到与模型严格对齐的 tokenizer（LM Studio 不会把真实分词回传），中文在主流 chat 模型里实测 1 token ≈ 1.5 字，`chars-per-token: 1.0` 因此是故意保守——宁可少给两块资料，也不让请求超出 `n_ctx`。
超窗口不是静默丢中间（这是我早先的假设，实测推翻了）：引擎会显式回 HTTP 400，响应体带 `n_prompt_tokens` 与 `n_ctx`。
所以两条路都留着——预算负责尽量不撞，`ContextOverflow` 负责撞了以后给出 413 并回显模型侧真实窗口，而不是笼统的「模型不可用」。
预算 = `n_ctx×charsPerToken − 预留输出 − 模板 − 历史`，历史从最新往回按轮数和字符数双重截断（`REFUSED` 的空回答不占预算）。装配结果（used/budget/unplacedHits/truncated）随 `retrieval_meta` 落库并在 SSE `meta` 事件里回给前端——截断必须可见，否则引用编号会让人误以为资料就给这么多。

**ADR-013：问答的崩溃语义是「先落库，再流式」。**
`chat_message` 在生成之前写两行（question + `status=STREAMING` 的 answer）；浏览器断开不中断生成（`SseSink` 吞掉写失败，让答案照常落库，否则用户刷新后一无所获）；模型中途报错把已生成的部分存为 `INTERRUPTED` 而不是丢弃；空召回直接 `REFUSED` 且零模型调用，不进提示词。引用编号在生成时分配并连同 `sources` 一起持久化，永不重算——重算会让历史消息里的 `[3]` 悄悄指向另一份资料。
SSE 走 Spring MVC `SseEmitter`（不引 WebFlux），工作提交到独立的 `chatExecutor`（4 线程 / 队列 8 / 10 分钟超时）：与入库 worker 分开是因为这里排队的是模型推理，混在一起一次长问答会把入库进度饿死；队列打满直接回 `error 503 并发问答已达上限`，而不是让请求在内存里无限堆。

**ADR-014：前端删掉 axios 与 EventSource，请求层只剩 fetch。**
问答是 POST + `text/event-stream`，浏览器原生 `EventSource` 既不能 POST 也不能带 JSON 体，硬用就得把问题塞进 URL 或改成长连接的 GET，两条都不如按规范自己切帧干净（`src/api/sse.ts`）。axios 的拦截器在这里只剩「弹一个全局 loading」，而问答页的等待态是逐字吐字、文档页是进度条，全局遮罩反而挡住正在发生的事，所以连同 `event-source-polyfill`、`uuid` 一起删除。信封解析统一走一处：非 200 或 `code != 200` 抛 `ApiError` 并带上 `traceId`，两个例外（health 的 503 报告、knowledge-bases 的默认库回显）走 `requestEnvelope` 拿完整信封。「停止接收」的语义单独处理：`AbortController` 断开后 Chrome 在读流中途抛错，只有 `signal.aborted` 为真时才算预期停止，界面标「已中断」而不是「失败」。

**ADR-015：反馈写入用 null 表示「不改」、空串表示「清空」，订正后的答案成为后续问答的事实。**
PATCH 类接口最容易出的错是「只点了一下 👍，把上次写的反馈文字抹了」。规则定在 SQL 里而不是 Java 分支里：三个字段各自 `COALESCE(CAST(:x AS …), x)`，缺席即保留。撤销评分走 `rating = 0`（中性），不额外开删除接口；清空文字走显式空串。守卫 `role = 'assistant'` 写进 WHERE，更新 0 行统一报 404——「消息不存在」和「那是用户自己说的话」都不该假装记录成功。
订正一旦存在就顶替模型原文进入下一轮历史（`Message.contextText()`）：改完还继续喂旧文本，等于让模型反复引用自己那句错话。界面同步这个语义——正文显示订正版本，模型原文折叠在「查看模型原文」里，两者都能拿到。

## 12. M3 交付面（接口与配置）

接口：`POST /api/search` 与 `GET /api/search?q=&kbId=|kbIds=&docIds=&mode=&topK=`（只检索不生成，来源面板与调参用）、`POST /api/chat/ask`（SSE，事件序列 `meta → delta* → done|error`）、`POST/GET /api/chat/sessions`、`GET /api/chat/sessions/{id}/messages`、`PATCH /api/chat/sessions/{id}?title=&pinned=`、`DELETE /api/chat/sessions/{id}`。

两条硬边界：检索与问答必须显式给 `kbIds` 或 `docIds`，否则 400——本地机器上「全库检索」听起来方便，实际是把无关库的资料塞进上下文并逼模型编造衔接；`topK` 上限 50、`mode` 只接受 `vector|keyword|hybrid`，越界一律 400 并回显可选值。

问答这条 400 在 2026-11-16 的真机跑之后才真正算落地：实现里一度留有「没给范围就查默认库」的兜底，与前端自己的注释相反，而答案里看不出资料来自哪一层范围。现在 `ChatController` 在建 `SseEmitter` **之前**调 `ChatService.requireScope`，`ask()` 内部再按同一套规则复算一次（两处共用 `scopeKbIds`，不存在校验与执行规则分裂）——起流之前就定得下来的错回 JSON 信封，不回事件流里的 `error`，否则前端只看到一个立刻断掉的流，和「服务炸了」在现场完全同形。代价是错误信封的 `Content-Type` 必须写死：客户端带着 `Accept: text/event-stream` 来，内容协商的结果是「只能吐事件流」，于是 400 变成没有 body 的 500，§7.4 那套按 content-type 分支的逻辑整段没机会跑。

`meta` 事件带全部可观测字段：请求模式与实际生效模式、当前关键词引擎及其说明、是否降级与向量路失败原因、每条来源的 `citation / vectorRank / keywordRank / rrf / similarity / parentExpanded / chars`，以及预算用量。降级和截断在这里可见，不再只体现在「答案质量忽然变差」。

配置（全部有可直接跑的默认值，环境变量前缀 `RAG_RETRIEVAL_`、预算侧 `RAG_LLM_N_CTX`）：

```yaml
rag:
  retrieval:
    mode: hybrid              # vector | keyword | hybrid
    top-k: 6
    candidate-k: 40           # 每路先取多少候选再融合
    rrf-k: 60                 # 改它等于改「第一名值多少」
    min-score: 0.45           # 只在纯向量生效
    min-rrf-score: 0.012      # 只在混合/关键词生效，量纲与上面完全不同
    parent-context: true      # 子块命中后展开为父块正文
    budget:
      n-ctx: 16384            # 必须与 LM Studio 实际加载的窗口一致（用 §实测指导 §3 的 curl 量出来）
      output-reserve-tokens: 700
      template-chars: 900
      chars-per-token: 1.0
      history-max-turns: 4
      history-max-chars: 800
```

纯逻辑（阈值语义与模式降级矩阵、预算装配与父块去重、引用编号、历史截断、配置边界）由 4 个不依赖数据库的单测类覆盖；检索 SQL 另有一层字符串级契约测试 `RetrievalSqlTest`（8 例），专门钉住只有连库才会暴露的四件事：每个分支的命名参数与占位符严格一一对应、范围谓词留在召回路内部（否则 HNSW 不可见）、阈值列跟着生效模式走、语句里不出现 `::` 简写转换。`mvn -o test` 共 124 例全绿。检索 SQL 的排名、RRF 算术、作用域过滤、pg_trgm 下限、父块无向量仍可达、命中计数由 `RetrievalIT`（14 例，Testcontainers）覆盖，Docker 未起时按既有约定干净跳过。与 M2 的蓝绿切换无冲突：检索谓词只有 `s.available AND d.available AND d.deleted_at IS NULL`，旧代次块已在切换事务里删除，因此不需要 `doc_version` 谓词——放开新一代与删除旧代次是原子的，检索不会看到两代并存。

留给后续里程碑：rerank 开关（默认关，M5）、入库进度 SSE（当前轮询，M4 需要时再换）。回答评分与反馈闭环已在 M5a 落地，见 §14；按文档覆盖分块参数 `chunk_override` 已在 M5c 落地，见 §15；单块人工编辑与单块重算向量已在 M5b 落地，见 §16。

## 13. M4 交付面（前端与契约）

技术栈：Vite 8 + Vue 3.5 + TypeScript 5.7（`vue-tsc` 严格模式）+ Element Plus 2.13 + Pinia 3（作用域与会话 id 落 localStorage）+ markdown-it + highlight.js（按需注册语言，不引全量包）。旧 `rag-web` 的 axios 与 `event-source-polyfill` 全部删除：请求层换成原生 fetch，SSE 换成自研分帧。

**契约层。** `src/types/api.ts` 是后端 record 的逐字段镜像，也是两侧之间唯一的契约文档——跨进程字段不匹配 `vue-tsc` 查不出来，所以后端改 record 必须同步这里。两个接口故意不走「非 200 即抛错」的默认信封：`/api/health` 的 503 报告本身就是要显示的数据，`/api/knowledge-bases` 把默认库 id 放在 `message` 里回显。

**流式。** 问答必须是 POST，浏览器原生 `EventSource` 只能 GET 也带不上 JSON 体，因此按 SSE 规范自己切帧（空行分帧、多行 `data:` 以 `\n` 拼接、冒号后的一个空格不属于值、断线时把残尾帧也交付）。后端所有事件载荷都是 JSON，`delta` 形如 `{"text": "…\n…"}`，换行在 JSON 字符串里是转义序列，所以正文中的 `\n\n` 不可能把帧切坏。不做自动重连：一次回答是一段推理，重连等于让模型把同一个问题再答一遍。

**页面与深链。** `/chat`（会话列表 + 正文 + 引用面板三栏）、`/documents`（列表 + 抽屉详情：分块 / 正文 / 分块预览）、`/search`（名次、RRF、相似度、引擎与降级原因）、`/settings`（分层自检 + 知识库表 + 只能改配置文件的项）。`/documents?doc=&segment=` 是可分享深链：问答页点引用编号高亮对应来源，点文档名跳过来并把那块高亮滚动到视野中间。

**状态。** 作用域（kbIds/docIds/mode/topK）在 `ui` store 里持久化并被问答、检索、文档三页共享；`chat` 只持久化 `activeId`；入库中的文档由 `documents` store 以 2 秒轮询驱动，队列空了自动停。入库进度没有换成 SSE：轮询已经够用，且换成 SSE 会让「同时看多个文档进度」变成多条长连接。

**窄屏。** 三栏里两侧是固定宽度，窗口一窄就会把正文压成 0 宽：≤1080px 收窄侧栏，≤860px 改成纵向叠放并整体滚动，正文始终保留最小高度；文档抽屉宽度用 `min(720px, 100%)`。

**验收。** `npm run typecheck` 与 `npm run build` 全绿。数据库与模型未起，因此用一份按 `types/api.ts` 契约写的临时 mock 服务（放在仓库外）在浏览器里跑通：SSE 逐字渲染与 markdown/代码块、引用编号点击联动来源面板、来源→文档深链与块高亮、停止接收（中断只断显示，界面标「已中断」并保留半截正文）、分块参数重切预览、块级检索开关的乐观更新与失败回滚、上传后自动进入轮询、自检的 UP/DEGRADED 分层报告。真实后端联调留给虚拟化打开之后一起做。

## 14. M5a 交付面（回答评分 / 反馈 / 人工订正）

`chat_message` 的 `rating`、`feedback_text`、`annotated_answer` 三列在 `V1` 里就已就位，本里程碑不加迁移，只把这三列接成一条能用的闭环。

接口：`PATCH /api/chat/messages/{id}`，请求体 `{rating?, feedbackText?, annotatedAnswer?}`。三者全缺 → 400；`rating` 只接受 `-1 / 0 / 1`，越界 400 并把收到的值写回消息；`feedbackText` 上限 2000 字、`annotatedAnswer` 上限 20000 字，超长 400 并报出「最长 N 字，当前 M」。写 0 行（消息不存在，或它是 user 行）→ 404。

服务层：`ChatRepository.setFeedback` 用 `COALESCE(CAST(:x AS …), x)` 逐字段保留未提交的列，`WHERE … AND role = 'assistant'` 挡住给人类消息打分；`Message.contextText()` 让订正文本优先于模型原文，`ChatService` 的三处历史入口（用量估算、`trimHistory`、`toChatHistory`）统一走它，因此「改完再问」下一轮引用的就是订正版。PG 的 `smallint` 经 JDBC 读回来是 `Short`，映射用 `rs.getObject("rating", Integer.class)`，直接强转 `Integer` 会在运行期 CCE。

前端：`FeedbackBar.vue` 挂在每条模型回答下面——👍/👎 就地评分（同键再点一次发 0 撤销），「反馈与订正」开对话框预填现有值，保存时两个字段一律按字符串提交（清空 = 空串 = 撤销），拒答行没有可订正的产出、对话框只留反馈框并说明评分仍计入拒答正确率。正文显示 `annotatedAnswer || content`，模型原文折叠在「查看模型原文」里。`http` 层新增 `patchJson`：会话改名走查询参数，消息反馈必须走 JSON 体，因为字段要用 null 与空串区分两种意图，查询参数表达不了「这个键没传」。

测试：`ChatFeedbackSqlTest`（6 例，不连库）钉住占位符与绑定值一一对应、`role = 'assistant'` 守卫存在、三个 COALESCE 都在、不出现 `::` 简写、写入列与读取列一致；`ChatFeedbackApiTest`（6 例）覆盖空 PATCH、评分越界、缺席字段以 null 下发、空串原样落库、超长拒绝、0 行报 404；`ChatServiceTest` 新增 `annotatedAnswerReplacesTheModelOriginalInFollowingTurns`。`mvn -o test` 共 137 例全绿。浏览器侧用临时 mock 验证：点 👍 只改评分不动反馈文字、订正保存后正文立刻换成订正版、清空反馈后引用条消失、刷新后状态从库里读回、拒答行只显示反馈框。

后续 M5e 直接吃这条闭环：`rating = -1 AND annotated_answer IS NOT NULL` 的行就是「人已经给出正确答案」的评测样本，不需要另建标注表。

**ADR-016：分块覆盖存「差异」而不是「快照」，校验放在合并之后。**
取值是三层：请求参数 > 本文档覆盖 > 全局 `rag.ingest.chunk.*`。逐键回退（`orElse`）而不是整份替换——用户只想改子块长度时，其余四项若跟着请求里那份前端默认值走，会被静默重置成界面抄的那份配置。
库里只存与全局不同的键（`deltasAgainst`），全等就写 NULL：整份抄一遍，改了全局默认覆盖追不上，列里躺着的是一坨过期快照，而且再也分不清「没设过」和「设得和默认一样」。
校验必须发生在合并之后（`merged()` 里报 400），而不是让 `ChunkConfig` 抛 `IllegalArgumentException`：单看请求值合法、配上全局值才不可能的组合（`overlap=500` 配全局 `child=400`）不在这里挡，接口就是 500；入库路径不在这里挡，一个手工改坏的覆盖会每天打死一个 worker 再退避重试，日志里只留下一句看不懂的分失败。库里读回的坏 JSON 同样不退化成异常，而是「没有覆盖」加一条 warn——解析失败的正确处理是回到默认，不是让这篇文档永远入库不了。
覆盖只改「下次怎么切」，不动已入库的那一代：立刻按新参数重切会让正在被引用的 `chunk_no / char_start` 集体错位，历史答案里的 `[3]` 悄悄指向另一段文字。所以保存后界面固定说「重新入库后生效」，真正生效的入口留在列表的「重算」。

## 15. M5c 交付面（文档级分块参数覆盖）

接口：`GET /api/documents/{id}/chunk-config`、`PUT /api/documents/{id}/chunk-config`。PUT 是整份替换，五个键全给，`null` 即「这项跟随全局默认」；两个接口返回同一个 `ChunkConfigView = {override, defaults, effective}`——只回 `override` 的话，界面得自己再实现一遍合并规则，两边各算各的迟早飘。

入库与预览都走这份合并结果：`run()` 用 `overrideOf(doc).merged(global)` 分块，并把真正生效的字数写进进度文案（`语义分块 子块 260 / 父块 900 字`），出问题时代码里日志里都有同一组数；`preview()` 多带一层请求参数，试参数仍然不用先保存。

无新增配置键（仍是 `rag.ingest.chunk.*`，环境变量前缀 `RAG_INGEST_CHUNK_`），无新增迁移：`V1` 里的 `chunk_override jsonb` 首次被读，只补了一句列注释——本机虚拟化还没开，这个文件尚未在任何数据库上执行过，因此不存在 Flyway 校验和冲突。

测试：`ChunkOverrideTest` 11 例（读空与读坏、只存差异、逐键回退、合并后才越界、六组非法组合）＋ `IngestServiceTest` 新增 6 例（入库用本文档覆盖、预览的三层顺序、坏 JSON 退化成全局、落库只写差异、0 行报 404），`mvn -o test` 共 154 例全绿。

前端：分块预览的表单从 `effective` 起，不再在前端抄一份默认值；控件上下限与后端约束对齐（子块 50–4000、父块 50–4000），新增「存为本文档覆盖」「恢复全局默认」两个动作和「这篇文档有自己的覆盖 / 跟随全局默认」标签，`http` 层补 `put`。浏览器侧用契约 mock 验证：标签随状态切换、恢复默认后表单立刻回到全局值、非法组合由后端 400 回显四个值与约束原文（含超过 400 字会被 512 token 窗口静默截断那句）、刷新后表单读回库里存的生效值。

**ADR-017：单块编辑是「正文改了、旧向量当场作废」，不是「向量重算成功才算保存成功」。**
整篇重算的代价是几十秒到几分钟的 embedding，而用户想改的往往是一个被解析弄乱的表格或一句错别字——用整篇重算来换一处文字，代价高到没人愿意用，于是错块一直留在库里污染检索。单块编辑必须连带把这条的向量置 NULL：留着旧向量，检索会按用户已经看不到的那段文字排序，答案里的 `[3]` 指向一段并不存在的依据，这是最难复现的一类「答案时好时坏」。
但向量算不出来不能把主操作判成失败：正文保存是用户点这一步的唯一目的，模型服务不在线时返回 502 只会让人以为改动丢了、再点一次、再撞同一个错，而文字其实早就存下了。所以是 200 + `embedded:false` + 一句 `note`，说清「关键词检索已经能用这一条」，并把补算的入口（`重算向量`）留在界面上。`note` 走返回体不走信封 `message`——前端的 `requestJson` 只把 `data` 交给调用方，`message` 会被丢掉。

## 16. M5b 交付面（单块人工编辑 / 单块重算向量）

接口：`PUT /api/documents/{id}/segments/{segmentId}/content`（体 `{content, reembed}`，`reembed` 缺省为 true）、`POST /api/documents/{id}/segments/{segmentId}/reembed`。两者返回同一个 `EditResult = {segment, embedded, note}`；`segment` 是改完再读回的那一行，前端整行替换而不是只 patch 正文，`emb_status`／`edited` 的新状态跟着后端走。

迁移只有一句：`V1` 的 `kb_segment` 加 `edited_at timestamptz`（本机虚拟化仍未开，该文件尚未在任何库执行过，无 Flyway 校验和冲突）。`SegmentView` 多一个 `edited` 布尔，由 `edited_at IS NOT NULL` 折算——不把时间戳推给前端，界面只需要知道「这条和原文不一样了」，而 `char_start/char_end` 描述的永远是编辑前的位置，这句话得有个地方说。

三条语义是钉在一起才成立的：
1. 改正文与置空向量在同一条 UPDATE 里（`embedding = NULL, emb_status = 'PENDING'`），父块例外——`emb_status` 用 `CASE` 保住 `SKIPPED`，给父块算向量既错又会让 `onlySearchable` 把它当成检索命中块。
2. 关键词路不需要额外动作：`content_ts` 是 `GENERATED ALWAYS … STORED` 生成列，改正文时 PG 自己重算；向量路过滤的是 `s.embedding IS NOT NULL` 而不是 `emb_status`，所以置 NULL 的那一刻这块就自动退出向量召回。两条路各走各的，不会出现「关键词搜到新文字、向量搜到旧文字」。
3. 入库进行中拒绝编辑（409，文案给出当前状态与「想中止就先重新排队」）：重新入库写的是影子代次，发布时 `deleteOtherGenerations` 整批删旧代次，这段时间改的文字会跟着旧代次一起消失，而界面已经说过「保存成功」。

正文走 `TextCleaner.normalize(...).trim()` 与入库同一套清洗；空 → 400 并指向「检索」开关（想排除就别塞空串），超 8000 字 → 400 并报「该调分块参数重新入库，而不是把一块改成一篇小文章」。8000 是给「两段并一段」留的余地，再长一定被 embedding 的 512 token 窗口截断。维度不符也不写库、不报错，只把「先核对 `LM_STUDIO_EMBEDDING_MODEL` 与 `rag.embedding.dim`」说出来。所有 WHERE 都带 `doc_id`：拿着别人的 `segmentId` 改本库的块和改自己库的块，返回的行必须不同。

前端：分块表加「操作」列（编辑 / 重算向量），`#` 列挂「已编辑」标签并在 title 里写明偏移与整篇重算的代价；对话框 meta 行显示向量状态与页/字偏移，「同时重算向量」对父块禁用并就地说明原因，`emb_status = PENDING` 的行才出「重算向量」；保存失败（400/409）不关框、草稿留着让用户接着改。`http` 层不需要新增动词。

测试：`SegmentEditServiceTest` 10 例（空/超长/0 行、父块不重算、维度不符不写库、模型异常仍算保存成功、不重算时留 PENDING、入库中 409、补算成功回读新行）＋ `SegmentEditSqlTest` 6 例（不连库钉 SQL 字符串：置 NULL 与 `CASE` 保 `SKIPPED` 在同一条语句、参数顺序、`doc_id` 谓词、`edited_at` 出现在读取列且映射列一一对齐、不出现 `::` 简写），`mvn -o test` 共 170 例全绿。浏览器侧用契约 mock 跑通六条路径：改子块并重算（正文与「已编辑」更新、向量 READY）、勾了重算但模型不可用（warning 型 note、行转 PENDING 并长出「重算向量」）、补算成功（READY、按钮消失）、父块（复选框禁用 + success 型说明 + `SKIPPED` 保持）、空正文 400（弹框不关、草稿留着）、入库中的文档 409。

连库才能验的部分留给虚拟化打开之后：`edited_at` 与 `content_ts` 生成列的实际刷新、`embedding IS NULL` 后向量路确实不再召回这一块。

## 17. M5d 交付面（知识库导出 / 导入）

接口：`GET /api/knowledge-bases/{id}/export?vectors=&files=`（回 `application/octet-stream` + UTF-8 `Content-Disposition`，文件名 `kb-{id}-yyyyMMdd-HHmmss.zip`）、`POST /api/knowledge-bases/{id}/import?rebuild=`（multipart，体只有一个 `file` part，回 `Summary`）。导出走 `StreamingResponseBody`，导入先落临时文件再用 `ZipFile` 随机访问——流式解 zip 只能按写入顺序读，缺一个条目就得整包重来。

包结构四件事，`FORMAT_VERSION=1`：`manifest.json`（谁、什么模型、什么维度、带不带向量/原件、逐篇条目）、`content/{slot}.txt`（一篇一个文件）、`segments/{slot}.jsonl`（一行一块）、`files/{slot}/{name}`（原件，可选）。`slot` 是包内序号（按 `kb_document.id` 排），不是库里的 id——id 属于目标库，导出时写死没有意义。条目名一律由 slot 现推，不在 manifest 里存一份路径，免得包被人手工改过之后清单和实际条目各说各话。向量存 `base64(小端 float32)`：768 维写成十进制文本约 15 KB，base64 只要 4 KB，一个库导出来差一个数量级；精度不用操心，pgvector 本来就是 float4，库里读回来的字面量已经是这个精度。

模式判定只看一件事——向量空间能不能直接用：`vectors && 维度相同 && embedding 模型名逐字符相同（忽略大小写、两侧 trim）&& !rebuild` 才是 **CARRIED**，否则 **REBUILT**。维度不符直接 409 并说出「本库 N 维、包里 M 维，要么改 `RAG_EMBEDDING_DIM` 要么勾强制重算」；不是 zip / 缺 manifest / 包版本比服务端新都是 400，且都发生在写第一行数据之前。CARRIED 逐块原样落回（含 `available=false`、`emb_status='SKIPPED'`、`edited_at`），REBUILT 只写正文与 `chunk_override`，`version=0`、`index_version=1`、状态 PENDING 并排进正常 INGEST（`reparse=false`，正文已经在包里，没必要再烧一次 Tika）。

记账按篇：同 sha256 已存在 → `skippedSame`（不覆盖、不重复烧 embedding，沿用上传的老规矩）；正文空白 → `skippedEmpty`；原件只在 sha 与清单一致时才落盘，不一致只导入正文并记一条 note；单篇异常 → `failed++` + note，不影响后面的篇。note 上限 40 条，超出补一句「其余说明过多已省略」。

配置新增 `rag.archive.max-import-mb`（`RAG_ARCHIVE_MAX_IMPORT_MB`，默认 512），同时把 multipart 上限提到 `max-file-size: 512MB / max-request-size: 640MB`——带向量的包比原文大一个量级，而单篇文档仍由 `rag.ingest.max-file-size-mb: 100` 把关，两个数各管各的。无新增迁移：导出的列和导入写的列都是 `V1` 里已有的。

测试：`VectorCodecTest` 4 例（往返一致、位数与 base64 长度、null 与空串、字节数不是 4 的倍数）＋ `KbArchiveRoundTripTest` 10 例（真走一遍 `ZipOutputStream`/`ZipFile`：CARRIED 保人工状态、REBUILT 排队、同 sha 跳过、空正文跳过、强制重算、维度不符拒绝、非 zip 拒绝、缺 manifest 拒绝、包版本过新拒绝、原件校验不过只落正文）＋ `ArchiveSqlTest` 10 例（不连库钉 SQL：`?::vector`/`?::jsonb`/`?::timestamptz` 三处显式 cast、参数顺序、`chunk_no` 升序、父块 LEFT JOIN、`edited_at::text` 读出）＋ `KnowledgeBaseArchiveApiTest` 7 例（导出先校验后开流、404 库不存在、Content-Disposition 带 UTF-8 文件名、导入超大小限制、空文件 400、临时文件用完即删、CARRIED/REBUILT 两种信封文案）。M5d 共新增 31 例，`mvn -o test` 现 202 例全绿。

前端：`ArchiveMenu.vue`（文档页工具栏「归档」按钮 → 对话框：目标库单选 + 带向量/带原件两个开关 + 导出，`选择 .zip` + 强制重算向量 + 导入），导入完再弹一个「导入结果」对话框，把 mode 标签、八个计数和逐篇 note 摊开——note 是唯一能说明「为什么少了一篇」的地方，不能只留一句成功。`http` 层新增 `download`（先判 content-type：后端失败发生在写响应头之前，回来的仍是 JSON 信封，不判就会把 `{"code":409…}` 当 zip 存盘）和 `saveBlob`（临时 `<a>` 要挂进 DOM，Firefox 不挂时 `click()` 是空操作；revoke 放到下一个宏任务）。浏览器侧用契约 mock 跑通：导出请求 200 + octet-stream、`filename*=UTF-8''` 解出中文名、库不存在时 404 弹的是后端的中文原因而不是半个坏文件、CARRIED 结果框（照搬块 128 / 原件 2 / 同名跳过 1 / 空正文 1 + 三条 note）、勾了强制重算后的 REBUILT 框（排队 3 / 失败 1 + 两条 note）、导入后列表自动重读并起轮询。

连库才能验的部分留给虚拟化打开之后：`insertArchivedGeneration` 写进 pgvector 的向量能否被向量路召回、父子链接是否真的接上、`kb_document.content_sha256` 去重在并发导入下是否仍只跳一次、原件落盘后的 `file_path` 与「重解析」能否走通。

**ADR-018：归档导入的「免重算」路径必须绕开索引发布器，人工意图是数据的一部分。**
最初的想法是让 CARRIED 复用 `SegmentIndexPublisher`——它已经把「放开新一代、删其余代次、置 READY」这条切换收在一个事务里，照搬它的代码看起来是零成本。但那三步的前提是「新一代刚写完、旧一代还留着」，而归档包里的块只有一代：没有旧代可删，放开动作也没有可对比的新一代，更重要的是 publisher 会按 `available` 与向量完整性重算一遍状态，把 `emb_status='SKIPPED'` 的父块当成漏算向量的块报出来。
于是改成直接写目标代次并置 READY，代价是这条路径不复用发布器、必须自己保证「写完块再链父」。换来的是三样人工意图能原样回来：被手工禁用的块仍然禁用（否则导入等于把用户「这块别进检索」的决定抹掉）、父块的 `SKIPPED` 不会被当成待补算、`edited_at` 还在（丢了它，界面就说不清这一条和原文不一样，而 `char_start/char_end` 指的仍是编辑前的位置）。
判断依据也只剩一条并且写死在代码与文案里：向量空间是否兼容。模型名或维度对不上就整体退回 REBUILT，不做「只对得上一半就先塞进去」——半个向量空间的库检索结果会按不可比的余弦分排序，比重新烧一遍 embedding 贵得多。



## 18. M6 交付面（一键部署与端到端回归）

`cp .env.example .env` 之后只剩两条命令：`deploy/start.sh`（PG 容器 → 打包并起 rag-api → 起 rag-web → 自检门）与
`deploy/stop.sh`（`--keep-db` 只停应用，`--purge-data` 要手输 `PURGE` 才删数据卷）。进程一律 pid 文件 + `nohup`，
日志落在 `deploy/logs/`，因此重复执行是幂等的：pid 还活着就跳过启动，不会把端口撞第二次。脚本只出 `.sh`，
不出 PowerShell 版——`docker`/`mvn`/`curl` 这套用法在实测指导里已经统一按 Git Bash 写，维护两份只会让两份漂移。

三个决定是这台机器教出来的，不是设计出来的：

1. **环境预检排在建镜像之前。** zhparser 首次编译 5–15 分钟，node 版本够不够 0.2 秒就能判定。
   于是 `java` 在不在、node 是否 ≥20.19/22.12（Vite 8 的硬门槛，本机系统默认还是 18）都提到 0/4，
   失败文案直接给「nvm use 22 再重跑，后端只认 JDK 17 不受影响」。
2. **`docker info` 必须套 `timeout`。** 引擎没起来时它不是返回错误，是一直挂着等——现象从「报错」变成
   「脚本卡住不动」，是最难转述的故障。现在 15 秒内没返回就判死，并给出 BIOS/WSL2 虚拟化的处置路径。
3. **8080 上已有应答时不静默复用。** 自检门只看 `/api/health` 的 `ready:true`，而任何忠实实现这个契约的服务
   （包括前端联调用的那份 mock）都会答 true。现在检测到「有应答但没有本脚本的 pid 文件」就明说：那是别人占着端口，
   继续跑下去第 4 步的绿是假的。

`deploy/smoke.sh` + `smoke.mjs` 把实测指导 §4~§10 的判定编成一条命令：health → 建库/选库 → 上传 `samples/` 全部七份
→ 轮询到终态 → 三种模式检索 → 契约负例 → 流式问答 → 块级禁用可逆 →（可选）归档导出/删除/导入。退出码 0/1/2，
失败清单一条一行，每条带着后端原文的 `message` 与 traceId。

实现选择：不用 bash+curl+jq。SSE 切帧、zip 中央目录解析、断言台账这三件事在 shell 里都是硬写，Node 单文件反而短。
`smoke.mjs` 零依赖，`fetch`/`FormData`/`Blob` 直接用，因此它和 rag-web 一样要求 Node 20.19+，这一点由 `smoke.sh` 拦住。
zip 不外部调 `unzip`：自己读中央目录 + `inflateRawSync`，为的是把「slot 从 0 连续编号、`content/{slot}.txt` 与
`segments/{slot}.jsonl` 成对、`files=true` 时每篇一个原件」这三条包结构约定变成断言，而不是靠人眼看 `unzip -l`。

**ADR-019：回归断言分两层，契约层随时可跑，事实层必须绑死写死的样本。**
「一条命令验全链路」的脚本最容易死在两种情况下：换环境就跑不动，以及跑绿了但什么都没验。所以断言拆成契约层
（信封、字段、事件顺序 `meta→delta…→done`、`hitCount==hits.length`、rrf 仍在 `1/(k+rank)` 量纲、错误都在写数据之前返回 4xx）
和事实层（`04/05` 必须 `GARBLED_TEXT`、`06` 必须判成同 sha 重复、「备份保留 35 天」必须出现在答案里、
关掉 `available` 的块两条检索路都召不回）。事实层只认 `samples/` 里那些故意写死的数字，改样本就得改脚本里的期望表——
这是有意的耦合，两边不同步的时候必须有一边报错。
代价是需要一个能答契约的东西来自检脚本本身：给前端联调用的那份 mock 补了会随时间推进的入库状态机、真 sha256 去重、
可解压的归档包和「导入只放回 READY」，于是 `smoke.sh --shape-only` 在没有数据库和模型的机器上也能跑完契约层那 27 项断言
（另外 18 项事实层按设计跳过；本机 2026-11-16 全量 `--archive --models` 是 PASS 54 / FAIL 0 / SKIP 0，12.7s）。
反过来，同一条脚本对 mock 打开事实层会稳定报 7 条**断言失败**（不是异常），这正是想要的形态：脚本崩了要修脚本，
断言红了要查系统，两种现象不能混。破坏性的一段（导出→删库内全部文档→导入）默认不跑，必须显式 `--archive`；
块级禁用那段自带恢复，所以默认可跑。

## 19. M5f 交付面（运行诊断与日志）

这一节针对的是一类特定的 bug：请求成功、响应正常、日志安静，而结果已经不值得信。本项目有三种，每种都合法、
连起来看是灾难——

- **检索降级**：embedding 服务没起来，或者库里还没建分词列，向量路整个缺席，RRF 分数改由关键词路单独给出。
  阈值量纲跟着换（0.45 的尺子去量 0.016），命中照样是命中。用户只会觉得「答案变笨了」，说不出哪里变了。
- **上下文截断**：召回 8 条，预算只装得下 3 条。答案缺后半段，现象和「模型不行」一模一样。
- **无证据拒答**：阈值调严或分块切坏都会让 `plan.empty()`，固定话术照常返回 200。

`RunDiagnostics` 把这三条加上 embedding 调用失败收成四个进程内计数器，`GET /api/diagnostics` 一次回三块：
`run`（计数 + 最后一次降级/模型故障的原因与时刻）、`effective`（当前真正生效的那套参数：模式、阈值、
`n_ctx` 与由它算出的 `contextBudgetChars`、分块尺寸、模型名与超时）、`warnings`（后端自己算出来的配置矛盾）。

四个决定：

1. **计数器不落库、不做直方图，重启归零。** 它回答的是「刚刚有没有变差」，不是「这个月平均降级率」。
   需要长期统计就去翻日志文件，那里每一条都带 traceId 和 answerId，能落到具体一次问答上。加库表等于给一个
   排障工具做持久化，代价是它自己也会坏。
2. **`warnings` 只报「几乎一定是错的」两条。** `min-rrf-score > 1/(rrf-k+1)`（RRF 第一名只有 0.0164，阈值 0.45
   意味着检索永远空手，而界面看起来像「库里没资料」）和 `child-chars > 480`（bge 系列 512 token 窗口，超出部分
   被模型静默截断，表现为「文档里明明有却搜不到」）。这两条的共性是：改配置的人不会收到任何异常。
   告警再往下加就会淹掉，和没有一样。
3. **日志文件让给 logback，`start.sh` 的 stdout 改写到 `rag-api.out`。** 原先 `nohup java -jar > rag-api.log`
   是唯一的那份日志，但它不滚动，而且 Windows 控制台是 GBK——重定向文件里的中文换台机器就是乱码，而排障恰恰
   要看那句中文。现在人读的是 `deploy/logs/rag-api.log`（logback 滚动，单文件 20MB / 留 14 天 / 封顶 500MB，
   显式 `logging.charset.file: UTF-8`），`.out` 只留「logback 还没起来」那一段（JDK 版本、jar 缺失）。
   测试侧用 `src/test/resources/application.properties` 把 `logging.file.name` 清空：这个值是相对当前目录的，
   不管住的话跑一次 `mvn test` 就在源码树里长出 `rag-api/deploy/logs/`。
4. **traceId 要跨线程。** 一次问答横跨 HTTP 线程与 `rag-chat-*` 线程，`MdcTaskDecorator` 在提交时复制 MDC、
   跑完还原（不是清空：线程会复用，留下上一个请求的 id 会让两次问答看起来像一次）。入库 worker 没有请求可挂，
   按任务自己造 `t{taskId}`——同一次入库的多行日志由此能连成一条线。

**ADR-020：诊断端点与 health 分开，回归脚本负责把两者说成同一件事。**
`/api/health` 回答「依赖通不通」（PG / 分词 / 目录 / 维度一致性，失败给 503），`/api/diagnostics` 回答
「依赖都通，但结果可疑」（永远 200）。两者合并会互相拖累：health 的语义要能给编排系统当存活探针用，
掺进「本轮降级 3 次」就没人敢拿它自动重启了。
连带的好处是回归脚本能把两条独立通道对起来——第 7 步 SSE 的 `meta.contextTruncated` / `meta.degraded`
与第 11 步的计数器必须一致。哪一边接错了线都会立刻红：只发事件不计数，或者只计数不发事件，都过不了这条对账。

## 20. M5e 交付面（评测集与跑分）

接口 8 个，全在 `/api/evaluation` 下：`GET/POST /cases`、`PATCH/DELETE /cases/{id}`、
`POST /cases/from-feedback?kbId=`、`POST /run?kbId=&mode=&topK=&note=`、`GET /runs?limit=`、`GET /runs/{id}`。
`GET /cases` 只有在 `enabledOnly=true` 时才额外查一次总数（「启用的 2 / 共 7 条」这句要两个数才说得出来），
列全量时不为一句话多付一次 `count(*)`。

迁移 `V3__evaluation.sql` 三张表：`eval_case`（问题 + `expect_marker` + `expect_doc` + `should_answer` +
`origin`/`origin_msg_id`/`note` + `enabled`）、`eval_run`（`settings` / `metrics` 两个 jsonb + 起止时刻）、
`eval_result`（`run_id`+`case_id` 主键，带 `first_rank`/`hits`/`refused`/`correct`/`took_ms`/`reason`/`detail`）。

**ADR-021：跑分只量检索与装配，不量答案质量；能按请求覆盖的参数只开 mode 与 topK。**
决定：`POST /run` 走 `HybridSearchService` + `EvidencePlanner` 之后就地判分，**一次都不调生成模型**。
理由：评测唯一的用处是「改一个参数，分数变化能归因到那个参数」。模型采样做不到可重复——同一套参数两次
跑出不同答案，把答案质量混进指标，一轮分数涨跌就再也分不清是检索变了还是采样抖动；只做检索则一轮几秒钟，
两次跑分只差 `mode`/`topK` 时差值就是那两个参数的效果。
同理，阈值这类参数不提供按请求覆盖：`eval_run.settings` 必须在跑第一条用例**之前**落库（中途崩了也要留下
这一轮的参数），一旦允许「请求里带一个、配置里读另一个」，快照记的就不再是真正生效的那份，比较的资格也就没了。
代价一：「检索找到了、模型答得烂」这套读不出来。那部分由回归第 7 步的事实断言（答案里必须出现写死的数字）
和反馈闭环兜住，不假装跑分覆盖了它。
代价二：请求的模式不等于生效的模式——快照写在跑之前，向量路算不出来时它仍然写着 `HYBRID`。
所以降级这件事由另外三处说实话：逐条 `reason` 补一句「降级跑的：请求 X，实际只走 Y」、这一轮汇总落一条 WARN、
`/api/diagnostics` 的 `vectorDegraded` 计数。回归第 11 步拿最后一个数和整轮检索对账：
不为 0 时前面那批 rrf 分数是关键词一路给的，整批结论都不作数。

四条判据是这套东西的全部价值，每一条都有它单独要躲开的坑：

1. **相关性只认 `expect_marker`（命中块正文里必须出现的一段文字），不认 segment_id。**
   改分块尺寸或重算向量之后块 id 必然变，而评测要问的偏偏是「换了参数还找不找得到」——锚在 id 上等于一调参就全废。
   比对前先折叠空白并转小写（分块会把换行变成空格，字面相等判不了正文），`expect_doc` 允许只写主干名。
2. **判「会不会拒答」复用问答链路的装配判据，而不是看 `hits.isEmpty()`。**
   命中 6 条但预算一条装不下，线上同样是拒答；评测若按「空命中」判，就会和用户体验各说各话。
   做法是把这条共用逻辑抽进 `EvidencePlanner`（`retrieval.parentContents` + `planner.assemble` + `plan.empty()`），
   问答与评测各自调同一个 bean——`EvaluationServiceTest` 里装的是真的 planner，不是 mock。
   反过来也一样要紧：**装得下就不叫拒答**。召回 6 块只装下 3 块是截断（`plan.truncated()`，模型照常拿到 3 块并生成），
   第一版判分把负例的 `refused` 写死成常量 `true`，于是同一条记录既写着「已拒答」又判「错」、原因写着「被召回了」，
   而它恰恰是混合模式那一轮唯一的真话（`拒答正确率=0`）。现在三处必须同源：`refused` 照抄 `plan.empty()`，
   `correct` 对负例就等于它，`reason` 只在没拒答时出现。
3. **分母为 0 的指标是 `null`，不是 0。** 「这批用例里没有负例」和「负例全错」是两件事，
   压成 0 就分不清了；接口文案把 null 写成「不适用」。同理，未标注的正例（没 marker，判不了）整个不进分母，
   否则「加了六条待标注」会被读成「检索退化了」——它只在 `metrics.invalid` 里报个数。
4. **错例的原因在判的那一刻就写成中文一句话落库，而「装不装得下」有自己的指标。**
   「空召回」「召回了但一块都没装下」「相关块排在第 5 名」三种失败的修法完全不同（调阈值 / 改分块或预算 / 改排序），
   混成一句「没召回」，跑分就退化成只能看出好坏。而被预算挤出去这件事最初只在原因里顺带提一句，
   `hit@K=1.0` 看起来一切正常——所以它现在是一项独立指标 `truncatedCaseRate`（正例里 `plan.unplacedHits()>0` 的占比），
   并且**刻意不参与 hit@k 的判定**：hit@k 量检索排第几，截断率量装配吃不吃得下，混在一起调 `n_ctx`
   就会看起来在改检索质量。真机读数：topK=6 每轮召回 6 块装下 5 块、topK=50 召回 22 块只装得下 12 块，
   两轮 `hit@K` 都是 1.0 而截断率都是 1.0。原因文案跟着分两种说清：
   相关块自己进了模型（「召回 N 块里有 K 块没装进上下文」）与没进（「排在第 N 名，本次上下文只装下 M 块，
   模型没读到它」）——后者是「分数说命中、线上答不出」的唯一提前预警。汇总不为 0 时同一轮还会落一条 WARN
   （`deploy/logs/rag-api.log` 里 grep `却没装进上下文`），因为这轮分数与预算充足那轮不可比。
   这个字段是后加的：改动之前的历史轮次没存过它，读出来是 `null`（信封写「不适用」）而不是 0，
   `delta` 也会跳过这一项——「没存过」和「一条都没截」同样是两件事。

**参数与历史。** `eval_run.settings` 记 15 项当轮真正生效的参数（模式、生效阈值及其两个来源值、候选池、rrf-k、
`parentContext`、关键词引擎、embedding 模型与维度、`n_ctx`、折算出的 `contextBudgetChars`，
外加 `modeOverride`/`topKOverride` 两个「这次是不是被请求改过」）。覆盖项只开 mode 与 topK 两个，
阈值这类不提供按请求覆盖——要比较就重启服务改配置，这样快照必然等于真实生效值，而不是「我以为的值」。
`GET /runs` 里每轮带 `delta`（相对上一轮的七项差值，任一侧缺该指标就不写这一项而不是补 0），
`detail` 单轮读不回上下文所以恒为空，这是有意的。

`eval_result` 的 `case_id` 不建外键：`ON DELETE CASCADE` 会让删一条用例顺手抹掉历史一整行，
`RESTRICT` 又让「改个判据」都得先删跑分记录。两边都不对，于是让结果行自己带着那一刻的 `question`、
`expect_marker`、`reason`——用例没了这一行照样自解释。`detail` 另存前 5 条命中的
`{rank, docName, chunkNo, rrf, relevant, snippet}`：只知道「没进前三」没用，得看见挤在前面的是什么。

**反馈闭环的下游。** `POST /cases/from-feedback` 只捞 `rating=-1` 且已填 `annotated_answer` 的回答（ADR-014
那条闭环的产物），取的是 `query_final`（改写后的那句，才是检索真正面对的输入），按会话的 `kb_ids` 过滤，
一次最多 50 条。生成一律 `enabled=false` 且 `expect_marker` 留空：机器从订正答案里截一段当判据，
等于让评测自己考自己——分数会跟着订正的措辞涨，检索一点没变。未启用的正例强行 `PATCH enabled=true` 会被 400 挡回去。

**前端不做。** 评测是开发者工具：一次判断要连着看两三轮的参数差值、要逐条读错例原因，命令行和回归脚本比界面顺手。
`deploy/smoke.mjs` 第 9 步已经把「建用例 → 两轮跑分 → 逼一次截断 → 参数快照 → 删用例后历史仍可读」这条链编成 8 项断言，
真机读数写进 [实测指导 §12](实测指导.md)。等标注工作量真的大到需要批量操作时再补页面。

**测试。** `EvalScorerTest` 14 例（纯判据：折叠空白、文档名主干、三种失败各自的说法、未标注不进分母、
分母为 0 报 null、装下一半是截断不是拒答、排在装不下的那一截要说「模型没读到它」、截断率不为 hit@k 污染、
负例的 refused/correct/reason 三处同源）、
`EvaluationServiceTest` 14 例（真装配器、写入捕获让 `detail()` 读回真存进去的那份、
四条超长命中真把预算吃光后截断率落到 metrics JSON 里、降级跑的每一行都写明「请求 HYBRID 实际只走 KEYWORD」、
参数快照、单条失败不毁整轮）、
`EvaluationApiTest` 13 例（八条接口的信封与人话文案，含「上下文截断率」单独成句并指向 n_ctx/parent-max-chars）、

## 1. 需求：这个系统在解决什么

### 1.1 一句话

公司内部文档（制度、运维手册、合同、论文、台账）灌进系统后，员工用自然语言提问，得到**带原文引用位置**的答案；
数据、向量、模型推理**全部在内网**，不调任何云端 API。

### 1.2 对标业界功能清单（以及本系统的实现状态）

| 业界常见功能 | 本系统 | 说明 |
|---|---|---|
| 多格式解析（PDF/Word/MD/TXT/CSV/HTML/JSON） | ✅ | Tika，8 类扩展名白名单 |
| 中文分词检索 | ✅ | zhparser + tsvector，不可用时三级降级 |
| 混合检索 + 重排融合 | ✅ | 向量 + 关键词双路，RRF |
| 父子分块（小块命中、大块作答） | ✅ | 400 / 1200 字 |
| 引用溯源到页/章节/字符偏移 | ✅ | `heading_path`、`page_start/end`、`char_start/end` |
| 流式输出 | ✅ | SSE `meta → delta* → done` |
| 无依据拒答 | ✅ | 空召回不调模型，状态 `REFUSED` |
| 多知识库隔离 | ✅ | `kb_id` 谓词贯穿每一路 SQL |
| 人工反馈与答案订正 | ✅ | 评分 / 反馈文本 / `annotated_answer` |
| 文档级分块参数覆盖 | ✅ | `chunk_override` 只存差异 |
| 单块编辑 + 单块重算向量 | ✅ | 旧向量当场作废 |
| 知识库导出 / 导入（免重算迁移） | ✅ | zip 归档包，`CARRIED` / `REBUILT` |
| 运行诊断（静默失败可见） | ✅ | `/api/diagnostics` + 4 个计数器 |
| 端到端自动化回归 | ✅ | 10 步 / 50+ 断言，契约层无依赖可跑 |
| **检索质量量化评测（hit@k / MRR / 拒答正确率）** | ❌ 待办 M5e | 简历红线，见 §16.1 |
| **rerank 模型重排** | ❌ 待办 M5g | 已设计：默认关、失败退回原序 |
| **鉴权 / 多租户 / 审计** | ❌ 明确不做 | 信任边界是局域网，见 §16.3 |
| OCR 扫描件识字 | ❌ 不做 | 但做了"乱码扫描件"识别并拒收，见 §5.2 |
| 联网搜索 / Agent 工具调用 | ❌ 不做 | 范围外，私有化知识库不需要 |

**面试话术**：被问"和 Dify / FastGPT / MaxKB 比怎么样"时，不要说"更好"。说：
> "它们是可搭建平台，覆盖的场景比我这个宽得多。我做的是**其中一个场景做到能验收的深度**——
> 中文分词的降级路径、引用能定位到字符偏移、重算时检索不能读到半成品、回归断言绑死样本事实。
> 平台类产品为了通用性在这些点上通常是妥协的，我这里是反过来的：功能面窄，但每一条我能讲到实现细节。"

### 2.2 两条动态主线（务必能默写）

**入库线（异步）**
```
POST /documents → FileStorage 落盘 + sha256 去重 → kb_document(PENDING)
   → kb_task 入队 → IngestWorker 轮询领取(租约 10min)
   → Tika 解析 → TextCleaner 归一 + 乱码闸 → ChineseSemanticSplitter 父子块
   → embedAll 批量 16 条 → 逐条维度校验
   → SegmentIndexPublisher 单事务发布（影子代次 + available 翻转）
   → 文档 READY / FAILED（永久失败不消耗重试预算）
```

**问答线（同步流式）**
```
POST /chat/ask（在 rag-chat-* 专用线程池执行）
   → resolveSession → 取历史（写本轮问题之前取）→ insertQuestion
   → scopeKbIds → HybridSearch.search（双路召回 + RRF + 阈值过滤）
   → ContextPlanner.budgetChars → assemble（父块去重 / truncated / unplaced）
   → beginAnswer 落库 → sink.meta(...)
   → plan.empty()? → 不调模型，固定话术，status=REFUSED，return
   → 流式 token → sink.delta → 完成 finishAnswer(OK, tokens, modelName)
   → 客户端断线 → markAnswer(INTERRUPTED) 保住已吐出的字
```

### 2.3 面试怎么用这一节

- 画架构图时**先画两条线再画框**：框是任何项目都有的，链路才说明你真做过。
- 主动指出**为什么入库异步、问答同步**：入库是长任务且可能失败重排，问答要即时反馈。
- 指出**为什么问答要独立线程池**：SSE 一占就是几十秒，4 并发 + 8 队列，超过直接明确拒绝，
  不把 Web 线程耗尽导致整个后端"看起来挂了"。

## 3. 技术选型：每个"为什么不是 X"

选型题的标准答法：**先说约束，再说选择，最后说换掉的代价**。本项目约束是「单机 + 内网 + 一个人 + 中文资料」。

| 选择 | 没选的那个 | 理由（能背的版本） |
|---|---|---|
| Java 17 + Spring Boot | Python / FastAPI | 重构前是 Node，团队栈要 Java；且入库/问答并发、事务边界、线程池这些在 Java 生态里更可控。代价：调试 embedding 响应比 Python 麻烦 |
| pgvector | Milvus / Weaviate / Qdrant | 已经有 PG，向量和元数据在**同一个库同一张表**才能一条 SQL 里做完「范围谓词 + 向量排序 + 全文召回 + 融合」；引入独立向量库就必须在应用层拼两路结果，且多一份运维。代价：库大了 HNSW 内存吃紧时没有专用向量库好扩 |
| 手写混合检索 SQL | `PgVectorEmbeddingStore`（langchain4j 自带） | ADR-001：那个 store 只会建 IVFFlat，也不给关键词路和 RRF 的插手空间。保留 langchain4j 只用它的模型客户端和 Tika 解析器。代价：自己维护距离算子和索引 DDL |
| HNSW | IVFFlat | 小库高召回优先，建库时不用先训练、`m=16 / ef_construction=64` 起步够用。代价：构建慢、内存大 |
| zhparser 自建镜像 | 官方镜像 + 应用层分词后存词 | 分词留在数据库里，`to_tsvector` 可以是 **GENERATED 列**，改正文自动重算，不会有一致性窗口。代价：镜像要自己维护（编译 5–15 分钟） |
| pg_trgm 作降级 | 直接启动失败 | "扩展没装"是可恢复的运维状态，不是代码缺陷。三级降级让系统**少装一个扩展也能跑**。代价：trgm 按字切，精度下降 |
| Flyway | JPA `ddl-auto` / 手工 SQL | 维度 `${embedding_dim}` 是 schema 的一部分，必须和配置同源；迁移脚本带条件逻辑（有 zhparser 才建 tsvector 列）。代价：占位符和配置不同源时启动校验直接报错（这是故意的） |
| JdbcTemplate | JPA / MyBatis | 检索侧全是窗口函数 + CTE + 向量算子，ORM 帮不上还挡路；写侧表少字段直白。代价：手写 RowMapper |
| SSE | WebSocket | 单向流式够用，浏览器侧 `EventSource` 不支持 POST，所以前端用 `fetch` + 自己切帧；服务端省握手与心跳。代价：没有双向通道（本项目不需要） |
| 任务队列用 PG 表 + `FOR UPDATE SKIP LOCKED` | Kafka / RabbitMQ | 单机私有化引入 MQ 只增加一套要备份的有状态组件；任务量级（部门文档）表完全够。代价：不能水平扩到多机高吞吐 |
| Pinia + fetch | axios + EventSource | ADR-014：请求层只剩 fetch，少一个依赖、SSE 分帧自己写更短更可控。代价：拦截器要自己组装 |
| LM Studio 本地推理 | OpenAI / 云端 API | 需求就是数据不出内网。代价：`n_ctx` 只有 4096，直接逼出了 §7 的预算设计 |

**必考反问**："为什么不用现成的 Dify？"
> "如果只要能用，Dify 一天就搭完了。我要的是**中文资料的引用能定位到字符偏移、重算时检索读不到半成品、
> 换机器不重算 embedding 也能迁移、静默降级能被诊断出来**——这四件事在平台上是黑盒。
> 而且私有化到单机内网时，多一层平台的部署与升级成本是我自己承担的。"

## 4. 数据模型（6 张表）

```
knowledge_base 1─N kb_document 1─N kb_segment（自关联 parent_id）
knowledge_base 1─N kb_task
chat_session   1─N chat_message（parent_msg_id 自关联：订正答案指向原答案）
```

### 4.1 `knowledge_base`——为什么模型名要存进库里

`embedding_model` / `embedding_dim` **与文档一起存**，不是只存配置。原因：向量空间不互通。
换 embedding 模型时维度可能一样（本机 bge-base 和 nomic 都是 768），schema 不变，但新旧向量混在一起检索就是污染。
所以启动时校验「库内已存的 embedding_model」与配置是否一致（`embeddingConsistency` 探针），不一致要显式处理。
`index_version` 配合 segment 的 `doc_version` 做索引代次。三个 `*_config` jsonb 存分块/检索/提示词偏好。

### 4.2 `kb_document`——三个关键列

| 列 | 为什么是它 |
|---|---|
| `sha256` + `UNIQUE (kb_id, sha256) WHERE deleted_at IS NULL` | 内容去重，同库同哈希不重复入库（省一次 embedding）。**部分唯一索引**：软删之后允许重新上传同名同内容 |
| `content`（清洗后正文，保留 `\f` 分页符） | ADR-008：重新分块**不再跑 Tika**。解析是最慢最不稳的一步，且清洗后的文本才是字符偏移量的基准 |
| `chunk_override` jsonb | 只存与全局默认不同的键；`NULL` = 完全跟随默认。改它只在下次"重算"时生效（ADR-016：存差异不存快照，校验在合并之后） |

状态机：`PENDING → PARSING → SPLITTING → EMBEDDING → INDEXING → READY`，失败进 `FAILED` + `error_code`/`error_msg`。
`progress`/`progress_msg` 给前端轮询显示；`retry_count` 只对临时失败累加（ADR-009）。

### 4.3 `kb_segment`——本表的设计密度最高，能讲 5 分钟

| 列组 | 设计意图 |
|---|---|
| `parent_id` 自关联 | 父子块：子块（400 字）用于精确命中，`parent_context=true` 时取父块（1200 字）作答 |
| `chunk_no` + `doc_version`，`UNIQUE(doc_id, chunk_no, doc_version)` | 代次。重算时写入新 `doc_version` 的"影子块"，发布时在一条事务里翻转 `available`（ADR-007） |
| `heading_path` `page_start/end` `char_start/end` | 引用溯源。纯文本无标题时 `heading_path` 为 NULL，位置只剩页/字符偏移 |
| `embedding vector(768)` + `embedding_model` + `emb_status` | 向量与它的来源模型、状态（`PENDING`/`DONE`/`SKIPPED`）分开记：人工跳过的块和没算的块不是一回事 |
| `edited_at` | 人工编辑过正文的时刻。**非空即说明 `char_start/end` 描述的是编辑前的位置**（ADR-017/018） |
| `available` | 块级开关。关掉后两条召回路的 WHERE 都排除它，是"这一条别拿来答"的最小粒度 |
| `hit_count` `questions` `metadata` | 运营与调试用的记账，不参与检索 |
| `content_ts`（条件 GENERATED 列） | 有 zhparser 才建，`GENERATED ALWAYS AS to_tsvector('chinese', content) STORED` + GIN。生成列=改正文自动重算，不会不一致 |

### 4.4 `kb_task`——用表实现队列

`status QUEUED/RUNNING/DONE/FAILED`，领取靠 `FOR UPDATE SKIP LOCKED`（并发 worker 不抢同一行），
`lease_owner`/`lease_until` 是租约：worker 崩了任务最多卡 10 分钟就被回收重排（部分索引 `WHERE status='RUNNING'` 支撑回收扫描）。
`attempt`/`max_attempts=3`/`next_retry_at` 做退避重试；`error_type` 区分永久与临时（永久直接终态，不浪费预算）。

### 4.5 `chat_session` / `chat_message`

`sources` 与 `retrieval_meta` 都是 jsonb——**答案生成时的检索现场必须原样留住**，否则事后调参无法复现当时的判断。
`status`：`STREAMING → OK / REFUSED / FAILED / INTERRUPTED`（ADR-013：先落库再流式）。
`rating`（评分）/ `feedback_text`（反馈）/ `annotated_answer`（人工订正后的答案，成为后续问答的事实来源）/
`parent_msg_id`（订正答案指回原答案）/ `trace_id`（能从这条消息回到后端日志）。

## 5. 入库链路

### 5.1 解析

`TikaDocumentParser`（langchain4j 的 Apache Tika 解析器）+ 扩展名白名单
`pdf,docx,doc,md,markdown,txt,csv,json,html,htm`，单文件上限 100MB（`rag.ingest.max-file-size-mb`）。
PDF 的分页符 `\f` 被**刻意保留**——它用来算 `page_start/page_end`，`TextCleaner` 里连控制字符清洗都绕开它，
并把 `\f` 独占一行处理，否则上一页末行和下一页首行会被当成同一段。

### 5.2 清洗与乱码闸（`TextCleaner`）

顺序有讲究：**先归一再检测**，反过来压缩空白会把乱码段落洗成看起来正常的文本。

- `normalize`：统一换行、去零宽字符与软连字符、去控制符（保留 `\f`）、制表符转 4 空格、压缩 3 以上空行。**不动行内空格**——代码块和表格里的空格是内容。
- `rejectGarbled`：按"可解释字符占比"判定。PDF 的 CID 字体缺 ToUnicode 表时，Tika 抽出来的是**看着像正文的乱码**，
  静默入库等于往库里灌噪声。实测样本 `05-乱码扫描件.md` 全角 ASCII 占比约 49%，超过 15% 底线 →
  `GARBLED_TEXT`，文案「疑似 CID 字体乱码（异常字符占比 49%）」；空正文（只有全角空格）也走同一个错误码。

**为什么值得讲**：这是 RAG 里典型的"垃圾进垃圾出"防线，而且它**不消耗重试预算**——永久性失败重试一万次也是失败。

### 5.3 中文语义分块（`ChineseSemanticSplitter`）

三层：段落 → 章节（父块，≤1200 字）→ 句子级子块（≤400 字，最小 120 字，相邻重叠 60 字）。

- 标题识别三种模式：Markdown `#`、中文卷章（`第X章/节/部分/条款`、`附录`/`摘要`/`参考文献`/`目录`/`前言`）、
  数字层级（`1.2.3 标题`）。识别不到标题时 `heading_path` 为 NULL，父块退化到段落聚合。
- **400 这个数不是审美，是模型窗口**：bge-base-zh-v1.5 在 512 token 静默截断，中文约 1 字 1 token，留余量到 400。
  写进校验：`childChars < 50` 直接报错并提示建议 300–450；`overlapChars >= childChars`、
  `parentMaxChars < childChars` 都拒绝。诊断接口对 `childChars > 480` 出一条告警——**因为它不会报错，只会让答案莫名缺一块**。
- 几乎没有句号的长段落（样本 `03`）退回定长窗口，仍保证相邻块重叠 60 字，且段落尾部不丢（末尾校验码 `TAIL-9F3C` 必须搜得到）。

### 5.4 向量化与索引发布

- `embedAll` 批量 16 条：实测 16 条/批 0.41s，单条 0.04s——批处理的意义在减少往返，不是减少计算。
  批量返回条数与请求不符（模型服务抽风）按异常记账。
- 每条向量单独校验维度；`embedding_model` 与配置不一致则拒绝写入（防止空间污染）。
- `SegmentIndexPublisher.publish()`：**一个 `@Transactional` 里七步**——清掉目标代次的残留 → 整代新块以
  **`available=false` 落库（文本和向量一起写，不留"有块无向量"的中间态）** → 回填父子链 →
  `publishGeneration` 把该代次 `available` 翻成 true → **校验"有没有可检索块缺向量"，有就抛异常回滚，
  拒绝放开这一代** → 删除其它代次 → 文档置 READY 并更新 `index_version`。
  这样并发检索要么读到完整旧的一套，要么完整新的一套；中途崩溃则整体回滚，可重试，
  **不存在"旧块删了、新块没放开"这种检索直接空的死态**。（最后那条向量完整性守卫是 ADR-007 的另一半：
  放开索引 = 承诺这块能被向量路召回，半成品放开就是把坏数据推进答案里。）

### 5.5 worker

`IngestWorker` 轮询（2s）领取 → 处理。崩溃恢复有**三条独立的自愈路**（能分开讲清就是懂了的证据）：

1. **租约回收**：`reapExpiredLeases()` 周期性把 `lease_until` 过期、仍挂在 RUNNING 的任务重新排队（worker 被 kill 时任务不会永久卡住）；
   启动时立刻先跑一次，所以重启不用等一个租约周期。
2. **文档落地**：`IngestStartupRecovery` 在 `ApplicationReadyEvent` 时把停在 `PARSING/EMBEDDING` 这类中间态的文档
   置成 `FAILED` + 可直接重试的说明文案——**否则界面上永远转圈**，那是无法自愈的中间态。
3. **优雅停机**：`@PreDestroy` 里 `releaseOwned(owner)` 把**自己正在跑**的任务归还队列，重启后别的 worker 立刻接手。

每条任务前 `MDC.put("traceId", "t"+taskId)`，finally 里清掉——**后台任务没有 HTTP 请求，日志也要能串起来**。

## 6. 检索（本项目最硬的一节）

### 6.1 三种模式

`VECTOR`（只走向量）/ `KEYWORD`（只走全文）/ `HYBRID`（双路 + RRF，默认）。切换只改排分方式，不动数据库。

### 6.2 双路 SQL 一次打完

`RetrievalRepository` 拼出的形状：

```sql
WITH vec AS (SELECT id, row_number() OVER (ORDER BY dist) AS rank, 1.0 - dist AS similarity
             FROM (SELECT s.id, s.embedding <=> CAST(:queryVec AS vector) AS dist
                   FROM kb_segment s WHERE <范围谓词> ORDER BY dist ASC LIMIT :candidateK) v),
     kw AS (SELECT id, row_number() OVER (ORDER BY m DESC, id) AS rank FROM (
             SELECT ts_rank(s.content_ts, plainto_tsquery('chinese', :kw)) AS m ... LIMIT :candidateK) k),
     fused AS (SELECT COALESCE(v.id,k.id) AS id, v.rank vec_rank, k.rank kw_rank,
               (CASE WHEN v.id IS NULL THEN 0.0 ELSE 1.0/(60+v.rank) END
              + CASE WHEN k.id IS NULL THEN 0.0 ELSE 1.0/(60+k.rank) END) AS rrf ...)
```

三个要点：
1. **`<=>` 是余弦距离**，相似度 = `1 - dist`。
2. **范围谓词写进每一路自己的 WHERE**（`kb_id`、`available`、文档过滤），不物化一个公共 scope CTE（ADR-011）。
   理由：物化 CTE 会让 PG 失去把谓词下推到索引的机会，向量路要走 HNSW、关键词路要走 GIN，两套执行计划被一条 CTE 卡死。
3. **单路模式不白跑融合**：只有一路可用时直接给该路 `1/(k+rank)`，另一路 rank 为 NULL。

### 6.3 RRF，以及它为什么不是"分数相加"

`score = Σ 1/(k + rank)`，`k=60`（业界惯例，作用是**压平第一名和第二名的差距**）。

- 为什么用 RRF：余弦分（0–1）和 `ts_rank`（PG 自己一套 A–Z 权重，量纲无关）相加等于让其中一路说了算。
  RRF **只用排名不用分数**，天然免疫量纲问题。
- 代价（一定要主动说）：**丢掉了分数的绝对置信度**。一个 0.92 的强命中和一个 0.55 的弱命中在 RRF 里都只是 rank=1，
  所以阈值必须换尺度：RRF 第一名 ≈ `1/61 ≈ 0.0164`，整个分数待在 `0.01x` 量纲。
- 因此**两套阈值按量纲配对**：`min-score=0.45`（纯向量余弦）/ `min-rrf-score=0.012`（混合 RRF）。
  照抄 0.45 到混合模式 → **所有结果被滤光**，这是本项目里最贵的一次踩坑（硬性约束 1，ADR-010）。
- ADR-010 的后半句：**阈值是"生效模式"的属性，不是"请求模式"的属性**。
  请求 hybrid 但实际只走成 vector 时，要用余弦阈值，不能用 RRF 阈值——否则降级本身就是把召回清空的原因。

### 6.4 降级矩阵（能默写就赢了）

```
effectiveMode(requested, vectorReady, keywordReady):
  !vectorReady && !keywordReady      -> null（两路都不通，直接返回空结果并记 vectorDegraded）
  VECTOR  -> vectorReady ? VECTOR : KEYWORD
  KEYWORD -> keywordReady ? KEYWORD : VECTOR
  HYBRID  -> both ? HYBRID : (vectorReady ? VECTOR : KEYWORD)
```

`vectorReady` 的真值是"查询向量算成功了"——embedding 服务调用失败时捕获异常、
记 `diagnostics.embeddingFailure(reason)`、把向量路关掉继续走关键词，并把阈值切到 RRF 那套。
**模型服务挂掉时系统还能降级作答**，这比 500 报错有价值。

### 6.5 关键词引擎探测（ADR-003）

`KeywordEngine` = `CHINESE_TSVECTOR` / `TRIGRAM` / `NONE`。
判定依据不是"扩展装没装"，而是**`kb_segment.content_ts` 这一列在不在**——那列是 migration 里按 zhparser 可用性建的，
列存在就说明分词配置真的能用。探测结果进程内缓存，`refreshEngine()` 手动刷新；结果同时出现在
`/api/health` 的 `chineseFullText` 探针、检索结果 `meta` 帧、`/api/diagnostics` 的生效配置里。

## 7. 上下文装配与流式问答

### 7.1 预算公式（`ContextPlanner.budgetChars`）

```
budgetChars = round(n_ctx * charsPerToken)
            − round(outputReserveTokens * charsPerToken)
            − templateChars
            − conversationChars(历史 + 本轮问题)
            （负数夹到 0）
```
默认 `4096 − 700 − 900 − 对话` → 无对话时 **2496 字**（`DiagnosticsApiTest` 断言了这个数）。

- **为什么按字符不按 token**：本地模型没有可靠的免费分词接口，为算长度多打一次服务不值。
  `charsPerToken=1.0` 是**故意保守**（中文约 1 字 1 token）。
- **为什么宁可少装**：超出 `n_ctx` 时模型不会报错，而是**静默丢掉中间段落**，表现是"文档里明明有却答不全"，
  这类问题排查成本极高。所以预算是硬边界。
- `n_ctx` 必须与 LM Studio 实际加载窗口同源（配置注释里写死了这一点）：**模型窗口是运行期事实，不是配置项**。

### 7.2 装配规则

- 按相关度顺序装；子块命中时**换成父块正文**（`parent_context=true`），同一父块被多个子块命中只装一次且不产生新引用。
- 剩余空间 < `MIN_USEFUL_CHARS=120` 就**停止装入**：塞半句话进去只会诱导模型编，不如空着走拒答。
- 装不下但被截半的 → `truncated=true`；召回了却没进上下文的条数 → `unplacedHits`（前端用它提示"还有资料没装下"）。
- 引用编号 `[1] [2]` **在装配时就固定**并随答案持久化，之后不再重算——否则订正答案时引用会错位。

### 7.3 提示词与拒答

`AnswerPrompt` 把资料按 `[n] 位置\n正文` 排好，要求答案标引用。
`plan.empty()` 时**一个模型调用都不发**：直接返回固定话术、状态 `REFUSED`、`diagnostics.refused()` 计数。
理由：没有资料时问模型就是让它凭参数记忆编——拒答要能和"答错"在评测里区分开，就得有独立状态。

### 7.4 SSE 协议与崩溃语义

```
meta → delta* → done
```
- **流之前的失败返回普通 JSON 信封**（参数错、超过并发上限），不是"流里报错"。前端 `sse.ts` 先按
  `content-type` 判断走哪条分支，并把 `traceId` 拼进错误文案。
- 事件顺序是**契约层断言**之一（回归脚本会检查 `meta→delta…→done` 顺序、`hitCount == hits.length`、
  rrf 仍在 `1/(k+rank)` 量纲）。
- ADR-013「先落库再流式」：`beginAnswer` 先建行（内容空、status=STREAMING），流式期间累积，完成时 `finishAnswer`；
  客户端断线则 `markAnswer(INTERRUPTED)` 保住已吐出的字。**崩溃语义要能恢复出"断在哪"，不能丢整条回答。**
- 专用线程池：4 并发 + 8 队列，`wait-for-tasks-to-complete-on-shutdown` + 20s 等待。

## 8. 反馈闭环与"人工意图是数据"

| 能力 | 实现 | 决策 |
|---|---|---|
| 答案评分 / 反馈 | `chat_message.rating` / `feedback_text` | ADR-015：**null = 不改，空串 = 清空**。REST 的 PATCH 语义只有靠这个区分才不会"改评分顺手清了反馈" |
| 人工订正答案 | `annotated_answer` + `parent_msg_id` | 订正后的答案**成为后续问答的事实**（进 prompt 的资料优先用它），并顺手成为评测样本来源（`rating=-1 AND annotated_answer IS NOT NULL`） |
| 文档级分块覆盖 | `chunk_override` 只存差异 | ADR-016：存快照会导致默认值变更后每篇文档都被"钉"在旧值上；校验放在合并之后，才能验出"覆盖后越界" |
| 单块编辑正文 | `PUT .../segments/{id}/content?reembed=` | ADR-017：**旧向量当场作废**（一条 UPDATE 里 `embedding=NULL` + `edited_at=now()` + `emb_status` 回 `PENDING`，人工标过的 `SKIPPED` 保留），而不是"重算成功才算保存成功"。模型服务挂着时人工修订也要能存进去；这段时间该块只靠关键词路命中 |
| 单块重算向量 | `POST .../segments/{id}/reembed` | 维度与模型名校验在这里；不符时给人类可读 reason 并计入 `embeddingFailures` |
| 块级禁用 | `available=false` | 两条召回路的 WHERE 都排除它 → 关掉后**向量路和关键词路都召不回**（回归脚本对这一段做双向断言，且自带恢复） |

**「人工意图是数据的一部分」这句是本项目最抽象也最值钱的一条**（ADR-018）：
`edited_at`、`available=false`、`emb_status=SKIPPED`、`annotated_answer` 都必须在导入导出后仍然成立。
归档导入因此**故意绕开** `SegmentIndexPublisher`（见 §9）。

## 9. 知识库导出 / 导入（免重算迁移）

### 9.1 包格式（format 1）

```
kb-<id>-<时间戳>.zip
├── manifest.json            元数据：模型名、维度、文档清单、sha256、统计
├── content/{slot}.txt       清洗后正文（slot 从 0 连续编号）
├── segments/{slot}.jsonl    每篇的块（含 base64 向量、父链、位置、available、edited_at…）
└── files/{slot}/{原文件名}   可选：原始文件（files=true）
```
向量用 base64 存（`VectorCodec`），比 JSON 数组短得多，解压即用。
**包结构约定是断言出来的，不是靠人眼看 `unzip -l`**：回归脚本自己读 zip 中央目录 + `inflateRawSync`，
校验「slot 从 0 连续编号」「`content/{slot}.txt` 与 `segments/{slot}.jsonl` 成对」「`files=true` 时每篇都有自己的原件目录」。

### 9.2 两种导入模式

| mode | 触发条件 | 行为 |
|---|---|---|
| `CARRIED` | 模型名与维度都对得上（且 `rebuild=false`） | 向量**直接照搬，一次 embedding 都不花**；绕过索引发布器，逐块写回原始状态 |
| `REBUILT` | 空间不兼容，或显式 `rebuild=true` | 按重新入库排队，等文档变 READY 后检索才完整 |

同 sha256 的文档跳过不覆盖，逐篇说明在 `notes` 里。
两道尺寸闸是分开的：multipart 512MB / 请求 640MB 是容器收字节的限制，
`rag.archive.max-import-mb=512` 是**业务上决定"这么大的包我们真的解不解"**——768 维 base64 后每块约 4KB，几百篇就轻松过 100MB。

### 9.3 ADR-018 为什么绕开发布器

发布器的职责是"把一批新算出来的块原子切成当前生效代次"。免重算导入要还原的是**已经存在的历史状态**，
包括 `available=false`、`emb_status=SKIPPED`、`edited_at` 这些人工意图。
走发布器会把它们一律"发布成可用"，**把用户手动关掉的内容重新塞回答案里**。
这个决定是踩出来的：先按"正常发布"实现，导入后人工禁用的块复活了，才定下绕开。

## 11. 可观测性：health / diagnostics / 日志（M5f）

### 11.1 两个端点，两种问题

| 端点 | 回答的问题 | HTTP |
|---|---|---|
| `/api/health?models=true` | 依赖**通不通**：`postgres` `chineseFullText` `storage` `embeddingConsistency` `modelIds`（+ `embedding` `chat` `modelEcho`） | `ready` 由 `postgres/storage/modelIds/modelEcho` 决定；模型服务没启动只报 `DEGRADED` |
| `/api/diagnostics` | 依赖都通但**结果可疑**：静默降级、预算截断、无证据拒答、向量补算失败，以及配置里的"确定写错"项 | 恒 200（这不是探活，是读表） |

`modelIds` 探为什么能拦 `ready`（ADR-005）：**LM Studio 对认不出的模型名不报错，会用当前已加载的模型应答**——
实测传错 id 也返回 200。静默换模型比报错难查得多，尤其 embedding：越入库越脏。所以模型名要靠**回显**校验，不能只信配置。

### 11.2 四个计数器

`RunDiagnostics`（进程内 `LongAdder` + 最近一次事件）：

| 计数器 | 触发 | 为什么原来看不见 |
|---|---|---|
| `vectorDegraded` | 实际生效模式 ≠ 请求模式，或向量路算失败 | 系统"正常返回"了结果，只是悄悄少走一路 |
| `contextTruncated` | `plan.truncated()` | 答案少了后半段，用户以为模型能力差 |
| `refused` | `plan.empty()` | 拒答文案像"答不上来"，像模型问题 |
| `embeddingFailures` | 补算向量被拒 / 批量维度异常 | 单块向量置空后只是"搜不到" |

**重启归零是可接受的**：它的设计目的是"把静默失败变成一条能查的数"，长期统计靠日志文件。
（被问"为什么不用 Micrometer/Prometheus"就答这句——单机私有化没有采集端，先保证 WARN 落文件带 traceId。）

### 11.3 只有两条配置告警（克制是设计）

- `min-rrf-score > 1/(rrfK+1)`（默认即 `> 0.0164`）→ 文案直说「混合检索会长期 0 命中，看起来像库里没资料，
  这个阈值只能待在 0.01x 量纲」；
- `child-chars > 480` → 超过 bge 系列 512 token 窗口（约 480 汉字），**超出部分被模型静默截断**。

只报"配了但几乎一定是错的"那种，不报"看起来偏低"——代码注释原话：**告警一多就没人看，和没有一样。**

### 11.4 日志与 traceId

- `logging.pattern.correlation = "[%X{traceId:-}] "`；`TraceIdFilter` 生成并经 `X-Trace-Id` 回给前端，
  同时写进 JSON 信封和 `chat_message.trace_id`——**用户报障时贴一个字符串就能定位到日志**。
- 一次问答横跨 HTTP 线程与 `rag-chat-*` 线程，所以 `ChatExecutorConfig` 装了 `MdcTaskDecorator`
  （Boot 4.1.2 classpath 上没有现成的，自己写）。语义要点：**执行完恢复该线程原来的 MDC，而不是清空**——
  否则上一个请求的 traceId 会跟着线程去服务下一个请求（专门写过一条测试断言这点）。
- 文件日志交给 logback：UTF-8、20MB 滚动、留 14 天、封顶 500MB；`start.sh` 把控制台另写到 `rag-api.out`。
  原因：**Windows 控制台是 GBK**，中文 WARN 只有进 UTF-8 文件才换得了机器、进得了编辑器。

## 12. 部署与回归

### 12.1 起停（`deploy/start.sh` / `stop.sh`）

`cp .env.example .env` 之后两条命令：`start.sh`（PG 容器 → 打包并起 rag-api → 起 rag-web → 自检门）、
`stop.sh`（`--keep-db` 只停应用；`--purge-data` 要手输 `PURGE` 才删数据卷）。
进程一律 pid 文件 + `nohup`，日志进 `deploy/logs/`，**重复执行幂等**（pid 还活着就跳过，不会撞第二次端口）。
脚本只出 `.sh` 不出 PowerShell 版——`docker/mvn/curl` 的用法在实测指导里已统一按 Git Bash 写，维护两份只会让两份漂移。

三个决定是这台机器教出来的（讲"踩坑"就讲这三个）：
1. **环境预检排在建镜像之前**：zhparser 首次编译 5–15 分钟，Node 版本够不够 0.2 秒就能判定。
   失败文案直接给「`nvm use 22` 再重跑，后端只认 JDK 17 不受影响」。
2. **`docker info` 必须套 `timeout`**：引擎没起来时它不是返回错误，是**一直挂着等**——现象从"报错"变成"脚本卡住不动"，
   最难转述。现在 15 秒没返回判死，并给 BIOS/WSL2 虚拟化处置路径。
3. **8080 上已有应答时不静默复用**：自检门只看 `/api/health` 的 `ready:true`，而任何忠实实现这个契约的服务
   （包括前端联调用的 mock）都会答 true。检测到"有应答但没有本脚本的 pid 文件"就明说是别人占着端口——
   否则下一步的绿是假的。

### 12.2 端到端回归（`smoke.sh` + `smoke.mjs`）

一条命令跑完实测指导 §4~§11：health → 建库/选库 → 上传 `samples/` 全部七份 → 轮询终态 →
三种模式检索 → 契约负例 → 流式问答 → 块级禁用可逆 →（可选 `--archive`）导出/删除/导入 → 诊断对账。
退出码 0/1/2，失败清单一条一行，每条带后端原文 `message` 与 traceId。

**实现选择：不用 bash+curl+jq。** SSE 切帧、zip 中央目录解析、断言台账这三件事在 shell 里都是硬写，
Node 单文件反而短。`smoke.mjs` 零依赖，`fetch/FormData/Blob` 直接用，因此它也要求 Node 20.19+，由 `smoke.sh` 拦住。

**ADR-019 两层断言**（这一条最能证明工程判断力，值得整段背）：
> 一条命令验全链路的脚本最容易死在两种情况下：**换环境就跑不动**，以及**跑绿了但什么都没验**。
> 所以断言拆成契约层（信封、字段、事件顺序 `meta→delta…→done`、`hitCount==hits.length`、
> rrf 仍在 `1/(k+rank)` 量纲、错误都在写数据之前返回 4xx）
> 和事实层（`04/05` 必须 `GARBLED_TEXT`、`06` 必须判成同 sha 重复、"备份保留 35 天"必须出现在答案里、
> 关掉 `available` 的块两条检索路都召不回）。
> 事实层只认 `samples/` 里故意写死的数字——**改样本就得改期望表，这是有意的耦合，两边不同步时必须有一边报错**。
> 代价是需要一个能答契约的东西来自检脚本本身：给前端联调用的 mock 补了会推进的入库状态机、真 sha256 去重、
> 可解压的归档包和"导入只放回 READY"，于是 `smoke.sh --shape-only` 在没有数据库和模型的机器上也能跑完契约层。
> 反过来，同一条脚本对 mock 打开事实层会稳定报 7 条**断言失败**（不是异常）——这正是想要的形态：
> **脚本崩了要修脚本，断言红了要查系统，两种现象不能混。**

## 15. 面试问答（60 题）

> 每题答案是**口语长度**，按 §0.2 的三段模板组织过。先自己答一遍再对照。

### A. 项目与业务（1–8）

**1. 这系统是干什么的，给谁用？**
内网自用的知识库问答：把公司文档灌进去，员工自然语言提问，答案带原文引用可溯源。给非技术同事用，
所以前端只有问答、检索调试、文档管理、设置四个页面，不给他们配置项地狱。

**2. 为什么要自研，不用现成平台？**
见 §3 那段话术：要的是四个不能是黑盒的点（字符级溯源、重算原子性、免重算迁移、降级可见）。

**3. 私有化的必要性在哪？**
文档本身敏感（合同、台账、运维手册），云端 API 意味着把原文发出去。本地推理的代价是窗口只有 4096、
吞吐有限，这个约束直接塑造了 §7 的预算设计。

**4. 你一个人做，需求从哪来？**
从"我要能用它查我自己的资料"来，加一圈业界功能对标（§1.2 那张表）。我把它写成编号的硬性约束清单，
比如"RRF 阈值不能照抄余弦阈值"就是踩过之后写进去的。

**5. 项目现在能上线吗？**
功能面能跑，缺三件：量化评测（M5e）、rerank（M5g）、鉴权与多租户（明确没做，边界靠局域网）。
**主动说这三件**比含糊过去强。

**6. 最大的技术风险是什么？**
本地模型的行为不可信：认不出的模型名不报错、超窗口静默截断、批量返回条数偶尔和请求不符。
所以我把"信回显、信列在不在、逐条校验维度"写进代码而不是文档。

**7. 数据量目标多少？**
部门级：几百到几千篇文档、几万到几十万块。这个量级 HNSW + GIN 完全够，也是我敢用单 PG 不引专用向量库的前提。

**8. 如果公司要接几十万人用，架构哪里先撑不住？**
三处：单卡推理吞吐（要换推理服务 + 批处理/量化/多副本）、pgvector 的 HNSW 内存（要分库或专用向量库）、
以及任务队列靠 `SKIP LOCKED` 的单机吞吐（要换 MQ + 多 worker）。我会说"现在的架构是**刻意**为单机内网做的最优选"。

### B. RAG 原理与调优（9–28）

**9. RAG 整条链路你怎么切分？**
入库（解析→清洗→分块→向量化→索引）和问答（检索→装配→生成→落库）两段，中间靠"块 + 向量 + 元数据"解耦。
**能被这样切的好处是每段都能单独验**——我的回归脚本就是按这两段分步骤组织的。

**10. chunk 大小怎么定的？**
不是试出来的审美值，是**从模型窗口反推**：bge-base-zh 512 token 静默截断，中文约 1 字 1 token，留余量到 400。
再加最小 120（低于它没语义）、重叠 60、父块 1200。并在诊断里对 >480 出告警。

**11. 为什么要父子块？**
两个诉求天然冲突：embedding 要短（准），给模型的上下文要长（全）。子块负责命中，父块负责作答，
靠 `parent_id` 关联，命中子块换父块正文，同父块去重成一个引用。

**12. 重叠是必须的吗？**
对一个几乎没有句号的长段落是必须的——退化成定长窗口时，60 字重叠保证边界事实不被切两半。样本 03 就是专门验它的。

**13. 混合检索为什么需要？纯向量不行吗？**
纯向量对专名、编号、精确短语不稳（"OPS-2026-118" 这种串在向量空间里不邻近）。中文全文检索负责字面命中，
向量负责语义。**两路的失败模式互补**，所以融合后收益是实打实的。

**14. 为什么用 RRF 而不是加权分数？**
量纲不同没法加权：`ts_rank` 和余弦相似度的数值范围与分布都没可比性。加权求和等于让其中一路说了算。
RRF 只用排名，天然可比。代价是丢掉绝对置信度，所以阈值尺度要换（→ 15）。

**15. 阈值怎么定的？**
按**生效模式**配：纯向量用余弦 0.45，混合用 RRF 0.012。RRF 理论最高分是 `2/(k+1)`（两路都第一）或
`1/(k+1)`（单路），量纲在 0.01x。把 0.45 抄到混合模式会**把所有结果滤光**——这是我踩过的最贵的一个坑。

**16. topK 和 candidateK 什么关系？**
每路先取 `candidateK=40` 候选参与融合，融合后取 `topK=6` 进上下文。candidateK 太小融合没意义（两路交集太少），
太大浪费排序。小库里 40 已覆盖绝大多数场景。

**17. 召回效果差怎么排查？**
按顺序：**先看它是不是根本没走那一路**（meta 里的 `effective` / `engine` / `degraded`；诊断的 `vectorDegraded`），
再看块在不在（`available`、`emb_status`、`edited_at` 是不是被人工关了或跳过），
再看分块是否切碎（分块预览页直接看切出来的块），最后才调参数。
这个顺序反过来说明我为什么把降级做成可见的——90% 的"搜不到"是静默失败，不是算法差。

**18. 幻觉怎么治？**
三道：① 无证据**不调模型**直接拒答（`REFUSED`）；② 提示词只让引用给定资料并要标 `[n]`；
③ 溯源面板把原文摆出来，用户能立刻核对。不是靠 prompt 说"别编"。

**19. 拒答和答错在系统里怎么区分？**
`chat_message.status`：`REFUSED` 是空召回，`OK` 是模型答了（可能对可能错，靠 `rating`/`feedback` 事后判定）。
这个区分是为评测准备的——拒答正确率和答错率必须分开算。

**20. 长文档、大表格怎么办？**
表格在清洗时保留行内空格（空格是内容），分块按父块 1200 字容错；解析弄乱时用户可以直接编辑那一块（`reembed` 可选）。
真正的表格结构化（行列还原）我没做——这是范围外。

**21. 扫描件 / 图片型 PDF？**
没做 OCR。但做了识别并拒收：CID 字体乱码（可解释字符占比）或空正文一律 `GARBLED_TEXT`，
**宁可 FAILED 也不要静默灌噪声**。

**22. 多语言？**
中文优先：分词、字符/token 系数、按字符预算都按中文设定。英文资料能入库检索，
但没有专门调过；`charsPerToken=1.0` 对英文偏保守（会少装）。

**23. rerank 什么时候该加？**
候选量上来、且 topK 内相关度排序明显不稳时。设计好了：默认关、rerank 调用失败**退回原序**（不能让增强变故障源）。
没做的原因是本地单卡多一次 cross-encoder 推理很贵，我想先有评测集再决定它值不值。

**24. 怎么防提示词注入（文档内容里的恶意指令）？**
诚实答：现在没有专门防护，只有"答案必须引用给定资料 + 用户可核对原文"这道软防。真上生产我会加
① 入库时对可疑指令文本打标，② 系统提示与资料段做更硬的边界，③ 对导出/导入包做来源校验。

**25. embedding 换模型会怎样？**
必须全量重算。库里存了 `embedding_model`，启动校验不一致（`embeddingConsistency` 探针），
因为维度可能同为 768 但空间不同，混用就是污染检索——这比报错隐蔽。

**26. 为什么余弦不用内积或 L2？**
embedding 归一化后余弦与内积单调等价，而 `vector_cosine_ops` 的 HNSW 索引语义直观（`<=>` 距离，相似度=1-dist）。
本地小库没必要在内积上优化。

**27. 检索结果重复怎么处理？**
父块去重：同一父块的多个子块只装一次且不产生新引用。跨父块的近重复我没做语义去重（评测集上线后值得加）。

**28. 知识库之间会串吗？**
不会。`kb_id` 谓词写进**每一路自己的 WHERE**，问答的 `kbIds` 必须显式指定；范围谓词不物化 CTE 是为了让两路各自走索引。

### C. 后端与数据（29–44）

**29. 为什么 JdbcTemplate 不用 JPA？**
检索侧全是 CTE、窗口函数、向量算子、GIN 命中——ORM 只会挡路。写侧表少字段直白，手写 SQL 反而清楚。
代价：RowMapper 自己维护。

**30. 6 张表里最关键的设计是什么？**
`kb_segment` 的 `doc_version` + `available` 代次机制（重算原子性），和 `edited_at`（人工意图的时间戳）。

**31. 重算时用户还在检索，怎么保证不读到半成品？**
整代新块先以 `available=false` 落库（文本 + 向量一起写），全部就绪后在**同一个 `@Transactional`** 里翻开关、
删旧代次、把文档置 READY（ADR-007）。中间还有一道守卫：**只要有可检索块缺向量就抛异常回滚，拒绝放开这一代**。
所以并发读者要么看到完整旧的一套，要么完整新的一套；崩溃就整体回滚可重试，不存在"旧块删了新块没放开"的空召回死态。

**32. 事务边界画在哪？**
索引发布：一条事务。单块编辑：**一条 UPDATE 同时改正文、把 `embedding`/`embedding_model` 置 NULL、写 `edited_at`、
重置 `emb_status`（但 `'SKIPPED'` 保持 SKIPPED——那是人工决定，不该被编辑动作覆盖）**，
模型补算在这条语句之后再做（否则慢推理会拖住行锁）。
问答：写问题/开始答案/收尾各自独立短事务，流式期间不持事务。

**33. 并发怎么控？**
入库 `concurrency=1`（单机单卡，>1 只让 embedding 排队撞超时）；问答专用池 4+8，超了明确拒绝；
DB 池 10。三个数都是"单机内网"的取舍。

**34. 队列为什么用表不用 MQ？**
`FOR UPDATE SKIP LOCKED` + 租约 + 重试列已经覆盖我要的语义（至少一次、崩溃回收、退避），
而引入 MQ 就多一套要备份的有状态组件——私有化部署里这是净负担。

**35. 任务卡住了怎么自愈？**
租约 10 分钟过期后被 `reapExpiredLeases` 回收重排（`idx_task_lease` 支撑扫描），worker 启动时先立刻跑一次回收；
停在中间态的文档由 `IngestStartupRecovery` 落地成 `FAILED` + 可重试（不能让它永远转圈）；
关停时 `@PreDestroy` 释放自己持有的任务。`attempt/max_attempts` 防死循环，永久失败直接终态。

**36. 大文件上传要注意什么？**
两道闸分开：multipart 512/640MB 是容器收字节，`max-import-mb=512` 是业务决定解不解；
普通文档另有 100MB 单文件限制。**改 multipart 不会放宽文档尺寸**，这一点写在配置注释里。

**37. Flyway 为什么用占位符？**
`embedding_dim` 是 schema 的一部分，必须和配置同源；不同源时启动校验直接报错——列宽不对，向量写不进去。

**38. 为什么自建 PG 镜像？**
官方镜像没 zhparser。编译扩展、建 `chinese` 配置（映射 `n,v,a,i,e,l,j,x WITH simple`），
并在 migration 里**条件建** tsvector 生成列——扩展不在就只留 trgm。

**39. 为什么 tsvector 用生成列而不是应用层写入？**
改正文时自动重算，没有一致性窗口，也不需要维护一条"记得同步 tsvector"的规则。
代价：列定义依赖 zhparser，所以建列必须写在条件 DDL 里。

**40. 接口怎么做错误契约？**
统一信封 `{code,message,data,traceId}`；**参数/权限类错误在写任何数据之前返回 4xx**（回归脚本断言这条），
业务异常带给人看的话并附 hint，5xx 记 error 级日志 + traceId。

**41. 为什么问答要 SSE 不用 WebSocket？**
只需要服务端单向推流。SSE 是普通 HTTP，代理和脚本都好处理；浏览器侧 `EventSource` 不支持 POST，
所以我用 `fetch` 读流自己切帧。

**42. 客户端断线怎么处理？**
已吐出的字回填成 `INTERRUPTED` 而不是删掉——界面和评测都能看到"断在哪里"。这是 ADR-013 的另一半：先落库再流式。

**43. 配置项怎么组织这么多？**
一个 `RagProperties` 前缀 `rag.*` 全类型化绑定，`application.yml` 里每个非显然的值都带一行**理由注释**。
面试时我说："注释只写为什么，不写是什么。"

**44. 如果让你加鉴权，怎么改？**
信任边界先从"局域网"改成"进程外"：入口加 OIDC/反向代理鉴权，`LM Studio` 的 1234 必须加 token 并只绑 127.0.0.1，
然后补多租户（`kb_id` 已经天然是租户边界，要做的是权限表和接口层过滤）与审计日志。

### D. 前端（45–50）

**45. 为什么不用 axios？**
ADR-014。所有请求都是同源 `/api`，拦截器的价值小；而 SSE 必须手写解析，axios 帮不上。少一个依赖，
`http.ts` 里统一处理信封和 traceId 就够。

**46. 浏览器 SSE 怎么自己实现？**
`fetch` POST + `Accept: text/event-stream`，`response.body.getReader()` + `TextDecoder('utf-8')`，
按 `\r?\n\r?\n` 切帧（正则容忍 `\r\n`），帧内解析 `event:`/`data:`，**半帧留在 buffer 里等下一块**。
不做自动重连：回答是一次性推理，重连等于让模型重答一遍。

**47. 流式渲染卡顿怎么解？**
增量拼字符串而不是每 token 重渲整段 markdown——渲染在帧结束时做，delta 只更新文本。
（被追问就说这是我知道的下一步优化点，别吹成做过。）

**48. 状态为什么用 Pinia？**
四个 store 分域（会话/文档/健康/偏好），偏好靠 persistedstate 落本地。组件间只共享数据不共享流程。

**49. 类型检查进构建了吗？**
`npm run typecheck` = `vue-tsc --noEmit`，build 先跑它。API 响应有 `types/`，SSE 事件形状有判别联合——
契约变了编译期就红。

**50. 引用位置怎么展示？**
`SourcePanel` 按 `[n]` 展开原文，位置优先 `heading_path`，其次页码，再次字符偏移；
`edited_at` 非空时明示"块正文被人工改过，偏移量描述的是编辑前位置"（否则用户会对不上）。

### E. 质量与交付（51–56）

**51. 208 例单测测的是什么？**
纯代码层：分块器边界与重叠、清洗与乱码判定、RRF 融合与阈值选择、降级矩阵全组合、预算算术与截断、
上下文装配去重、归档编解码、MDC 装饰器语义、诊断端点形状与告警。全部不碰库不碰模型，`mvn -o test` 一条命令。

**52. 那集成测试呢？**
4 个 Testcontainers IT：`SchemaMigrationIT`（真 pgvector 上迁移与谓词能力，**故意用不含 zhparser 的官方镜像**覆盖降级分支）、
`RetrievalIT`（混合检索 SQL）、`IngestPipelineIT`（解析→分块→向量→发布全链路，embedding mock）、
`LmStudioConnectivityIT`（真机 models/embed/chat）。

**53. 为什么单测不连库？**
连库测试跑不动的环境就多（我这台机器虚拟化没开就是活例）；核心逻辑在纯代码层能被完全覆盖。
"不连库也能验"的层次越厚，换环境的成本越低——这条在回归脚本上也复现了一次。

**54. 回归脚本怎么防"跑绿了但什么都没验"？**
两层断言（ADR-019 整段话）。

**55. 为什么脚本用 Node 不用 bash？**
SSE 切帧、zip 中央目录解析、断言台账三件事在 shell 里都是硬写。Node 单文件零依赖，
和前端一样要求 Node 20.19+，版本由 `smoke.sh` 前置拦住。

**56. 覆盖率看过吗？**
没把覆盖率当验收指标（它测的是"执行过"，不是"断言过"）。我更看断言的有效性：样本事实绑死 + 契约层/事实层分离。
真要说指标，我用的是"里程碑退化能不能被一条命令发现"。

### F. 压力与追问（57–60）

**57. 这项目最难的地方在哪？**
不是算法，是**静默失败的集合**：模型静默换、窗口静默截、扩展静默缺、阈值静默清空召回。
每个都不报错，但都让答案变差。我的解法是把它们全部变成可读的信号（生效模式/引擎/计数器/告警/WARN+traceId）。

**58. 你说没做评测，那你凭什么说检索是好的？**
"我只有**证据级的弱保证**：写死事实的样本 + 端到端断言 + 分块预览可人工核对。这能证明链路对，
不能证明排序优。所以我把它列成下一个里程碑，样本来源都想好了——
`rating=-1 AND annotated_answer IS NOT NULL` 的消息就是天然标注集。"（承认边界 + 有方案 = 加分）

**59. 如果给你两个人一个月，你砍什么、加什么？**
砍：归档导出导入（迁移场景一年用不了几次）、SettingsView 的富配置。
加：评测集与跑分（**所有调参的前提**）、rerank、鉴权。
答这题的原则：**别表现成"我都想留"**——那说明没评估过成本。

**60. 你这个项目有什么是你现在觉得做错了的？**
① 评测排到 M5e，太晚；② 前端曾计划更多依赖，后来请求层删到只剩 fetch，返过工；
③ 一开始把 `min-score` 当成全局阈值用，酿成 §15-15 那个坑，之后才补了"硬性约束清单"这个机制。
（这题必须有答案，"没觉得哪里错"是最差答案。）

## 16. 没做 / 讲不出来的部分，怎么答

### 16.1 检索质量没有量化
> "评测集是 M5e，还没做。现在我对召回的信心来自三层弱保证：写死事实的样本断言、分块预览的人工核对、
> 诊断计数器把静默降级暴露出来。量化指标（hit@k、MRR、空召回率、拒答正确率）是我下一件事，
> 样本来源已经确定：反馈里 `rating=-1` 且已人工订正过的答案就是天然标注对。"

### 16.2 本机集成测试没跑过（虚拟化没开）
> "我这台机器 WSL2 虚拟化当时是关的，Docker 引擎起不来，所以 Testcontainers 的 4 个 IT 和事实层断言
> 我留成了待办。为了让'回归本身'不依赖这些，我给 mock 补了契约层能力，`--shape-only` 能全绿。
> 这是刻意设计——脚本坏了和系统坏了要能分开。"

### 16.3 没有鉴权和多租户
> "需求写死了信任边界是局域网：模型端口 1234 不对外映射，`.env.example` 里连这条都注明了。
> 这不是'忘了安全'，是我明确记录了范围外并给出了改法（§15-44）。如果对方要求生产安全，我把它当第一批待办。"

### 16.4 性能没有基准数字
> "我只报我实测过的：embedding 16 条一批 0.41 秒、单条 0.04 秒，这是本地单卡 + bge-base-zh 的数字，
> 不外推。问答首 token 延迟我没压测，因为它由模型加载与 `n_ctx` 决定，不在我的代码里。"

### 16.5 被问 pgvector 内部机制（HNSW 参数细节）
> "`m=16 / ef_construction=64` 是我抄的 pgvector 文档推荐起步值并显式写进 DDL。查询期的 `ef_search`
> 我没调——小库里全扫和索引扫差别不大。要调的话我会先有评测集，否则是在噪声上调参。"

## 17. 自述稿与最后检查

### 17.1 三分钟自述（面试官说"介绍下这个项目"）

> "我做的是一个**内网私有化的知识库问答系统**，前端 Vue 3 + TS，后端 Java 17 + Spring Boot，
> 数据和模型全部不出内网，模型是 LM Studio 跑的 qwen2.5 加一个 768 维中文 embedding。一个人完成，
> 31 个接口、6 张表、4 个前端页面、208 例单测加一条命令的端到端回归。
>
> 链路两段：入库做了解析、文本治理、中文语义分块、批量向量化和**原子索引发布**；
> 问答做了向量 + 中文全文**双路召回、RRF 融合**、按模型窗口反推的**上下文预算**、SSE 流式和**引用溯源**。
>
> 我最想讲三件事。第一，中文全文检索在官方 PG 镜像里没扩展可用，我自己编译了 zhparser 镜像，
> 并且把"扩展缺失"设计成**三级降级**而不是启动失败。第二，混合模式分数在 0.01x 量纲，
> 我一开始把余弦阈值抄过去，结果召回被清空——从那以后阈值变成**生效模式的属性**，
> 并且降级、截断、拒答这四类静默失败全部进了 `/api/diagnostics` 计数器。第三，
> 回归断言分**契约层和事实层**：契约层在没有数据库和模型的机器上也能全绿，
> 事实层绑死我特意写死的样本文档，这样'脚本坏了'和'系统坏了'是两种不会混淆的信号。
>
> 边界我也说清楚：检索质量还没量化评测（M5e 待办）、没做鉴权和多租户，因为需求把信任边界定在局域网。"
